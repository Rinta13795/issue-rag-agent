## Bullet 1：LangGraph 四节点工作流

### 【简历原文】
> 基于 LangGraph 编排四节点 workflow（Query Analysis → 混合检索 →
> Cross-Encoder 精排 → LLM 决策），实现开源社区 Issue 智能分诊 Agent，
> 输出 duplicate / similar / new 判定与置信度。

### 【面试官会怎么问】

**Q1（必被问）：为什么用 LangGraph？不用行不行？**
- **口语答案**：说实话，这个规模用普通函数链也写得出来。我选它有三个实际原因：
  一是它的共享 State 模式——每个节点只返回自己新增的字段，框架做合并——正好
  匹配我"重试时大部分字段覆盖、历史字段追加"的需求，不用手写状态管理；二是
  条件边把"低置信度回环"表达得干净，流程图就是代码；三是我确实想按主流编排
  框架的方式组织项目，方便以后加节点。但我会主动说清楚：它是条件工作流，不是
  自主 Agent，LLM 没有"决定下一步干什么"的权力，唯一的分支是我写死的那条
  置信度判断。
- **追问链**：
  ① "State 具体怎么合并的？"→ TypedDict 12 个字段，节点返回 dict，框架做
  update：新键加入旧键覆盖；previous_decisions 是唯一追加的，我在节点里 copy
  后 append 防止原地污染。
  ② "为什么不叫它 Agent？"→ Agent 意味着模型自主选工具/规划步骤；我的流程
  固定四步，模型只在"要不要重试"上有间接影响（通过置信度），自主性被刻意
  限制成一条条件边——分诊场景要的是稳定可解释，不是自由发挥。
  ③ "如果要加一个'搜代码库'的节点，改动量多大？"→ 加节点函数+两条边+State
  加字段，其他节点不动——这正是当初选图结构的回报。
- **翻车提示**：把它吹成"多 Agent 系统""自主智能体"必翻——追问一句"你的
  Agent 自主决策了什么"就露馅。低调反而加分。

**Q2：四个节点分别的输入输出是什么？**
- **口语答案**：Query Analysis 吃原始 issue 文本，吐改写 query、关键词列表、
  组件猜测；Retrieval 吃改写 query 和原文，吐 RRF 融合后的 Top-30 候选；
  Rerank 吃 query 加 30 条候选，吐带精排分的 Top-5（分差小时最多扩到 10）；
  Decision 吃 query、关键词和 5 条候选的正文摘要，吐三分类、置信度、关联
  id 和理由。全程走共享 State，出口只暴露五个字段。
- **追问链**：① "候选长什么样？"→ dict：id/title/body/metadata/score，score
  是 RRF 融合分不是相似度；② "Decision 看多少正文？"→ v2 每候选 400 字符
  （v1 是 200，因为 v2 有 docstore 补齐才敢加量）；③ "改写失败怎么办？"→
  双层兜底，解析不出 JSON 就直接拿原文当 query，流程不断。
- **翻车提示**：说不出"score 是 RRF 分不是余弦相似度"这种字段语义，会被判定
  为"跑过 demo 没读过代码"。

**Q3：重试机制怎么工作？**（详见 Bullet 4，此处一句话版）
- **口语答案**：Decision 置信度低于 0.7 且没超过 2 次上限时，条件边把流程送回
  Query Analysis，重写 prompt 里带上一轮的判断、检索诊断和 Top-3 候选，整轮
  重跑，最多 3 轮。
- **翻车提示**：retry_count 语义要说准——它是 Decision 执行轮数（首轮结束=1，
  最大=3），说成"重试了 3 次"就和配置 MAX_RETRIES=2 对不上。

**Q4：这个"分诊 Agent"输出错了谁负责？怎么被人使用？**
- **口语答案**：定位是辅助分诊不是自动关单。高置信 duplicate 给维护者一个
  "先看这条"的强提示，similar 是参考列表，new 走正常流程；最终动作永远是人做。
  为了让人敢信，我做了两件事：related_issues 过候选白名单，绝不返回编造的
  id；reasoning 必须引用具体候选特征，可核查。
- **追问链**：① "白名单怎么实现？"→ 校验层用本轮精排候选的 id 集合过滤 LLM
  输出；② "如果过滤后一个 id 都不剩？"→ 说明结论没有可核查证据，降级成 new
  并把置信度压到 0.4 以下，触发重试；③ "误报的代价？"→ 最贵的是高置信误判
  duplicate 导致误关 issue，所以评估里要单列这类错误（这是我 v3 计划里
  三分类标注集的用途）。

**Q5：你说"四节点"，Rerank 和 Decision 为什么不合并成一步让 LLM 直接挑？**
- **口语答案**：成本和可靠性。让 LLM 读 30 条候选，token 费用比 Cross-Encoder
  贵一个量级，而且长上下文里真答案容易被淹没（Lost in the Middle）。
  Cross-Encoder 把 30 压到 5，LLM 的任务从"大海捞针"变成"5 选 1 的比对推理"，
  又便宜又稳。
- **翻车提示**：答"因为教程都这么写"= 没做过权衡。

### 【可信度自查】
必须答得上：Q1 的"为什么不叫 Agent"、Q2 的字段语义、Q3 的 retry_count 语义。
这三个都是"读没读过自己代码"的试金石。答不上的话这条 bullet 不用删，但把
"Agent"改成"工作流/Workflow"更安全。

### 【表述边界】
- ✅ LangGraph 四节点、条件边重试、State 管理——两版都有，可以直说。
- ✅ 白名单校验、无证据降级——**仅 v2**；如果面试官看的是 GitHub 版，要说
  "线上仓库还没推这部分，本地 v2 已实现并有单测"。
- **过头的话**："我实现了一个自主 Agent""模型会自己规划检索策略"——说了就是
  给自己挖坑。

## Bullet 2：混合检索与 RRF 融合

### 【简历原文】
> BM25 + 向量双路召回 Top-30，RRF 融合解决量纲不一致问题，
> BGE-Reranker 精排取 Top-5 送入 LLM 判定。

### 【面试官会怎么问】

**Q1（必被问）：RRF 是什么？公式？为什么不用加权融合？**
- **口语答案**：倒数排名融合。每个文档在每一路结果里排第 n 名，就得
  1/(k+n) 分，k 我用 60，两路分数加起来排序。它只看名次不看分数，正好绕开
  量纲问题——BM25 分数没上界，余弦相似度在 0 到 1，直接加权得先归一化，而
  min-max 归一化对每次 query 的分数分布特别敏感，权重 α 还得要验证集去调，
  我当时连可信评测集都没有。k=60 是 Cormack 2009 年在 TREC 上验证的经验值，
  我直接用了，没数据支撑我去调它。
- **追问链**：① "RRF 丢了什么信息？"→ 分数的绝对置信度——某一路"非常确定"
  和"勉强第一"在 RRF 眼里一样，这个损失我靠下游 Cross-Encoder 重打分兜回；
  ② "k 调大调小会怎样？"→ k 小头名优势放大、单路易独大；k 大排名趋于平权；
  ③ "你的 RRF 有几层？"→ 两层：每条 query 内融合向量+BM25，改写和原文两条
  query 之间再融合一次，同一 issue 被多路命中就多次加分。
- **翻车提示**：公式写不出来直接出局；说"RRF 是加权平均"也是硬伤。

**Q2：为什么要 BM25，向量不是更先进吗？**
- **口语答案**：issue 查重有两类信号。错误码、异常类名这种精确 token——
  `MOZ_CRASH`、`NullPointerException`——是低频词，BM25 的 IDF 机制天然给它们
  超高权重，一命中就顶到前排；向量模型反而会把不同错误码嵌到相近位置，因为
  它们"语义上都是错误"。反过来，"点登录就闪退"和"crash on login button"没有
  一个词相同，只有向量能召回。两路召回的是不同的子集，谁也替代不了谁。
- **追问链**：① "BM25 的 TF 饱和是什么？"→ 词出现 10 次不比 5 次贡献翻倍，
  k1 控制（我用库默认 1.5）；② "实测两路差多少？"→ v2 抽样 200 条：向量
  recall@30=0.48，BM25=0.43，向量略优但延迟差 100 倍（22ms vs 2.9s）；
  ③ "BM25 慢怎么办？"→ rank-bm25 是纯 Python 全库打分，这是最大瓶颈，换
  Elasticsearch/Tantivy 是 v3 第一优化项。
- **翻车提示**：说"BM25 是老技术所以效果差"——我的实测里它 recall 只比向量低
  5 个点，还便宜；贬低它反而暴露没测过。

**Q3：为什么 Top-30？为什么精排后是 Top-5？**
- **口语答案**：30 是召回层的"宁滥勿缺"——召回丢了后面全完，K=5 在召回层会
  漏真 duplicate。5 是判定层的"宁精勿滥"——控制 LLM 的阅读量和注意力。中间
  用 Cross-Encoder 完成 30→5 的压缩。另外我做了动态截断：第 5、6 名分差小于
  0.05 就继续放，最多到 10，防止真答案恰好卡在第 6 被硬切。
- **追问链**：① "Cross-Encoder 和向量模型区别？"→ 双塔独立编码可预计算扛
  规模，交叉编码拼接输入逐层交互精度高但逐对现算；② "为什么不用大点的
  reranker？"→ base 版对"30 里挑 5"够用，large 在 CPU 上单轮多几秒；③ "动态
  截断有数据支撑吗？"→ 🟡 诚实说：机制有单测，但"扩展 vs 固定 5"的消融还没跑，
  在我的消融计划里。
- **翻车提示**：被问"30 和 5 怎么定的"答"随便定的"会崩——正确姿势是讲清两层
  各自的目标函数（召回覆盖 vs 注意力预算），再承认精确值未做网格搜索。

**Q4：BGE-Reranker 输入是什么？截断怎么处理？**
- **口语答案**：每条候选组成 (query, 标题+正文前 800 字符) 的文本对，批量
  打分。截 800 是因为底层 BERT 约 512 token 上限，不主动截会被模型内部不一致
  地截。这里有个 v1 的坑：只被 BM25 召回的候选正文是空的，Reranker 对着空
  字符串打分——v2 我用 docstore（id 到正文的映射文件）在融合后补齐，冒烟
  测试里 30 条候选全部有正文。
- **追问链**：① "为什么不覆盖向量路候选的正文？"→ 它们的 body 是命中的
  chunk，是与 query 最相关的片段，比正文开头更好的精排证据；② "800 字符外的
  证据怎么办？"→ 承认盲区，改进方向是"最相关 chunk 拼接"替代"开头截断"；
  ③ "rerank 分数是概率吗？"→ 不是，只能同 query 内比大小，所以我只拿它排序
  和算分差，不做跨 query 的阈值。
- **翻车提示**："双路并行召回"这个词慎用——实现是**顺序执行**的（先向量后
  BM25），说"并行"被追问线程模型就尴尬；说"双路召回、逻辑上互相独立"最稳。

**Q5：融合后去重怎么做的？两路信息冲突怎么办？**
- **口语答案**：按 issue id 聚合，RRF 分数累加。信息保留有个细节：同一 id
  在一路只有空正文（BM25-only）、另一路有 chunk 正文（向量路）时，保留证据
  更完整的版本；外层融合同分时靠 Python 稳定排序保证改写主路排前。
- **翻车提示**：这题答不出细节没关系，但不能答错方向（比如说"取两路分数最大
  值"）——排序融合的核心是"累加共识"。

### 【可信度自查】
必须答得上：RRF 公式与两层结构、BM25 vs 向量的信号分工、30→5 的两层目标、
空正文候选问题。前两个答不上，这条 bullet 建议改写成"混合检索（BM25+向量）+
重排序"这种不点名 RRF 的弱化版——写了 RRF 就一定会被问公式。

### 【表述边界】
- ✅ 双路召回、双层 RRF、动态截断、（v2）docstore 补齐——已实现有单测。
- 🟡 "BGE-Reranker"没问题（真实是 bge-reranker-base），但**"BGE 向量化"在
  v2 不成立**（embedding 是 all-MiniLM-L6-v2）——见 Bullet 3。
- **过头的话**："并行召回"（实现是串行）；"RRF 权重调优过"（k=60 是文献
  默认值，没调过——直说反而专业）。

## Bullet 3：数据构建（清洗/切分/向量化/倒排）

### 【简历原文】
> 处理 GitBugs 15 万条 bug report：清洗去噪（HTML/invalid/wontfix），
> title / error_log / body 结构化切分，BGE 向量化写入 ChromaDB，
> rank-bm25 构建 issue 粒度倒排索引。

### 【面试官会怎么问】

**Q1（必被问）：为什么切三种 chunk？**
- **口语答案**：issue 里混着三种性质完全不同的文本：标题是人写的最强摘要；
  错误堆栈是机器输出的精确指纹；正文是自由描述。混在一个向量里会互相稀释——
  一条三千字的帖子，错误码信息被平均掉了。所以我用正则识别堆栈起点（认
  Traceback、XxxError:、at file:line 三种模式），把堆栈单独切出来，标题单独
  成块，剩余正文按 500 字符、重叠 80 递归切，小于 30 字符的碎片丢弃。
- **追问链**：① "正则漏了怎么办？"→ Rust/Go panic 确实认不出，降级进 body
  chunk，不丢数据只丢"单独成块"的加成，这是已知限制；② "500/80 怎么定的？"→
  经验值：约一个段落+16% 重叠，坦白没做网格搜索，评估闭环建好后这是可调点；
  ③ "检索时 chunk 怎么回到 issue？"→ 先多召一倍 chunk（60 个），按
  issue_id 聚合取最高分 chunk 当代表，避免同一 issue 占多个名额。
- **翻车提示**：说"我用了语义切分/智能切分"然后被发现是 RecursiveCharacter
  按分隔符递归切——术语拔高必翻。

**Q2：清洗具体做了什么？为什么过滤 invalid/wontfix？**
- **口语答案**：三步：BeautifulSoup 去 HTML 标签，解码 HTML 实体，压缩空白；
  过滤只有一类——closed 且 resolution 是 invalid 或 wontfix 的，因为这批是
  "被官方判定为无效"的历史，检索出来当证据会误导判定。10.6 万条里实际只过滤
  了 58 条。字段层面还有个 normalize 步骤在 clean 之前，把不同来源的字段名
  （body/description/content）统一掉——我的评估链路曾经漏了这步，是踩过的坑。
- **追问链**：① "为什么不过滤空正文/超短 issue？"→ 当时没做，标题 chunk 保证
  它们至少可被标题命中；② "HTML 清洗多慢？"→ 10.6 万条约两三分钟，是离线
  资产构建的主要耗时，所以我把 docstore 和评测集构建合并成一次清洗两份产出。
- **翻车提示**："15 万条"这个数要改口——本地快照实际 106,714 条、8 个项目。
  被追问"哪 8 个项目"答不出至少要能说出 Firefox/Cassandra。

**Q3：为什么 BM25 用整条 issue、向量用 chunk？（粒度不对称）**
- **口语答案**：BM25 是词频统计模型，文档越完整统计越准，切碎会破坏 TF 和
  文档长度归一化，还得处理同一 issue 的切片互相抢排名；向量正相反，长文压进
  一个定长向量必然糊。各用最优粒度，融合层统一折算回 issue 排名。
- **翻车提示**：两边说反了就是灾难，先记住口诀："统计要完整，语义要切碎"。

**Q4：embedding 模型是什么？维度多少？（⚠️ 高危题）**
- **口语答案**（v2 口径，推荐）：英文数据集，我用 sentence-transformers 的
  all-MiniLM-L6-v2，384 维，本地 CPU 跑，归一化后走余弦。早期版本用过
  bge-small-zh——那是个选型失误，中文模型嵌英文数据，后来意识到后换成英文
  模型并重建了索引，这也是我讲"数据驱动纠错"时的真实案例。Reranker 一直是
  BGE 家族的 bge-reranker-base。
- **追问链**：① "为什么不用更大的？"→ 10 万条建库在 CPU 上跑，384 维存储和
  延迟都减半，召回层精度缺口由 Cross-Encoder 补；② "换模型要多久？"→ 全量
  重建数小时，v3 计划和 created_at 元数据重建合并成一次；③ "MiniLM 的弱点？"
  → 长文本和代码 token 表征弱，这是 recall@30 只有 0.48 的原因之一。
- **翻车提示**：**简历写"BGE 向量化"但答 384 维（MiniLM 的维度）= 当场自相
  矛盾**。二选一：简历改成"Sentence-Transformers 向量化 + BGE-Reranker 精排"
  （全真），或坚持 BGE 就换回 bge-small-en 重建索引。不要抱着"BGE"说 384。

**Q5：ChromaDB 为什么？生产环境还会用它吗？**
- **口语答案**：单机开发它最省事：本地持久化、带 metadata 过滤、和
  LangChain 生态贴合。生产到千万级会换 Milvus 或 pgvector——分片、副本、
  增量写入都是 Chroma 单机形态给不了的。我的检索器接口是抽象的，换库改
  实现层就行。
- **翻车提示**：说"ChromaDB 能扛亿级"会崩；反过来把它贬得一无是处也不必——

必须答得上：三 chunk 动机、粒度不对称、embedding 到底是什么模型几维。

## Bullet 4：低置信度反思重写

### 【简历原文】
> 设计低置信度条件边：置信度 < 0.7 时携带上一轮决策与检索诊断反思重写
> query，最多重试 2 次，提升歧义输入下的召回鲁棒性。

### 【面试官会怎么问】

**Q1（必被问）：重试时模型到底看到什么？**
- **口语答案**：三类信息。一是上轮的输出：改写 query、关键词、判断、置信度、
  理由；二是检索诊断——这些是 Python 算的客观数字：融合后候选数、精排候选数、
  缺正文证据的候选数、最高精排分、前两名分差；三是 v2 加的：上轮 Top-3 候选
  的 id 和标题。prompt 里还有两条反偏见指令：不要把低置信度直接归因为召回不
  准，不要把上轮 reasoning 当事实。诊断的用法举例：候选很多但前两名分差极小，
  说明区分度不够，该补充能区分候选的错误码；一条候选都没有，该放宽 query。
- **追问链**：① "为什么要给 Top-3 候选？"→ 只有数字诊断时模型不知道"检索回
  了什么"，无法判断该换方向还是加细节——这是 v1 到 v2 的真实迭代；② "重试
  会不会越写越偏？"→ 原文永远保留在 prompt 最前面，改写只是补充视角，且最多
  2 次硬上限；③ "重试有效吗？数据呢？"→ 🟡 诚实：我写了专门的对照 benchmark
  （legacy prompt vs 诊断 prompt），但它要求人工 verified 的案例数据，还没
  标注，所以目前只有机制没有效果数字。
- **翻车提示**：把"重试"吹成"自我反思的 Agent 能力"然后拿不出效果数据——
  主动降格为"带上下文的受控重写 + 待验证"反而稳。

**Q2：0.7 和 2 次怎么定的？**
- **口语答案**：0.7 对齐判定 prompt 里的置信度分档语义——0.7 以上定义为
  "核心症状一致"，低于它说明判断本身承认没把握；2 次是成本封顶，最坏 3 整轮，
  延迟和 LLM 费用都乘 3。两个都是设计值不是调优值，校准置信度、用数据重选
  阈值在我的 v3 计划里（先要有三分类标注集）。
- **翻车提示**：编造"0.7 是调出来的"会被"用什么验证集调的"一击毙命。

**Q3：重试整轮重跑不浪费吗？**
- **口语答案**：会浪费，这是当前图结构的代价——回到 Query Analysis 后检索
  精排全部重来，即使新旧 query 差别很小。我想过的优化是：新旧 query 相似度
  高就跳过重检索只重跑判定，或者检索结果无变化就短路终止。没做是因为它是
  最坏路径优化，先把评估闭环建好才知道值不值。
- **翻车提示**：不承认浪费、硬说"整轮重跑是特性"会显得没思考过。

**Q4：什么情况下重试也救不回来？**
- **口语答案**：三类：答案根本不在索引里（我评测集清洗时发现 34% 的标注目标
  不可达，线上对应"老 issue 被删/在别的仓库"）；输入信息量太少（"it crashed"
  再怎么改写也没有信号）；以及判定层的系统性偏差（比如 prompt 对 similar 的
  定义模糊）。第一类要靠数据治理，第二类应该直接低置信输出让人介入而不是
  烧三轮 API，第三类靠标注集+prompt 迭代。
- **追问链**：会顺到"怎么发现 34% 的"→ 这是我最好的故事，见通用问题 Q2。

### 【可信度自查】
必须答得上：Q1 的三类信息（背下来）、Q2 的"设计值非调优值"。这条 bullet
整体可信度高（机制真实存在且有代码细节），放心保留；但"提升鲁棒性"这半句
目前没有数字支撑，建议改成"用于歧义输入的受控重写机制"或补跑 benchmark。

### 【表述边界】
- ✅ 条件边、诊断字段、反偏见指令、2 次上限——两版都有。
- ✅ 上轮 Top-3 候选进重试 prompt——仅 v2。
- 🟡 "提升召回鲁棒性"——机制在、效果未量化；说成"实测提升 X%"就是编造。

- **选项 A（推荐）**：补跑 v2 的 hybrid / hybrid_rerank 评估（命令已就绪：

- **选项 B**：整条删除，评测能力并入 Bullet 4 或单写"构建含可达性过滤与
  duplicate-family 隔离划分的评测体系"。

### 【面试官会怎么问】（按你已改写为选项 A 后准备）

**Q1（必被问）：测试集怎么构建的？**
- **口语答案**：用数据集自带的 duplicate_of 标注当 ground truth，但直接用有
  三个坑，我都踩过并修了。一是可达性：13,104 条标注 query 里 34% 的目标 issue
  根本不在索引里——被清洗过滤了或数据集本身缺——这种题无解，必须剔除，剩
  8,599 条有效；二是自命中：评测 query 自己在索引里，第一名永远是自己，检索
  时多取一条剔除自身 id；三是泄漏：随机划分会把同一个重复家族拆进调参集和
  测试集两侧，我用并查集把 query 和标注目标连成 3,333 个家族，以家族为单位做
  80/20，同族绝不跨侧。
- **追问链**：① "怎么发现 34% 的？"→ recall 反常难看，停止调参去人工抽查
  未命中 case，发现目标 id 不在索引——教训是先验证尺子再调参；② "并查集为

  统计随文件落盘可复现。
- **翻车提示**：这题答好是全场最大加分项；但前提是简历数字先换成真的。

**Q2：指标为什么选 Recall@K / MRR / nDCG？**
- **口语答案**：Recall@30 是召回层硬底线——精排的候选池就这么大，召回丢了

  质量。nDCG 我还修过一个实现 bug：理想 DCG 要按全部相关目标数算，我第一版
  按"已检索到的命中"重排来算，等于命中 1 条就满分，数值虚高——修完才知道
  之前的数不可信。
- **追问链**：① "Rerank 后为什么不算 recall@30？"→ 精排输出最多 10 条，和

- **翻车提示**：能主动讲出"自己修过 nDCG bug"是深度信号；假装一直算对反而

**Q3：消融怎么做的？**
- **口语答案**（如实版）：目前完成的是分路对照：vector_only 和 bm25_only 在

  支持、正在补跑。设计好的五组开关消融——docstore、keywords 进 BM25、双路
  召回、零分过滤、动态截断——每组看对应的靶点指标，比如 docstore 看的是
  rerank 后 recall@5，因为它的机制是让 BM25-only 候选能被精排排上来。
- **翻车提示**：把"设计了消融"说成"跑完了消融"，被要第三组数字时就崩。边界

## 通用问题

**Q1：为什么做这个项目？**
- **口语**：想做一个"检索质量可以被严格度量"的 RAG 场景。issue 查重的好处是
  数据集自带 duplicate_of 标注，不像问答类 RAG 连 ground truth 都要自己造；
  而且它有真实痛点——大项目每天新 issue 里高比例是重复的，人工在十几万历史
  里找，一条几分钟。
- **追问链**：真实用户是谁→开源项目维护者/企业内部工单团队；为什么不直接用
  GitHub 自带搜索→关键词搜索换个说法就漏，也不给判定和理由。

**Q2：项目里最大的难点/最深的坑？**
- **口语**：不是搭链路，是让评估可信。我搭完链路后指标一直难看，调参没起色，
  最后发现是评测集本身的问题——34% 的 query 的标准答案根本不在索引里，另外
  还有自命中污染和家族泄漏。停下来重建评测体系（可达性过滤+剔自命中+并查集
  家族划分），之前的指标全部作废重测。这件事给我的铁律是：优化之前先验证
  尺子。
- **翻车提示**：这故事的数字（34%、13104→8599、3333 家族）要背熟，含糊了
  故事就不可信。

**Q3：这个方案最大的缺点？**
- **口语**：三个真实的。一是判定质量未度量：三分类没有人工标注测试集，说不出
  端到端准确率——这是 v3 第一优先级。二是置信度未校准：0.8 不等于 80% 对，
  重试阈值 0.7 也是设计值不是调优值。三是时间穿越：评测和线上都在检索全量
  索引，包含比 query 更晚的 issue，真实场景只能查历史，所以当前指标偏乐观，
  修复要把 created_at 加进元数据重建索引。
- **翻车提示**：只会说"数据量不够大"这种万能缺点=没有自省；说代码层面的
  具体缺陷才可信。

**Q4：数据量翻 100 倍怎么办？**
- **口语**：三个瓶颈按顺序爆。最先是 BM25：rank-bm25 纯 Python 全库打分，
  现在 10 万条 p50 就 2.9 秒、p95 49 秒，千万条直接不可用——换 Elasticsearch
  或 Tantivy，倒排跳表把延迟拉回几十毫秒。第二是 Chroma 单机内存——换
  Milvus/pgvector 分片或 IVF-PQ 量化。第三是建库时长——GPU 批处理+增量索引。
  四节点流程和检索器接口不用动。
- **追问链**：QPS 高了呢→检索线程池隔离+缓存层（同 issue 重复提交直接命中）；
  成本呢→judge/decision 换更小模型+上下文预算器控 token。

**Q5：如何评估？召回上不去怎么排查？**
- **口语**（排查顺序）：先查数据——ground truth 在不在索引里（34% 的教训）；
  再分路诊断——vector_only 和 bm25_only 单独跑，某路单独能中而融合丢了是
  融合层问题，两路都不中查 query——拿原文直接搜对比，定位改写漂移；再查
  切分——关键信息是否被 chunk 边界切断；最后才换模型。
- **翻车提示**：一上来就答"换个 embedding 模型"= 没有工程排查思维。

**Q6：线上延迟高怎么优化？**
- **口语**：先看画像再动手。我的实测：向量 22ms 不是瓶颈；BM25 2.9s 是第一
  瓶颈，换引擎收益最大；Rerank CPU 上一到三秒，可以 ONNX 量化或 GPU；LLM 两
  次调用走网络，可以流式返回先给候选列表。已经做的免费优化：模型和图进程内
  只加载一次、两路 query 相同自动去重。
- **翻车提示**：不带数字的延迟优化都是背书；报自己的 P50/P95 才是做过的证据。
