# 03 消融矩阵：逐组件量化贡献

> 消融（ablation）：控制其余变量、只开关一个组件，用指标差量化该组件的贡献。
> **本文件最重要的一组是"粒度对称 vs 不对称"——它是简历核心设计点
> （BM25 走 issue 粒度、向量走 chunk 粒度），目前没有任何数据支撑。**
> 全部消融在检索层进行（确定性，每组跑 1 次），共享同一评测集（test set
> 抽样 200 条，seed=42，自命中剔除）、同一 Chroma 索引、同一套依赖版本。

## 1. 主消融链（四步递进）

每一步只比上一步多一个组件；四步用同一批 query 同一评测集。

### 步骤 ① 向量基线（vector_only）

- **配置**：只用 VectorRetriever（chunk 召回×2 → issue 聚合 → Top-30）。
- **控制变量**：无（它是原点）。已有实测：recall@30=0.4835，recall@10=0.3965，
  MRR=0.2709（200 条抽样）。
- **作用**：一切增量的分母。

### 步骤 ② + BM25（**对称粒度**：chunk 级）+ RRF

- **配置**：新建一个 **chunk 粒度的 BM25 索引**——语料不是"title+body 整条"，
  而是与 Chroma 完全相同的 chunk 集合（复用 `chunk_issue` 的输出，逐 chunk
  分词建 BM25Okapi）；查询后按 issue_id 聚合（同一 issue 取最高分 chunk，
  与向量路聚合规则一致），再与向量路做 RRF。
- **为什么必须有这一步**：如果直接从"纯向量"跳到"现有混合检索"，涨的点数是
  "加了 BM25"和"BM25 用了 issue 粒度"两件事的混合贡献，**拆不开**。对称粒度
  这一步把"加一路关键词检索"的贡献单独量出来。
- **新建索引的实现规格**（无 HNSW 随机，确定性构建）：

```text
输入：与建 Chroma 相同的 clean issues → chunk_issue() 输出的全部 chunk
语料：tokenize(chunk.page_content)，记录 (chunk_idx -> issue_id) 映射
检索：get_scores → chunk 排名 → 按 issue_id 取每 issue 最高分 → issue 排序 Top-30
持久化：bm25_chunk.pkl（与 bm25.pkl 并存，评测专用，不进在线链路）
```

- **控制变量**：RRF_K=60、两路 Top-30、聚合规则与向量路一致；不引入
  keywords/0 分过滤（这两个是 v2 的独立改进，放诊断组测）。
- **预期**：recall@30 相对 ① 上涨（BM25 捞回错误码强匹配、纯向量漏掉的
  候选）。
- **如果不符**：不涨甚至跌 → a) RRF 配额被 BM25 的低质量 chunk 命中挤占
  （查分层：高词面重合桶应该涨，若连它都不涨则 BM25 路本身有问题）；
  b) chunk 粒度 BM25 天生弱（正好为步骤 ③ 提供动机）。

### 步骤 ③ + 粒度不对称（BM25 换 issue 粒度）★ 简历核心设计点

- **配置**：其余与 ② 完全相同，仅把 BM25 从 chunk 索引换成现有的 issue 粒度
  索引（bm25.pkl）。
- **控制变量**：只动 BM25 的语料粒度这一个变量——RRF、Top-K、向量路、聚合
  规则全部不变。
- **预期**：③ 相对 ② 上涨，理由（待验证的假设）：issue 粒度下 TF/文档长度
  归一化的统计意义完整，且 title+body 的词共现证据不被切散；chunk 粒度下
  同一 issue 的多个 chunk 会稀释彼此的词频统计并互相竞争排名。
- **如果结果不符**：
  - ③ ≈ ②：粒度不对称的贡献可忽略——**简历上就不能把它当核心设计点讲**，
    应降格为"工程选择"（省一次聚合）；这正是要测的原因。
  - ③ < ②：chunk 粒度反而好（可能因为长 issue 的无关段落在 issue 粒度里
    拉低了 BM25 的长度归一化得分）——设计结论反转，诚实更新文档与简历。
  - 分层解读：粒度差异预期在**长 issue 桶**最明显（长文档才有"切与不切"的
    区别）；短 issue 桶两者应接近——若短桶差异反而大，说明另有原因（如
    title 权重在两种语料里的占比不同），需要进一步单独消融"BM25 语料是否
    含 title"。
- **报告格式**：② vs ③ 的 recall@5/10/30、MRR、nDCG@10 全量 + 按长度分桶，
  差量带绝对值和相对值。

### 步骤 ④ + Cross-Encoder 精排

- **配置**：在 ③ 之上加 bge-reranker-base 精排（Top-30 → Top-5，动态扩展
  开启，与线上一致）；指标只在 @5/@10 计算（公平截断）。
- **控制变量**：精排输入 = ③ 的输出，逐条深拷贝（防 v1 式原地污染）。
- **预期**：recall@5、MRR、nDCG@10 相对 ③ 的"直接取 RRF Top-5/10"显著上涨
  （RRF 分是名次共识不是相关性，精排应该把真答案往前提）。
- **如果不符**：精排不涨 → a) 候选正文证据不足（对照 A2-4，检查空证据率；
  这正是 docstore 的价值点，可加"④ 无 docstore"对照）；b) 800 字符截断把
  证据截没了（长 issue 桶单独看）；c) reranker 与领域不匹配（换模型的依据）。

## 2. 诊断性消融组

| 组 | 开关 | 怎么测 | 能诊断什么 |
| --- | --- | --- | --- |
| D1 关掉反思重写 | MAX_RETRIES=0（等效：should_retry 恒返回 end） | 端到端（含 LLM，重复 n=3）：三分类准确率、related 命中率、平均延迟与成本 | 重写的净价值：准确率差量 vs 成本增量（最坏 3 倍）。若差量≈0，重写机制应降级或收紧触发条件——这也是 retry_quality benchmark 的问题，本组给它全局视角 |
| D2 关掉上下文裁剪 | DECISION_BODY_PREVIEW_CHARS: 400 → 4000（近似"不裁"）；对照组再加 200（v1 值） | 端到端（重复 n=3）+ token 成本 | 证据长度对判定质量的边际收益曲线：200 vs 400 vs 4000 三点。若 4000 不比 400 好，说明证据瓶颈不在长度而在"截断的是不是相关段"（支持"最相关 chunk 拼接"方案） |
| D3 RRF_K 扫描 | K ∈ {20, 60, 120} | 检索层跑一次/点 | K 的敏感性：若 20/60/120 差异<1pp，说明"K=60 经验值"够用不必调；若敏感，说明两路排名质量不均衡（弱路在小 K 下被压制），提示先修弱路而不是调 K |
| D4 Top-K 扫描 | HYBRID_TOP_K ∈ {10, 30, 60}（精排输入随之变） | 检索层 recall@K 曲线 + 精排后 recall@5 + 精排延迟 | 候选池大小的收益/成本拐点：30→60 若 recall@30 内已平台化则维持 30；10 若明显掉说明召回层确实需要宽口径 |
| D5 关 docstore（仅 v2） | HybridRetriever 传 docstore=None | 精排后 recall@5/@10（检索层，跑一次） | docstore 的独立贡献：BM25-only 候选能否被精排排上来。机制上它只影响精排输入，所以看精排后指标而非召回指标 |
| D6 关 keywords 进 BM25（仅 v2） | retrieval 节点不传 bm25_extra_terms | bm25_only 与 hybrid 的 recall/MRR | keywords 加权的独立贡献；若为负（keywords 噪声反而带偏），说明 Query Analysis 的 keywords 质量不行，该修上游 |
| D7 关 0 分过滤（仅 v2） | BM25_MIN_SCORE 检查移除 | hybrid recall@30 | 预期无差或正差（0 分候选本来不该占配额）；若关掉反而涨，说明 RRF 配额逻辑有意外交互，需排查 |
| D8 关双路 query | search_queries 只传 rewritten_query | 检索层（固定改写 fixture，跑一次）rescue/regression 率 | 原文兜底路的净价值——dual_query benchmark 的全集版 |

## 3. 执行矩阵与命名

| 变体名（入库用） | 基于 | 改动 |
| --- | --- | --- |
| `v_only` | — | 步骤 ① |
| `hyb_sym` | v_only | + chunk 粒度 BM25 + RRF（步骤 ②） |
| `hyb_asym` | hyb_sym | BM25 换 issue 粒度（步骤 ③）＝现有 hybrid |
| `hyb_asym_rr` | hyb_asym | + Cross-Encoder（步骤 ④）＝现有 hybrid_rerank |
| `d1_noretry` … `d8_singleq` | 线上默认配置 | 对应诊断开关 |

规则：每个变体一行结果记录（字段见 05 文档）；主链四步必须同一天同一环境
连续跑完（消除环境漂移）；诊断组按需跑。

## 4. v1 / v2 口径

- 主消融链在 **v2** 上跑（v2 才有 docstore/校验，且资产齐）。
- v1 的意义是"改进前后对照"：用同一评测集跑 v1 的 `hyb_asym` 与
  `hyb_asym_rr` 等价配置（v1 代码 + 共享资产 + 每配置深拷贝候选），与 v2
  同名变体对比——差值就是"docstore + 0 分过滤 + keywords"等 v2 检索层改进
  的总贡献（再用 D5/D6/D7 拆单项）。
- ⚠️ 待确认：v1 若用其 GitHub 原配置（bge-small-zh + chroma_db），向量路
  与 v2 不可比；对照必须统一为 chroma_db_en 资产（见 01 文档第 4 节）。
