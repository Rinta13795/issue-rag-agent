# 06 评测专题面试问答（10 问）

> 口语答案 + 追问链。数字均来自真实实测（v2，200 条抽样，自命中已剔除）；
> 标 🟡 的是"设计已完成、数据待跑"，说的时候要用"我的方案是"句式。

## Q1 测试集怎么构造的？Ground Truth 哪来的？

- **口语**：GitBugs 数据集自带标注——被维护者处理成 duplicate 的 issue 有个
  duplicate_of 字段指向它重复的目标，这就是天然的标准答案。但直接用有三个坑
  我都踩过：一是 34% 的标注目标根本不在索引里（被清洗过滤或数据集缺失），
  这种题无解必须剔除，13,104 条清完剩 8,599 条；二是评测 query 自己在索引里
  会自命中，检索时多取一条剔掉自身；三是随机划分会把同一个重复家族拆到调参
  集和测试集两侧，我用并查集把 query 和答案连成 3,333 个家族，按家族整体做
  80/20。
- **追问链**：① "34% 怎么发现的？"→ recall 反常低、调参无效，停下来人工抽查
  未命中案例，发现目标 id 不在索引——教训是先验证尺子；② "并查集为什么必要？"
  → a 重复 b、b 重复 c 要传递合并，不然 a、c 仍会分居两侧泄漏；③ "负样本呢？"
  → 检索层不需要（每条 query 有确定答案集）；端到端三分类需要，从未标 duplicate
  的 issue 里抽并人工复核——因为"没标"不等于"真不重复"。

## Q2 为什么要分层评测？

- **口语**：平均数会说谎。我按三个维度分桶：词面相似度高低——高重合是 BM25
  主场、低重合是向量主场，混在一起两路的短板互相掩盖；按仓库——Firefox 和
  Cassandra 的 issue 文风完全不同，某个仓库差往往是我的堆栈正则不认它的格式；
  按长度——长文本考验切分和截断，短文本考验精确词匹配。每个桶指向不同的修复
  动作，这才叫诊断而不只是打分。
- **追问链**：① "举个分层发现问题的例子？"→ 🟡 预期例：长 issue 桶精排不涨
  说明 800 字符截断丢证据；② "桶太小怎么办？"→ 样本量随表展示，小于 30 条的
  桶只参考不下结论；③ "词面相似度用什么算？"→ token Jaccard，简单够用，它
  本身不是被测对象。

## Q3 哪些测试要重复跑、哪些不用？为什么？

- **口语**：我先做了一张随机性盘点表。BM25 打分、RRF、精排、向量查询在"固定
  索引+同机+锁版本"下全是确定性的——排序都是稳定排序，同分并列顺序也唯一——
  所以检索层指标跑一次就行，我还留了一条"同 query 跑两遍比对序列"的断言守住
  这个前提。三个 LLM 节点是随机源，而且我的结构会放大它：置信度在 0.7 阈值
  附近抖一下，整条链路就多跑或少跑一轮。所以端到端指标重复三次，报均值加
  标准差，差量超过两倍标准差才算信号。
- **追问链**：① "索引也确定吗？"→ 查询确定，**构建**不确定——HNSW 建图抽
  随机层数，重建索引等于换基线，所以对照实验必须共享同一份索引文件；② "为
  什么是 3 次不是 30 次？"→ 成本权衡，3 次能给出标准差的量级估计，发现不显著
  再加大；③ "温度设多少？"→ 评测统一 0，线上 0.1，两个口径都记元数据。

## Q4 temperature=0 不就确定了吗？

- **口语**：不能。四个原因：服务端动态批处理让浮点求和顺序变化，两个 token
  概率接近时 argmax 会翻转并逐 token 级联；deepseek-chat 是 MoE 架构，路由对
  数值扰动敏感；同一个模型名背后服务商可能更新权重，API 锁不了版本；而且我
  的系统里这点微小差异会被条件边放大成"是否多跑一整轮"。所以 t=0 只是压方差，
  LLM 相关数字永远报统计量不报单次。
- **追问链**："那你怎么复盘单个 badcase？"→ 每次调用的原始响应落盘，解析层
  可以离线重放，不用再调 API。

## Q5 你怎么定义幻觉、怎么测？

- **口语**：这个场景里幻觉有明确定义：输出的 related_issues 里出现了本轮
  检索候选集之外的 issue id——模型凭空编了个编号。测法是断言不是指标：对每条
  输出检查 related_issues 是否为本轮精排候选 id 集合的子集，要求 100% 通过。
  v2 我在代码里加了白名单校验层，所以断言在 v2 上是"验证防线没失效"；在 v1
  上跑同一断言，违例率本身就是 v1 的幻觉率——这个对照能把"我修了幻觉问题"
  变成一个可测的数字。
- **追问链**：① "判断错误算幻觉吗？"→ 不算，我把"编造不存在的引用"（结构
  幻觉，可规则判）和"判断错误"（语义错误，要标注集测准确率）严格分开；
  ② "reasoning 里的幻觉呢？"→ 规则测不了，方案是 LLM-as-a-Judge 抽查
  reasoning 是否引用了真实候选特征，裁判结果再抽样人工复核。

## Q6 你的数字可信吗？版本之间怎么保证可比？

- **口语**：每次运行落一行完整元数据：代码 commit、配置 hash（含三个 prompt
  文件内容）、数据快照 hash、索引文件 hash、评测集 hash、种子、依赖版本。
  可比性规则是硬的：数据、索引、评测集、种子四个 hash 全一致才允许直接比，
  不一致的对比必须声明差异项。抽样也固定种子，200 条永远是同样的 200 条。
  另外报告开头强制展示样本量和抽样方式，防止把抽样数当全量说。
- **追问链**：① "改了 prompt 怎么比？"→ prompt 内容进配置 hash，改了 hash 就
  变，这正是被测变量，其他 hash 不动；② "换机器呢？"→ 浮点行为可能变，CI 和
  本地数字分池存放不混合出报告。

## Q7 粒度不对称的贡献怎么单独测出来的？

- **口语**：这是我消融链里专门设计的一步。我的设计是 BM25 用整条 issue 建
  索引、向量用 chunk——但如果只比"纯向量"和"最终混合"，加 BM25 和 BM25 用
  什么粒度两件事的贡献混在一起拆不开。所以我插了一个中间变体：专门建一份
  chunk 粒度的 BM25 索引，语料就是和向量库完全相同的那批 chunk，检索后同样
  按 issue 聚合。这样四步链就是：纯向量 → 加对称粒度 BM25 → 换不对称粒度 →
  加精排，第三步减第二步的差量就是粒度不对称的净贡献。预期它在长 issue 桶
  差异最大，因为长文档才有"切不切"的区别。
- **追问链**：① "如果测出来没差呢？"→ 那就诚实降格：它从'核心设计点'变成
  '省一次聚合的工程选择'，简历相应改写——这正是我做这组消融的原因，🟡 目前
  这个数字还没跑出来，我不会在跑出来之前把它当成果讲；② "chunk BM25 会不会
  天生吃亏？"→ 聚合规则和向量路完全一致（每 issue 取最高分 chunk），控制变量
  只有语料粒度这一个。

## Q8 改了 prompt 之后怎么知道变好还是变坏？

- **口语**：三层防线。第一层断言：结构契约（枚举、白名单、字段完整）必须
  100% 过，改坏了直接红；第二层冒烟回归：固定 50 条评测集跑一遍，和存好的
  基线出差量表，检索层看排名指标、端到端看三分类和重试率；第三层显著性：
  端到端差量要超过基线标准差的两倍才算信号，不然标记为噪声，要么加大重复
  次数要么放大样本。另外 prompt 内容在配置 hash 里，每个数字都能追溯到具体
  哪一版 prompt。
- **追问链**："fallback 率有什么用？"→ 它是解析层的健康度：prompt 改动导致
  模型输出格式变差时，指标可能还没掉，fallback 率先升——是个前置报警器。

## Q9 Recall 和 Precision 在你的场景哪个更重要？

- **口语**：分层看。召回层只看 Recall@30——它是全链路上限，丢了就全丢，
  precision 在这层不重要因为后面有精排兜。精排层看 Recall@5 和 MRR——决定
  LLM 和人看到的头部质量。Precision@5 我也报但要带背景解读：大多数 query
  只有一个标准答案，precision@5 的理论上限就是 0.2，我实测 0.074 看着难看，
  换算成"三条 query 里两条的 Top-5 含答案"更接近真实含义。端到端最贵的错误
  是两类：真 duplicate 判成 new（白费人工）、误报 duplicate（可能误关 issue），
  混淆矩阵里单列。
- **追问链**："为什么精排后不算 recall@30？"→ 精排输出最多 10 条，跟返回 30
  条的配置比 @30 不公平，只在 @5/@10 比。

## Q10 这套评测方案的最大局限是什么？

- **口语**：三个。一是标注天花板：ground truth 只覆盖 duplicate 正例，similar
  的边界必须人工标，我首期只计划 30-50 条，这个类别的指标置信度有限。二是
  时间穿越：评测检索的是全量索引，包含比 query 晚创建的 issue，真实上线只能
  查历史，所以当前数字偏乐观——修复要把 created_at 加进索引元数据重建。三是
  标注噪声：duplicate_of 本身是维护者手工标的，有漏标（负样本可能是假负），
  我用人工复核负样本缓解但没法根除。我把这三条都写在报告的免责段里，数字
  从来和它的边界一起交付。
- **追问链**："既然有这么多局限，这套评测还有什么意义？"→ 评测的意义不是
  绝对真值而是**可比性**：同一把有已知偏差的尺子，量得出改动的方向和量级——
  34% 的教训恰恰说明，没有这把尺子时连方向都是错觉。

### N1 「你这个数字可信吗？」→ 评测集三处失效修正

- **触发场景**：报完任何指标后被追问"怎么测的/数字可信吗"；或介绍评测集时
  主动抛出（强烈建议主动讲——它是全场含金量最高的内容，等着被问太可惜）。
- **口语答案**：可信，因为这套评测集我修过三处失效。第一处是可达性：原始
  13,104 条 duplicate 标注里，34% 的目标 issue 根本不在索引里——被清洗过滤
  或数据集本身缺——这种题无解，留着只会系统性压低所有指标，我用索引 id 全集
  逐条校验剔掉，剩 8,599 条有效。第二处是自命中：评测 query 自己就在索引里，
  第一名永远是自己，我检索时多取一条把自身剔掉。第三处是划分泄漏：随机切
  80/20 会把同一个重复家族拆到两侧，调参集见过 A 重复 B、测试集又考 B 重复
  A，我用并查集把 query 和答案连成 3,333 个家族，按家族整体划分，同族绝不
  跨侧。修完这三处，数字才有资格叫基线。
- **追问链**：
  ① "34% 是怎么发现的？"→ recall 反常低、怎么调参都没起色，停下来人工抽查
  未命中案例，发现目标 id 压根不在索引——教训：优化前先验证尺子。
  ② "并查集为什么必要，直接按 query 对划分不行吗？"→ 重复关系是传递的，
  a→b、b→c 时 a 和 c 必须同侧，成对处理漏传递闭包，并查集一次解决。
  ③ "修完之后指标是升了还是降了？"→ 升了——剔除无解题等于把分母里的必错项
  拿掉；所以新旧口径的数字不可混比，我所有报告都带评测集版本 hash。
- **翻车提示**：三个数字（34%、13104→8599、3333 家族）说含糊，整个故事的
  可信度就塌了——背熟。另外别说成"我清洗了数据"（那是另一码事），这是
  **评测集**修正。

### N2 「为什么简历只列 Recall@10 和 nDCG@10 两个指标？」

- **触发场景**：面试官看着简历问"就这两个指标？Precision 呢？"
- **口语答案**：体系里有四个——Recall@K、Precision@5、MRR、nDCG@10，简历
  只列两个是因为四个指标高度相关，罗列数字不如讲清诊断分工。Recall@10 是
  候选层硬底线：答案在不在前十；nDCG@10 是排序质量：答案排得多靠前、多答案
  时排得多整齐——一个管"有没有"，一个管"排得好不好"，正交且互补。MRR 和
  nDCG 高度同向（都对头部敏感），列一个够了；Precision@5 在我的场景有个
  解读陷阱：大多数 query 只有一个标准答案，P@5 理论上限就是 0.2，绝对值
  看着难看，不带背景直接放简历反而引误解，所以留在报告里配注释。
- **追问链**：
  ① "Recall 高但 MRR 低说明什么？"→ 答案能进候选池但排不到前面——召回层
  没问题，瓶颈在排序，该加强精排而不是换 embedding；反过来 MRR 高 Recall
  低说明命中的都排得好但漏得多，该扩召回。
  ② "P@5 上限 0.2 怎么算的？"→ 单答案 query 在 Top-5 里最多命中 1 条，
  1/5=0.2；我实测 0.074，换算成"约三分之一强的 query 前五含答案"更接近直觉。
  ③ "nDCG 和 MRR 什么时候会背离？"→ 多答案场景：MRR 只看第一个命中，nDCG
  看全部命中的位置分布——family 大的 query 上 nDCG 更能反映整体质量。
- **翻车提示**：答"因为这两个数字最好看"必崩；正确的姿势是"指标是诊断工具
  不是装饰，每个都能说出它诊断什么"。

### N3 「粒度不对称的贡献怎么单独测出来的？」

- **触发场景**：简历里"+粒度不对称单独贡献 +X pp"被看到后的必然追问。
- **口语答案**：靠一个专门构造的中间变体。我的设计是 BM25 用整条 issue 建
  索引、向量用 chunk——但如果只比"纯向量"和"最终混合"，"加了 BM25"和
  "BM25 用什么粒度"两件事的贡献混在一起拆不开。所以我插了一步：专门建一份
  chunk 粒度的 BM25 索引，语料就是和向量库完全相同的那批 chunk，检索后同样
  按 issue 聚合、每 issue 取最高分 chunk，聚合规则和向量路一致——控制变量
  只剩语料粒度这一个。消融链变成四步：纯向量 → 加对称粒度 BM25 → 换不对称
  粒度 → 加精排，第三步减第二步就是粒度不对称的净贡献。
- **追问链**：
  ① "预期在哪类样本上差异最大？"→ 长 issue 桶——长文档才有"切不切"的区别，
  分层报告里单独看；短 issue 桶两者应接近，若反常需再查 title 在两种语料里
  的权重占比。
  ② "如果测出来没差呢？"→ 那它就从'核心设计点'降格为'省一次聚合的工程
  选择'，简历相应改写——我做这组消融就是为了让这句话有数据背书或者被数据
  否掉，两个结果我都接受。
  ③ "chunk 粒度 BM25 为什么可能吃亏？"→ TF 和文档长度归一化的统计意义被
  切散，同一 issue 的多个 chunk 还会互相竞争排名——这正是当初选不对称的
  理论依据，消融是去验证它。
- **翻车提示**：数字没跑出来之前被问到，**绝不现编数字**——说"消融设计
  完毕、chunk 索引这周构建、数字下周有"都比编一个 +5pp 安全一万倍。

### N4 「你的实验重复跑吗？怎么保证可比？」

- **触发场景**：报均值/对比数字时；或被问"你跑几次取的值"。
- **口语答案**：分两类。检索链路——BM25 打分、RRF、向量查询、Cross-Encoder
  ——在固定索引、同机、锁版本的前提下没有任何随机源：打分是纯算术，排序是
  稳定排序，同分并列由语料顺序唯一决定，所以单次评估就是最终值，我还留了条
  断言：同一 query 跑两遍比对 id 序列必须完全一致，守住这个前提。含 LLM 的
  环节相反：temperature 设 0 也压不掉服务端的浮点抖动和 MoE 路由，而且我的
  置信度阈值 0.7 会把微小抖动放大成"是否多跑一整轮"，所以端到端指标重复
  3 次报均值±标准差。可比性靠元数据：数据、索引、评测集、种子四个 hash 全
  一致才允许直接比。
- **追问链**：
  ① "索引不是确定的吗，为什么要锁 hash？"→ 查询确定，**构建**不确定——
  HNSW 建图给每个节点抽随机层数，重建索引等于换了一张图，同 query 的近邻
  集合会有边缘差异，所以重建即断代，跨批次数字只看趋势不做精细对比。
  ② "t=0 为什么还不确定？"→ 服务端动态批处理改变浮点求和顺序，两个 token
  概率接近时 argmax 翻转并逐 token 级联；MoE 路由对扰动敏感；模型名背后
  权重可能被更新。
  ③ "3 次够吗？"→ 给出标准差量级估计够了；差量小于两倍标准差就标记不显著，
  加大重复或样本量再下结论。
- **翻车提示**："我都跑了很多次取平均"——检索层跑多次是不懂随机性来源的
  信号，反而减分；正确答法是"确定性的跑一次并有断言守护，随机的重复三次"。

### N5 「nDCG 那个 bug 是怎么发现的？」

- **触发场景**：讲评测体系时主动讲，或被问"你说修过指标 bug，什么 bug"。
- **口语答案**：v1 版的 nDCG 里，理想 DCG 是从"已检索到的命中"重排出来算的
  ——问题在于：一条 query 有两个标准答案、我只召回了一个排第一，DCG 是
  1/log2(2)=1，而错误实现的 IDCG 也只有这一个命中，同样等于 1，nDCG 直接
  满分。也就是说只要命中至少一条，nDCG 恒等于把命中的重排到顶端的完美值，
  漏掉的答案根本不进分母——它退化成了 Recall 的另一种写法，失去了衡量排序
  的意义。正确算法是 IDCG 按 min(答案总数, K) 个理想命中算：刚才那个例子
  IDCG=1/log2(2)+1/log2(3)≈1.63，nDCG≈0.61 才是真实值。发现的过程是我给
  metrics 写单测时构造了"两答案命中一个"的用例，期望值和实现对不上，追进去
  发现理想序算错了。修完之后补了回归测试锁住。
- **追问链**：
  ① "这个 bug 对之前的数字影响多大？"→ 方向确定是虚高（多答案 query 全部
  被高估），幅度和多答案占比相关；所以修复前的 nDCG 一律作废不引用。
  ② "为什么说它退化成 Recall？"→ 命中≥1 即满分、命中 0 才 0 分——它只区分
  "中没中"，不区分"排多前"，这正是 Recall 的语义。
  ③ "怎么防止这类指标 bug？"→ 指标函数全部配已知期望值的手算用例（完美
  排序=1、无命中=0、部分命中=手算中间值），进回归测试。
- **翻车提示**：讲不清"为什么退化成 Recall"这一步，故事就只剩"我修了个
  bug"，含金量掉一半——把 1/log2(2) 那个两答案例子背熟，能白板手算。
