## 2. 选择标准（测试前写死，测完不改）

1. **质量第一**：第 12-14 轮的 3 项质量检查（错误码、试过的两个方法、只给 PowerShell 命令）在两遍运行中都全部通过，否则直接淘汰。
2. **跨轮缓存命中率第二**：每轮第一次模型调用的命中 token / 输入 token（按 token 加权，第 2-14 轮），两遍取平均。
3. **总花费第三**：含回答、压缩和记忆整理的全部调用，两遍取平均。
4. **实现复杂度**：只在前三项打平时用来决定（无额外模型调用 < 额外模型调用；状态字段越少越简单）。

"打平"的定义：命中率相差不到 5 个百分点、花费相差不到 10%，视为打平。

## 3. 候选方案

| 方案 | 策略 | 做法 | 额外模型调用 |
| --- | --- | --- | --- |
| A | `sliding` | 当前默认：每轮最近 10 条（含当前消息） | 无 |
| B | `stepped` | 只追加，窗口超过 20 条时一次性砍回最近 10 条 | 无 |
| C | `compact` | 只追加；未压缩历史超过 16 条时，把较早部分连同上一版摘要压成摘要（≤400 字，原样保留错误码、试过的方案、偏好），保留最近 6 条原文 | 每次压缩 1 次 |
| D | `case_summary` | 同 C 的阈值，但用当时的案例摘要替换旧历史并**冻结**，不额外调用模型；案例摘要为空时不压缩 | 无 |
| E | `full` | 只追加、不截断（参照组，受会话最多保存 80 条限制） | 无 |

E 是根据调研加的：Claude Code、Codex 都是"只追加 + 接近上限才压缩"，而这次测试的 14 轮远没到上限，E 代表"这个规模下根本不截断"的上界，用来衡量 B、C、D 截断造成的命中和质量损失。

## 4. 实现与测试脚本

- `src/chat/history.py`：五种策略的 `select_history`。默认 `sliding` 与改动前逐条一致（有单测）。
- `config.py`：`CHAT_HISTORY_STRATEGY="sliding"`、窗口 10、阶梯上限 20、压缩阈值 16、保留 6。
- `src/chat/models.py`：`ChatSession` 新增 3 个窗口状态字段，都有默认值，旧会话可直接读取。
- `src/chat/runtime.py`：用策略模块组装历史；`compact_history` 用 `planner` 客户端做压缩。
- `eval/benchmarks/history_window.py`：
  - 固定 14 轮对话（第 1、2、7 轮埋细节，第 12-14 轮考查），工具结果是固定假数据，回答最大输出 300 token。
  - 每个方案、每遍重复在独立子进程里并发运行；系统提示词、压缩提示词、记忆整理提示词最前面都加 `[scheme-X run-N]`，防止互相蹭缓存。
  - 去掉 `ask_user`（会走暂停恢复路径，绕过历史窗口）和 `draft_issue`，所有方案相同。
  - 模型客户端外面包了一层，只暴露非流式调用，逐次记录 DeepSeek 返回的 `prompt_cache_hit_tokens` 等原始字段；拿不到就记空值，不推算。
  - 记忆整理按生产方式开启，每轮结束等它完成，所以 D 用的是真实生成的案例摘要。
  - 运行前先用离线替身估算费用，超过 `--max-cny`（默认 5）就停。
- `tests/test_history_window.py`：5 个策略单测。

### 5.2 离线结构分析（替身模型，**不是**缓存实测）

每轮第一次调用的提示词，与上一轮第一次调用提示词的**字符级公共前缀占比**（第 2-14 轮）：

| 方案 | 第 2-14 轮逐轮公共前缀占比 |
| --- | --- |
| A sliding | 0.35 0.40 0.41 0.43 **0.34 0.35 0.34 0.35 0.34 0.35 0.34 0.35 0.35** |
| B stepped | 0.35 0.40 0.41 0.43 0.44 0.45 0.45 0.46 0.48 **0.34** 0.42 0.43 0.44 |
| C compact | 0.35 0.40 0.41 0.43 0.44 0.45 0.45 0.46 **0.34** 0.42 0.43 0.44 0.45 |
| D case_summary | 0.35 0.40 0.41 0.43 0.44 0.45 0.45 0.46 **0.34** 0.42 0.43 0.44 0.45 |
| E full | 0.35 0.40 0.41 0.43 0.44 0.45 0.45 0.46 0.48 0.48 0.49 0.50 0.51 |

能确认的只有机制：

- **A 从第 6 轮起，前缀每轮都断在系统提示词之后**（0.34-0.35 正好是系统提示词的占比），之后的历史一轮也接不上。你的怀疑在结构上成立。
- B、C、D 只在截断或压缩的那一轮断一次，之后前缀继续变长；E 一路增长。
- **一个新发现**：每轮都会变的"调查上下文"块（记忆、证据、源 Issue）放在历史之后，本身就跨轮无法命中。在替身数据下它约占提示词的一半；真实运行时证据更多，占比可能更大。所以**不管选哪个窗口方案，跨轮命中率都有上限**，窗口策略只能改善历史那一段。

替身回答很短，真实回答约 300 token，历史段会更长，只追加方案的优势应该更明显。但具体数值必须以实测为准。

## 6. 选择结论

**按写死的标准，现在无法选出胜者**：第一条标准（质量）和第二条（跨轮命中率）都依赖实测数据，而实测没有跑成。

实测前的预期（只是待验证的假设，不作为结论）：

- A 跨轮命中最低；质量取决于记忆整理能不能把早期细节写进案例摘要和偏好。
- E 的命中和质量都应该最好，但历史无上限，长对话时成本和超窗风险最高。
- C 的质量取决于压缩摘要有没有保住错误码和试过的方案，代价是每次压缩多一次调用。
- D 不需要额外调用，但案例摘要由记忆整理异步生成，内容不受窗口控制，质量风险最大。

## 7. 胜出方案的代价和风险（待实测后补）

目前能提前确认的通用风险：

- 只追加类方案在截断或压缩那一轮会整体丢一次缓存。
- C 多一次模型调用；摘要质量直接决定后面几轮能不能答对早期细节。
- D 依赖记忆整理按时完成；如果上一轮的整理还没完成，就会冻结一份过期摘要。
- 新增的会话状态字段要随会话持久化；对旧会话有默认值，向后兼容。

## 8. 是否合并到主分支

- **建议合并"可切换的实现 + 测试脚本"**：默认策略仍是 `sliding`，行为与改动前一致（有单测保证），合并没有行为风险，也方便之后在能联网的环境直接跑实测。
- **不建议现在切换默认策略**：等实测选出胜者后，再单独改 `CHAT_HISTORY_STRATEGY` 一行。

## 9. 怎么跑实测

在能访问 `api.deepseek.com` 的环境（你本机，或者放开网络后的新会话）：

```bash
git checkout main && git pull
pip install -r requirements.txt
export DEEPSEEK_API_KEY=...          # 不要写进任何会提交的文件
# 先到官网核对价格和模型名；如果 deepseek-chat 已弃用，用 --model 指定新模型名
python -m eval.benchmarks.history_window run --schemes A B C D E --runs 2 --max-cny 5 \
  --price-hit 0.0028 --price-miss 0.14 --price-out 0.28
```

结果写到 `eval_results/history_window/summary.json`，把对比表填进第 5.1 节，然后按第 2 节的标准选择。

费用估算：按 V4-Flash 价格、每次调用 6000 token、全部未命中，5 个方案各跑 2 遍保守上限约 ¥3.1；如果实际单价是旧版 deepseek-chat（未命中约贵一倍），上限会超过 ¥5，脚本会自动停下。
