# 02 两类测试：Assertion（确定性）与指标（概率性）

> 依据 00-随机性盘点：Assertion 只依赖确定性性质或对 LLM 输出的**结构约束**，
> 跑一次、要求 100% 通过；指标测试分"纯检索层（确定，跑一次）"和"端到端
> （含 LLM，重复 n 次）"。

## A. Assertion 测试（规则可判，违反即 bug）

### A1 幻觉控制类（核心）

| # | 断言内容 | 违反意味着什么 | 怎么实现 |
| --- | --- | --- | --- |
| A1-1 | `related_issues` 中每个 id ∈ 本轮 `reranked_docs` 的 id 集合 | LLM 编造了 issue 编号且**穿透了校验层**——v2 的白名单失效或被绕过（v1 没有校验层，跑 v1 时该断言=检测幻觉率的探针，预期会有违例，违例本身就是 v1→v2 的改进证据） | 对每条 run 的输出：`set(related_issues) <= {d["id"] for d in reranked_docs}`；需要 run_agent 返回或 trace 记录本轮候选集（v2 的 previous_decisions 里有 top_candidates 可用，完整候选集建议从 trace 取） |
| A1-2 | `decision` ∈ {"duplicate", "similar", "new"} | 枚举校验失效；下游按未知类别分支会出未定义行为 | 简单成员检查 |
| A1-3 | `0.0 <= confidence <= 1.0` 且为 float | 截断逻辑失效；重试条件 `confidence < 0.7` 对超界值的行为未定义 | 类型+区间检查 |
| A1-4 | decision ∈ {duplicate, similar} ⇒ `related_issues` 非空 | "说是重复却给不出对象"——v2 的降级规则（无合法 id 降级 new）失效 | 条件断言 |
| A1-5 | decision == "new" ⇒ `related_issues` 为空 | 违反 decision prompt 的硬约束第 4 条（"必须返回 new，related_issues 留空"）。⚠️ 待确认：v2 校验层**当前没有**强制这条（只处理了 duplicate/similar 无 id 的方向），此断言先作为观测探针，若违例率>0 建议在校验层补规则 | 条件断言 |
| A1-6 | 输出恰含 5 个字段：decision/confidence/related_issues/reasoning/retry_count，类型正确 | 结构化契约破坏，调用方（API/CLI）会 KeyError | schema 校验（对照 run_agent 返回结构） |
| A1-7 | `1 <= retry_count <= 3` | 回环控制失效（死循环或未执行） | 区间检查 |

v2 中支撑 A1-1/A1-4 的真实实现（被测对象）：

```python
candidate_ids = {str(doc.get("id", "")) for doc in state["reranked_docs"]}
related_issues = [str(i) for i in related_issues if str(i) in candidate_ids]  # 白名单
if decision in ("duplicate", "similar") and not related_issues:
    decision = "new"; confidence = min(confidence, 0.4)                       # 降级
```

### A2 管线不变量类

| # | 断言内容 | 违反意味着什么 | 怎么实现 |
| --- | --- | --- | --- |
| A2-1 | `reranked_docs` 的 id ⊆ `retrieved_docs` 的 id | 精排凭空多出候选（数据污染，参考 v1 的原地写分数坑） | 集合包含检查 |
| A2-2 | `len(retrieved_docs) <= HYBRID_TOP_K`；`len(reranked_docs) <= RERANK_TOP_K + RERANK_MAX_EXTRA_DOCS` | 截断逻辑失效，下游 prompt 长度失控 | 长度检查 |
| A2-3 | reranked_docs 按 rerank_score 非递增排列 | 排序被破坏（比如中途原地修改） | 相邻比较 |
| A2-4 | （v2，docstore 存在时）reranked_docs 中不存在 title 与 body 同时为空的候选 | docstore 补齐失效，精排在给空文本打分 | 字段非空检查 |
| A2-5 | 评测模式下 retrieved_docs 不含 query 自身 id | 自命中剔除失效，全部排名指标失真 | id 不等检查 |
| A2-6 | BM25 返回的每条 score > 0（仅 v2） | 0 分过滤失效 | 数值检查 |
| A2-7 | 同一输入、同一索引资产下，纯检索两次调用返回完全相同的 id 序列 | 检索层出现未知随机源（违反 00 盘点结论），一切"跑一次"的前提崩塌 | 关键回归测试：同 query 跑两遍比对序列 |

### A3 评测资产类

| # | 断言内容 | 违反意味着什么 | 怎么实现 |
| --- | --- | --- | --- |
| A3-1 | golden set 每条 query 的每个答案 id ∈ 索引 id 全集 | 可达性过滤失效，34% 问题回归 | 构建后全量校验 |

**执行方式**：Assertion 全集作为 pytest 用例挂进冒烟流程；A1 类在每次端到端
评测 run 上逐条执行（对每条输出断言），任何一条失败即整个评测报告标红作废。

## B. 指标测试（概率性分级）

### B1 各指标适合诊断什么

| 指标 | 诊断什么 | 备注 |
| --- | --- | --- |
| Recall@30（检索层） | 召回硬底线："精排的候选池里有没有答案"。它是全链路上限——这里丢了后面全丢 | 主门槛指标 |
| Recall@5 / @10 | 精排头部质量（配合 rerank 输出算） | rerank 输出最多 10 条，只在 @5/@10 比（公平截断） |
| Precision@K | 头部纯度：给 LLM 的候选里噪声占比 | 多答案少时天花板低（每 query 通常 1 个答案 → precision@5 上限 0.2），解读要带这个背景 |
| MRR | 第一个答案排多前，对应"维护者看第几条能看到" | 对头部敏感，配合 nDCG 用 |
| nDCG@10 | 多答案时的整体排序质量 | IDCG 必须按 min(答案数, K) 算（v1 本地实验版有此 bug，v2 已修并有回归测试） |
| 端到端三分类准确率 + 混淆矩阵 | 系统最终价值；混淆矩阵单列两类高成本错误：真 duplicate→new（漏检）、误报 duplicate（可能误关 issue） | 需要 01 文档的人工标注集 |
| related_issue 命中率 | 判为 duplicate/similar 时，标准答案是否在 related_issues 里（"判对且引用对"） | retry benchmark 已有实现雏形 |
| 重试触发率 / 平均轮数 / fallback 触发率 | LLM 随机性与流程健康度的观测口 | 均值±标准差都要报 |
| P50/P95 延迟、token 用量 | 成本与在线可行性 | 检索层与 LLM 层分开报 |

### B2 哪些跑一次、哪些重复跑

| 层 | 指标 | 跑几次 | 理由（对应 00 盘点） |
| --- | --- | --- | --- |
| 纯检索层（vector/bm25/hybrid 召回 + 精排排序） | Recall/Precision/MRR/nDCG/延迟 | **1 次** | 固定索引+同机+锁版本下全链路确定；A2-7 断言守护这个前提 |
| 端到端（含 Query Analysis / 重试 / Decision） | 三分类准确率、混淆矩阵、related 命中率、重试率、端到端延迟与成本 | **n=3（预算够 n=5）**，报均值±标准差 | LLM 随机 + 条件边放大（confidence 横跨 0.7 时整条路径分叉） |
| 中间混合（固定改写 query 测检索） | 同检索层 | 1 次 | 把 LLM 输出固化成 fixture 后，剩余链路确定——这正是 dual_query benchmark 的设计（固定 rewritten_query，隔离检索策略变量） |

**"固化 fixture"技巧**（把随机变确定的通用手段）：把某次 LLM 输出存下来当
固定输入，用于测它下游的确定性部件。retry_quality benchmark 反向用了同一
思想——固定案例与预期，只切换 prompt 变体：

```python
# eval/benchmarks/retry_quality.py（真实代码）：同一份代码切换 prompt 变体，
# 隔离"是否提供诊断上下文"这一变量，不必在两个 Git 提交间来回切换

    nodes._PROMPTS["query_analysis_retry"] = LEGACY_RETRY_PROMPT
```

### B3 v1 / v2 分别怎么跑

- **v2**：全套直接跑（资产、断言、指标均已就位；hybrid/rerank 两配置数字
  待补跑）。
- **v1**：目的不是"优化 v1"而是**量化 v1→v2 的每项改进**。方式：共享 v2 的
  golden set 与索引资产，在 v1 代码上跑同一指标集；预期 A1-1（白名单）与
  A2-4（空证据）在 v1 上出现违例——**违例率本身就是改进的度量**（v1 幻觉
  率、v1 空证据候选率）。注意 00 文档的 v1 原地污染坑：v1 评测每配置必须
  深拷贝候选。

## C. 负样本设计

### C1 三类负样本的区分

| 类别 | 定义 | 来源 | 用途 |
| --- | --- | --- | --- |
| **检索层负例** | 对某条 query，候选列表里"不是它的 ground truth"的所有 issue | 天然存在——Top-30 里除答案外全是 | 不需要专门构造；Precision/nDCG 的分母天然包含它们 |
| **判定层负样本（真"新" issue）** | 应被判为 new 的完整 query | 从 resolution 非 duplicate 且无 duplicate_of 的 issue 中抽 50-100 条，**人工快速复核**（"没被标"不等于"真不重复"，标注有漏） | 端到端三分类评估的 new 类；测系统会不会"过度合并"（把新问题硬安到旧 issue 上） |
| **难负样本（hard negative）** | 与 query 高度相似、但标注上不是 duplicate 的候选 | 挖掘流程见 C2 | 压力测试精排与判定的"区分力"；也是 similar 档的间接替身 |

### C2 难负样本挖掘（利用系统自身的检索结果）

流程（确定性，跑一次）：

```text
1. 对每条 golden query 跑一遍现有混合检索，取 Top-30 候选；
2. 剔除 ground truth 与 query 自身，剩下的都是"系统认为相似但标注非 duplicate"
   的候选——负样本原料；
3. 用候选内排名（或 RRF 分数）作难度代理，分三层：
   - easy   ：排名 21-30（系统自己都不太确信）
   - medium ：排名 6-20
   - hard   ：排名 1-5（系统最容易误认的——真正的压力所在）
4. 落盘 hard_negatives.json：{query_id, negative_id, rank, rrf_score}，
   随 golden set 一起记 hash。
```

**为什么用排名当难度代理**：没有人工相似度标注时，"检索系统把它排多前"就是
"它有多像"的最好免费信号；hard 层（排进 Top-5）意味着它会实际进入 LLM 的
候选列表，是线上真实会发生的混淆场景。

### C3 专项对照：hard 子集上量化两阶段架构的必要性

**设置**：取含 hard 负样本的 query 子集，比较两种 Top-5 的构成：
a) 融合后直接取 RRF Top-5；b) 融合 Top-30 经 Cross-Encoder 精排后取 Top-5。

**指标**：误判率差——两种 Top-5 里 hard 负样本挤掉 ground truth 的比例
（即"答案在 Top-30 但被 hard 负样本压出 Top-5"的 query 占比），以及
ground truth 在两种 Top-5 中的命中率差。检索层确定性，跑一次。

**这组的意义**：单独量化"Cross-Encoder 精排"这个第二阶段的必要性——如果
b) 相对 a) 在 hard 子集上误判率显著下降，就证明了"RRF 名次共识分不动的
细粒度差异，交叉编码能分动"；如果没差，两阶段的成本（CPU 上 1-3 秒/查询）
就失去辩护，简历上"Cross-Encoder 精排"应从"效果设计"降格为"架构实践"。
这与 03 文档主链步骤④互补：④测的是全量平均提升，本组测的是**最难场景下的
区分力**——平均值可能被简单案例稀释，hard 子集才是精排的试金石。

### C4 similar 档的诚实说明

similar（症状相似但根因不同，需人工进一步确认）**没有任何现成 ground
truth**——GitBugs 只标了 duplicate，没有"相似但不重复"的标注。两条路：
人工标注（首期 30-50 条，成本高）；或用难负样本**间接验证**：hard 负样本
在语义上恰好接近 similar 的定义（很像但标注说不是同一个），系统对 hard
负样本的理想行为就是判 similar 或 new 而非 duplicate——统计"hard 负样本
被误判为 duplicate 的比例"可以作为 similar 边界能力的代理指标。⚠️ 局限要
写明：这是代理不是真值，hard 负样本里可能混有漏标的真 duplicate（标注噪声），
该比例的绝对值不可靠，只用于版本间相对比较。
