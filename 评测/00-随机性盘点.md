# 00 随机性盘点：哪些模块确定、哪些随机、怎么控制

> 结论先行：**检索侧（BM25/向量查询/RRF/精排）在"固定索引 + 固定环境"下是
> 确定性的，可以跑一次；三个 LLM 节点是主要随机源，必须重复跑**。
> 一个例外要单独警惕：**索引构建阶段**（HNSW 建图）有随机性——"同一份索引上
> 查询确定" ≠ "重建索引后结果不变"。
> 版本口径：v1 = GitHub `issue-rag-agent`（commit fe4c55c）；v2 = 本地改进版。
> 两版检索算法相同，差异点在文中单独标注。

## 1. 总表

| 模块 | 是否确定 | 随机来源 | 如何控制 |
| --- | --- | --- | --- |
| jieba 分词（tokenize） | ✅ 确定 | 无（词典 + Viterbi 均为确定性算法） | 锁 jieba 版本与词典（requirements 锁版本） |
| BM25 检索（rank-bm25 get_scores + 排序） | ✅ 确定 | 无。打分是纯算术；排序用 Python `sorted`（稳定排序），同分按语料下标序打破，结果唯一 | 锁 bm25.pkl 文件（记录其 hash）；同分并列顺序依赖建库时的语料顺序——语料顺序由数据文件决定，锁数据快照 hash |
| Embedding 推理（MiniLM/bge，CPU） | ⚠️ 基本确定 | 浮点求和顺序受 BLAS/线程数影响，跨机器、跨 torch 版本可能有 1e-6 级差异；同机同版本重复推理结果一致 | 锁 torch/sentence-transformers 版本；固定 `OMP_NUM_THREADS`；评测结论只在同机同版本内比较 |
| ANN 查询（Chroma/HNSW，固定索引） | ✅ 确定 | 固定已建好的索引上，HNSW 图遍历是确定性的 | 锁 chroma_db 目录（记录索引 manifest/hash），评测期间禁止重建 |
| **ANN 索引构建**（HNSW 建图） | ❌ 不确定 | HNSW 为每个节点抽随机层数（RNG），且插入顺序影响图结构；重建后同一 query 的近邻集合可能有边缘差异 | **重建索引 = 新基线**：任何跨版本对比必须注明索引构建批次；对照实验共享同一份索引文件 |
| 向量结果聚合（chunk→issue，`1-distance` 排序） | ✅ 确定 | 纯算术 + 稳定排序 | 无需额外控制 |
| RRF 融合（内层/外层） | ✅ 确定 | 纯算术；同分并列由 dict 插入序 + 稳定排序打破（v2 代码注释明确利用了这点：同分时改写主路排前） | 无需额外控制 |
| Cross-Encoder 精排（bge-reranker-base，CPU） | ⚠️ 基本确定 | 同 Embedding：同机同版本确定，跨环境有浮点边缘差异；分差恰好在动态阈值 0.05 附近时，1e-6 的抖动可能改变截断条数（放大效应） | 同 Embedding 控制；报告中记录"动态扩展触发率"以监测该敏感性 |
| **Query Analysis（LLM）** | ❌ 随机 | DeepSeek API，temperature=0.1；即使 temp=0 服务端也不保证逐 token 一致（详见 04 文档） | 评测时 temperature=0；端到端指标重复 n 次报均值±标准差；缓存原始响应用于复盘 |
| **反思重写（LLM，重试轮的 Query Analysis）** | ❌ 随机且**级联** | 同上，且其输入包含上一轮 LLM 输出——随机性逐轮放大；是否触发重试本身又取决于上一轮 confidence | 同上；额外单独统计"重试触发率"的方差；固定评测集内逐条记录轮数 |
| **Decision（LLM）** | ❌ 随机 | 同上；confidence 是自报浮点值，同一输入多次调用可能 0.65/0.72 跳变——**恰好横跨 0.7 重试阈值时，随机性被条件边放大成"整条链路走向不同"** | 同上；这是端到端必须重复跑的核心理由 |
| JSON 解析与兜底（_parse_json） | ✅ 确定 | 纯正则+json.loads；随机的是它的输入（LLM 文本） | 无需控制，但要统计 fallback 触发率（它是 LLM 随机性的观测口） |
| v2 输出校验（枚举/截断/白名单/降级） | ✅ 确定 | 纯规则 | 无 |
| docstore 补齐（仅 v2） | ✅ 确定 | 纯字典查找 | 锁 docstore.pkl hash |
| 测试集采样（run_eval --limit） | ✅ 确定（已固定 seed） | `random.Random(seed).sample`，seed=42 固定 | 已控制；seed 记入结果 `_meta` |
| Golden set 划分（仅 v2 可信版） | ✅ 确定 | `random.Random(seed)` 打乱 family，seed=42 | 已控制；构建统计随文件落盘 |

## 2. 需要内嵌证据的三个判定

### 2.1 BM25 排序为什么确定（含同分并列）

v2 真实代码（v1 相同，仅少 extra_terms 与 0 分过滤）：

```python
scores = self.bm25.get_scores(query_tokens)          # 纯算术，无随机
top_indices = sorted(
    range(len(scores)),
    key=lambda index: scores[index],
    reverse=True,
)[:top_k]
```

Python 的 `sorted` 是稳定排序：分数相同的 issue 按下标（=建库语料顺序）排列，
每次结果完全一致。**推论**：语料顺序变了（数据文件重排）同分并列顺序会变——
所以数据快照 hash 必须进运行元数据（见 04 文档）。

### 2.2 LLM 随机性被条件边放大（本项目特有的结构性风险）

```python
# graph.py（v1/v2 相同）
if state["confidence"] < CONFIDENCE_THRESHOLD and state["retry_count"] <= MAX_RETRIES:
    return "retry"
```

Decision 的 confidence 是 LLM 自报值。同一输入两次调用报 0.68 和 0.72，就会
走出"重试一整轮"和"直接结束"两条完全不同的执行路径——后续的检索、精排、再
判定全部不同。**因此端到端指标的重复实验单位是"整条 run"而不是"单次 LLM
调用"**；报告里除了判定指标，必须同时报"重试触发率"的波动。

### 2.3 v1 特有的确定性坑：Reranker 原地污染 State

v1 真实代码：

```python
# v1 reranker.py —— 直接往调用方传入的 dict 写分数
scores = self.model.predict(pairs)
for doc, score in zip(docs, scores):
    doc["rerank_score"] = float(score)
```

后果：`retrieved_docs` 里的对象被悄悄加了 `rerank_score` 字段。在**同一进程内
重复评测**时（消融脚本常见写法：同一批候选喂给不同配置），前一个配置写入的
分数会残留到下一个配置的输入里，造成"顺序依赖的伪随机"。v2 已修（先
`doc.copy()` 再打分）。**对 v1 跑评测的硬规则：每个配置使用深拷贝的候选，或
直接在 v2 上跑（推荐）**。

## 3. 对后续设计的直接约束（本文档的输出）

1. **检索层指标（Recall/MRR/nDCG@检索与精排）只跑 1 次**——前提三锁：索引
   文件锁 hash、依赖锁版本、同机运行。
2. **含 LLM 的端到端指标重复 n=3（预算允许 n=5）**，报均值±标准差；同时报
   fallback 触发率、重试触发率两个"随机性观测口"。
3. **对照实验（消融）必须共享同一份索引资产**；涉及"重建索引"的消融（如粒度
   对称 vs 不对称，需要新建 chunk 粒度 BM25 索引）——新建的是 BM25（确定性
   构建，不含 HNSW 随机），**不允许**顺手重建 Chroma。
4. 每次运行记录：git commit、config hash、索引/docstore/数据快照 hash、
   模型名与版本、seed、时间戳（字段定义见 04/05 文档）。
5. Assertion 类测试（见 02 文档）只依赖确定性模块的性质 + 对 LLM 输出的
   **结构约束**（结构约束与内容随机无关），跑一次要求 100% 通过。
