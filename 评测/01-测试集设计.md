# 01 测试集设计

## 1. GitBugs 的 duplicate 标注长什么样、怎么变成 Ground Truth

**标注形式**：每条 issue 经 normalize 后有两个相关字段——`resolution`（处理
结论，如 duplicate/fixed/wontfix）和 `duplicate_of`（字符串列表，指向它重复的
目标 issue id）。真实样例（本地快照）：

```json
{"id": "firefox:1718989",
 "resolution": "duplicate",
 "duplicate_of": ["firefox:1710985"],
 "title": "Clearing 'Browsing & Download History' ... forget frecency ranking",
 "project": "firefox", ...}
```

**转成 Ground Truth 的规则**（v2 已实现，v1 需先移植——v1@GitHub 没有
golden set 构建器，v1 本地未提交版有四个有效性缺陷）：

1. 筛选：`resolution == "duplicate"` 且 `duplicate_of` 非空 → 该 issue 作为
   query，`duplicate_of` 列表作为标准答案；
2. **可达性过滤**：答案 id 必须存在于当前索引（用 bm25.pkl 的 id 全集校验），
   剔除自引用；全部答案不可达的 query 整条丢弃。v2 实测：13,104 条原始记录
   → 8,599 条有效（34% 无解，这是 v1 指标被系统性低估的根源）；
3. query 文本 = `title + "\n" + body`，走与建索引完全相同的
   normalize→clean 链路。

v2 真实代码（golden_set_builder.py 的过滤核心）：

```python
targets = []
for target in issue["duplicate_of"]:
    target_id = str(target)
    if target_id == query_id:                 # 自引用是数据噪声
        stats["dropped_self_reference_targets"] += 1; continue
    if target_id not in indexed_ids:          # 不可达：检索永远不可能命中
        stats["dropped_unreachable_targets"] += 1; continue
    targets.append(target_id)
if not targets:
    stats["dropped_no_reachable_target"] += 1; continue
```

## 2. 规模与正负样本

- **检索层测试集**：全量 held-out test 1,726 条（v2 family 隔离划分的 20% 侧）；
  日常回归用固定 seed 抽样 200 条（实测 200 条已能稳定区分 vector/bm25 的
  5 个点差距）；冒烟集 50 条（每次改动必跑）。
- **端到端判定测试集**（含 LLM，贵）：150–300 条，**必须含负样本**：
  - 正样本（真 duplicate）：从 test set 抽 100–200 条；
  - 负样本（应判 new）：从"resolution 非 duplicate 且无 duplicate_of"的 issue
    里抽 50–100 条。**注意**：这些只是"没被标为重复"，不保证真不重复（标注
    可能漏），所以负样本需人工快速复核一遍，剔除可疑者；
  - similar 类**没有现成标注**，只能人工标（从检索 Top-5 含高分候选但未标
    duplicate 的案例里挑）——这是最贵也最有价值的部分，首期 30–50 条即可。
- **比例建议**：duplicate : new ≈ 2:1 起步（现实分布里 new 更多，但评测要
  保证 duplicate 的统计功效；报告时同时给按真实先验加权的版本）。

## 3. 分层维度（每层为什么值得分、能诊断什么）

| 分层维度 | 怎么分 | 为什么值得分 | 能诊断出什么 |
| --- | --- | --- | --- |
| **难度（词面相似度）** | 计算 query 与其 ground truth 的词面重合度（如 token Jaccard），分高重合（≥0.3）/低重合（<0.3）两桶 | 高重合是 BM25 的主场，低重合是向量的主场；混在一起平均会互相掩盖 | 低重合桶 recall 差 → 语义召回弱（换 embedding 收益大）；高重合桶差 → 分词/索引问题（如驼峰不拆、词干不还原）；两桶都好但总体差 → 融合层把两路优势抵消了 |
| **仓库（project）** | 按 8 个项目分桶 | 各项目的 issue 文风差异大（Firefox 带 UA 串和 crash 报告格式，Cassandra 偏 Java 堆栈）；且 family 划分本来就按 project 分层 | 某项目显著差 → 该项目的文本形态没被 chunk/正则覆盖（例如 error 正则不认它的堆栈格式）；也防"平均数被大项目主导"的误读 |
| **issue 长度** | query 文本长度分短（<200 字符）/中（200–1500）/长（>1500）三桶 | 长短文本走的是系统里完全不同的路径：短文本靠 title chunk 与 BM25 精确词，长文本靠切分与截断策略 | 长桶差 → 截断/切分丢证据（RERANK_DOC_MAX_CHARS、chunk 策略的问题）；短桶差 → 信号太少，反思重写与放宽 query 的机制是否起作用 |
| **答案数（可选）** | 单答案 / 多答案（duplicate_of 长度>1） | 多答案时 nDCG/Recall 的行为不同；家族大小影响难度 | 多答案桶 recall@30 低 → 候选池太小或融合配额被挤占 |

分层报告格式：总表 + 每维度分桶表；**分桶样本量必须一并展示**（<30 条的桶
只做参考不下结论）。

## 4. 采样与配置的固定（保证版本间可比）

- **种子**：所有随机操作（family 打乱、抽样）用 `random.Random(EVAL_SEED)`
  显式实例，EVAL_SEED=42 写在 config；**禁止**用全局 `random.seed()`（会被
  其他库污染）。v2 现有实现已符合：

```python
# run_eval.py
def sample_queries(queries, limit, seed=EVAL_SEED):
    if limit is None or limit >= len(queries):
        return queries
    return random.Random(seed).sample(queries, limit)
```

- **划分固定**：golden_set.json 一经生成即视为资产，记录其文件 hash；重新
  生成（数据或索引变了）= 新评测集版本，跨版本数字不直接可比，报告必须注明
  评测集版本号。
- **配置记录**：每次运行落盘 `_meta`（v2 已有雏形：test_set_total、
  evaluated_queries、sampling、self_hit_excluded），扩展字段见 04 文档。
- **v1 怎么跑**：v1 没有可信评测集。方案：把 v2 的 golden_set.json 与
  docstore/索引资产**原样共享**给 v1 代码跑（两版索引内容一致时可比）；
  ⚠️ 待确认：v1@GitHub 的 chroma_db 是 bge-small-zh 建的旧索引，与 v2 的
  chroma_db_en 不是同一份资产——**跨 v1/v2 的向量路对比必须先统一索引**
  （要么 v1 换用 chroma_db_en + MiniLM 配置，要么明确标注"对比含索引差异"）。
