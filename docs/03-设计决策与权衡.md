# 03 设计决策与权衡（面试核心）

> 每个决策统一五段式：**决策 / 为什么 / 备选方案 / 为什么放弃备选 / 代价与局限**。
> 全部对应实际代码位置；"代价"一栏是面试加分点——说得出代价才证明真的做过权衡。

## 决策 1：混合检索（BM25 + 向量），而不是纯向量

- **决策是什么**：每个 query 同时走 BM25 关键词检索和向量语义检索，各取 Top-30，
  RRF 融合成一个候选列表（`src/retrievers/hybrid_retriever.py:31-108`）。
- **为什么这么选**：issue 查重场景里两类信号缺一不可。
  ① 错误码、异常类名、函数名（如 `NullPointerException`、`MOZ_CRASH`）是**精确匹配
  信号**——BM25 对这类罕见 token 有天然的高 IDF 加权，向量模型反而会把不同错误码
  嵌到相近的位置；② "描述同一现象的不同说法"（"点登录就闪退" vs "crash on login
  button"）是**语义信号**，BM25 一个词都对不上，只有向量能召回。GitBugs 数据里两类
  duplicate 都真实存在。
- **考虑过的备选方案**：a) 纯向量；b) 纯 BM25；c) 向量召回 + BM25 只做过滤。
- **为什么放弃备选**：a) 纯向量对错误码/版本号这类 OOV 精确信号不敏感，且
  all-MiniLM 只有 384 维，区分细粒度技术术语能力有限；b) 纯 BM25 无法跨说法召回，
  同义改写直接漏；c) 过滤式组合有先后依赖，一路错全错——对等融合让两路互为兜底。
- **代价/局限**：BM25 全量打分是纯 Python（rank-bm25 库），106,656 条 issue 约
  2-5s/query，是在线延迟大头；两套索引要同步维护（同一批 clean 数据构建，
  `scripts/run_step2.py:37`），存储翻倍（1.8G Chroma + 101M bm25.pkl）。

## 决策 2：RRF 融合，而不是加权分数融合

- **决策是什么**：两路结果只用**排名**融合：`score(d) = Σ 1/(k + rank_d)`，k=60
  （`hybrid_retriever.py:63-64,76-77`；k 值 `config.py:87`）。多 query 场景再做一层
  同公式的外层 RRF（`hybrid_retriever.py:159-181`）。
- **为什么这么选**：两路分数**量纲完全不可比**——BM25 分数无上界（长 query 能打到
  几十分），向量相似度在 0-1 之间。线性加权 `α·bm25 + (1-α)·cos` 必须先归一化再调 α，
  而 BM25 的 min-max 归一化对 query 长度极其敏感，α 也没有标注数据可调。RRF 只看
  排名，天然免疫量纲问题，k=60 是 Cormack 2009 在 TREC 上验证的经验值，不需要调参。
- **考虑过的备选方案**：a) 归一化后线性加权；b) 训练 LTR（learning-to-rank）模型；
  c) 两路取并集直接交给 Reranker。
- **为什么放弃备选**：a) 归一化方式本身就是新超参，且没有验证集可调（做这个项目时
  连可信 golden set 都还没有）；b) LTR 需要标注的相关性数据和特征工程，冷启动做不了；
  c) 并集不排序会让 60 个候选全进 Cross-Encoder，精排延迟直接翻倍，而 RRF 的"两路
  共识排前"本身就是有效的粗排。
- **代价/局限**：RRF 丢掉了分数的绝对信息——BM25 第 1 名是 50 分还是 0.5 分，RRF
  眼里都是 1/61；极端情况下"一路非常确定"的信号被平均化。这个损失由下游
  Cross-Encoder 重打分兜底。

## 决策 3：本地小模型 Embedding（all-MiniLM-L6-v2），而不是 API 或大模型

- **决策是什么**：用 sentence-transformers 的 all-MiniLM-L6-v2（384 维）本地 CPU
  跑 embedding（`config.py:36-42`，加载 `src/indexer.py:146-164`，
  `normalize_embeddings=True` 走 cosine）。
- **为什么这么选**：① 建库要对 10 万+ issue 的约 30 万个 chunk 全量向量化，走 API
  百万级 token 的费用和限流都不可控，本地模型零成本可重跑；② 数据集全英文，MiniLM
  在英文 STS 任务上性价比高；③ 384 维让 1.8G 的 Chroma 存储和检索延迟都减半
  （对比 768 维模型）；④ 离线可用（`HF_HUB_OFFLINE=1`，`indexer.py:152-154`）。
- **考虑过的备选方案**：a) OpenAI/其他 embedding API；b) bge-large 等 768/1024 维
  大模型；c) 曾经用过 bge-small-zh-v1.5（v1 早期，中文模型）。
- **为什么放弃备选**：a) 费用+限流+网络依赖，且数据出境合规存疑；b) CPU 上建库时间
  数倍增长，Mac 内存压力大，召回层的精度损失可以由 Reranker 补（两阶段设计的意义
  就在这）；c) 数据集实际全英文，中文模型是早期误选，v1 后期已换（`config.py:36`
  注释记录了这次纠错）。
- **代价/局限**：MiniLM 对长文本和代码片段的表征弱；384 维天花板明显——所以召回层
  只求"进 Top-30"，精度交给 Cross-Encoder。换更强 embedding 需要全量重建索引
  （数小时 CPU）。

## 决策 4：单独建 docstore，而不是把正文塞进 BM25 索引或查 Chroma

- **决策是什么**：独立文件 `docstore.pkl`（issue_id → {title, body 前 1200 字符}，
  `src/docstore.py:16-39`），检索融合后只给"缺正文的候选"补齐（`_hydrate`，
  `hybrid_retriever.py:203-228`：只填空、不覆盖）。
- **为什么这么选**：v1 的最大已知缺陷是——bm25.pkl 只存 id 和倒排结构，**只被 BM25
  召回的候选没有 title/body**，Reranker 对它打分、Decision 对它判断时拿到的是空字符
  串，等于这些候选"白召回了"。修复要点是给候选补正文，而正文的唯一权威来源是清洗后
  的 issue 数据，所以独立建一份 id→正文映射最直接。
- **考虑过的备选方案**：a) 把正文直接存进 bm25.pkl；b) 在线时按 issue_id 反查
  Chroma；c) 不补，让 Reranker 只对有正文的候选打分。
- **为什么放弃备选**：a) bm25.pkl 已 101MB，塞正文后每次加载 BM25 都被迫连正文一起
  加载，职责耦合，且换 BM25 实现（如 ES）时正文逻辑跟着重写；b) Chroma 按 metadata
  反查 30 个候选要 30 次 `get`，且 Chroma 存的是 chunk 不是完整正文，拼回 issue 还要
  聚合；c) 等于系统性歧视 BM25-only 候选——恰恰错误码强匹配的候选最可能只被 BM25
  召回。冒烟实测补齐后 30/30 候选都有正文证据。
- **代价/局限**：多一份 72MB 资产要与索引同步重建（`scripts/build_eval_assets.py`
  把它和 golden set 合并成一次预处理产出）；正文截 1200 字符，超长 issue 的后段
  信息丢失（够用：下游 Rerank 只看 800、Decision 只看 400，`config.py:61` 注释）；
  docstore 缺失时静默退回 v1 行为（`docstore.py:42-56`），是柔性降级但也意味着
  忘了建就悄悄变弱。

## 决策 5：加 Cross-Encoder Reranker，而不是召回分直接排序

- **决策是什么**：RRF Top-30 之后用 bge-reranker-base 对 (query, 候选) 逐对精排，
  取 Top-5（分差近时最多扩到 10）再交给 LLM（`src/reranker.py:25-76`）。
- **为什么这么选**：两阶段是"算力分配"问题。召回层（双塔向量 + BM25）为了能在
  10 万级语料上跑，query 和 doc 各自独立编码，**互相看不见对方**，精度天花板低；
  Cross-Encoder 把 query 和 doc 拼在一起过同一个 BERT，每层 attention 都在做
  token 级交互比对，精度高但一对一对算——只可能用在小候选集上。30 → 5 正是
  "贵模型只算 30 对"的设计点。另一个动机是保护 LLM：给 Decision 塞 30 个候选，
  prompt 超长且真答案容易淹没在中间（Lost in the Middle），Top-5 让 LLM 的比对
  任务变简单。
- **考虑过的备选方案**：a) 直接按 RRF 分取 Top-5 给 LLM；b) 让 LLM 自己从 30 个
  候选里挑（跳过精排）；c) 用更大的 reranker（bge-reranker-large）。
- **为什么放弃备选**：a) RRF 分是排名共识不是相关性度量，Top-5 截断误伤率高；
  b) LLM 读 30 个候选的成本比 Cross-Encoder 贵一个量级，且长上下文比对可靠性差；
  c) large 版 CPU 上单轮多花数秒，base 版精度已够"从 30 里挑出前 5"这个难度的任务。
- **代价/局限**：CPU 上 30 对约 1-3 秒（待确认，以 hybrid_rerank 评估结果为准）；
  输入截 800 字符，候选核心证据若在正文后段会打分失真；分数不是概率，只能比大小
  （所以诊断里的 top_score/score_gap 只当相对线索用，`nodes.py:436-440` 注释）。

## 决策 6：chunk 策略——title / error_log / body 三类，500/80 递归切分

- **决策是什么**：每条 issue 切成三类 chunk（`src/indexer.py:85-143`）：
  ① title 单独成 chunk（必建）；② 用正则从 body 里定位第一个错误特征
  （Traceback / XxxError: / at file:line 三种模式，`indexer.py:33-49`），从那里截到
  文末作为 error_log chunk；③ 剩余 body 用 RecursiveCharacterTextSplitter 按
  500 字符/重叠 80 切分，<30 字符的碎片丢弃。检索时 chunk 召回、按 issue_id 聚合
  （`vector_retriever.py:35-53`）。
- **为什么这么选**：① issue 的 title 是人写的最强摘要，混进长 body 会被稀释，单独
  成 chunk 让"短标题撞短标题"的 duplicate 可以直接命中；② 错误堆栈是查重最强信号，
  但它和自然语言描述的向量分布完全不同，切出来单独嵌入避免互相污染；③ 500 字符
  约一个段落，是"语义完整"和"向量不稀释"的折中；80（16%）重叠保住跨边界的句子。
- **考虑过的备选方案**：a) 整条 issue 一个向量；b) 固定长度硬切不分类型；
  c) 按 Markdown 结构/句子边界切。
- **为什么放弃备选**：a) issue 长短差异极大（一行 vs 几千字），长 issue 的向量被
  平均成"模糊的大意"，错误码信号完全稀释；b) 会把堆栈从中间切断，错误特征跨 chunk
  后哪个都匹配不上；c) issue 正文是用户随手写的，结构不可靠，通用递归分隔符
  （`config.py:71`：段落→换行→句号→……）更稳。
- **代价/局限**：error 正则只认三种模式，Rust panic、Go panic 等格式识别不到
  （落回 body chunk，不丢数据只丢"单独成块"的加成）；error_log 取"第一个匹配到
  文末"，若错误段在正文中间会把后面的描述也卷进去；聚合时每个 issue 只留最高分
  chunk 作代表，其余命中 chunk 的信息被丢弃。

## 决策 7：要有 Decision LLM 阶段，而不是"Rerank 分数超阈值即 duplicate"

- **决策是什么**：精排 Top-5 之后由 DeepSeek 做三分类（duplicate/similar/new）+
  置信度 + 引用 + 理由，且输出过程序级校验（`src/agent/nodes.py:346-493`）。
- **为什么这么选**：① "相关"不等于"重复"——两个 issue 讲同一个模块、症状相似，
  可能根因完全不同；duplicate 的判定标准是"同根因、可由同一次修复解决"
  （`prompts/decision_system.md`），这是需要**比对推理**的任务，不是相似度阈值能
  表达的；② 分诊场景需要 similar 这个中间态（提示维护者"先看这几个再决定"），
  二值阈值给不了；③ reasoning 让维护者可以核查判断依据，可解释性是采纳的前提。
- **考虑过的备选方案**：a) rerank_score 阈值二分类；b) 训练一个专门的
  duplicate 分类头；c) 不做判断，直接返回 Top-5 列表让人看。
- **为什么放弃备选**：a) Cross-Encoder 分数不是概率、不同 query 间不可比，一个全局
  阈值在"歧义 query"上大量误判，也产不出理由；b) 需要成对标注数据（当时没有），
  且三分类边界（similar vs duplicate）恰恰是标注最难的部分；c) 那系统就退化成
  搜索框，没有解决"压缩人工阅读"的核心目标——但我们保留了 c 的精神：related_issues
  必须可核查（白名单校验），LLM 结论是建议不是终审。
- **代价/局限**：每轮 1-2 次 API 调用的延迟和费用；confidence 是 LLM 自报值，
  只截断未校准（0.8 不等于 80% 准确率）；判断质量受 prompt 影响大；LLM 输出
  不可靠的部分靠校验层兜（枚举/白名单/降级，`nodes.py:388-425`）。

## 决策 8：双路召回（rewritten_query + raw_issue），而不是只用改写结果

- **决策是什么**：Retrieval 同时用"LLM 改写 query"和"原始 issue 文本"各跑一遍完整
  混合检索，外层 RRF 融合（`nodes.py:307-312`，`hybrid_retriever.py:110-201`）。
- **为什么这么选**：改写是双刃剑——它能提炼技术信号提升召回，但 LLM 可能删掉
  关键错误码、改错术语（改写幻觉/漂移），此时真 duplicate 会**完全漏召回**，
  后面的 Rerank/Decision 再强也救不回来。原文路是针对"上游单点故障"的保险。
- **考虑过的备选方案**：a) 只用改写（v1 做法）；b) 只用原文不改写；c) 改写失败时
  才回退原文（串行 fallback）。
- **为什么放弃备选**：a) 把全链路押在一次 LLM 输出上，尾部风险不可接受；b) 原文
  含大量口语噪声，主路检索质量下降；c) "改写在语义上错了但格式上成功"检测不出来，
  串行 fallback 只能兜格式失败，兜不住语义漂移。
- **代价/局限**：检索耗时接近翻倍（两路串行执行；改写恰好等于原文时会去重免掉，
  `hybrid_retriever.py:126-134`）；两路结果都一般时外层 RRF 可能互相稀释——
  这正是 `eval/benchmarks/dual_query_retrieval.py` 要量化的问题（rescue vs
  regression 率），目前缺人工 verified 案例还没跑出正式结论（待确认）。

## 决策 9：LangGraph 固定四节点 + 条件边，而不是自主 Agent 或裸函数链

- **决策是什么**：StateGraph 编排 query_analysis → retrieval → rerank → decision，
  唯一分支是 decision 后的 should_retry 条件边（`src/agent/graph.py:85-119`）。
- **为什么这么选**：查重流程是**确定性流水线**，不需要 LLM 自己决定"下一步干什么"；
  需要的是共享状态（State 合并语义）+ 一个受控回环（低置信度重写）。LangGraph 的
  TypedDict State + 条件边正好覆盖，还免费拿到未来扩展点（加节点、加分支、可视化）。
- **考虑过的备选方案**：a) 普通 Python 函数顺序调用 + while 循环；b) ReAct 式自主
  Agent（LLM 决定调什么工具）。
- **为什么放弃备选**：a) 可行且更简单，但 retry 时"哪些字段覆盖、哪些追加"的状态
  管理要手写，节点间契约靠约定，工程上不如声明式清晰——诚实说：这个规模下 a 和
  LangGraph 差距不大，选 LangGraph 也有熟悉主流编排框架的学习动机；b) 自主 Agent
  在固定流程上纯属浪费：不可控、更贵、更难评估。README 里明确不把本项目称为
  "高度自主 Agent"，防止面试被拆穿。
- **代价/局限**：引入框架依赖和版本演进风险；每节点整轮重跑（retry 时 rerank 明明
  可能不需要重做，但图结构是整轮回环）。

## 决策 10：BM25 用 issue 粒度、向量用 chunk 粒度（不对称设计）

- **决策是什么**：Chroma 存 chunk（一条 issue 多个向量），BM25 把 title+body 合并成
  一条文档建索引（`src/indexer.py:221-241`），检索后统一到 issue 粒度融合。
- **为什么这么选**：向量的"稀释问题"来自平均化——长文本压进一个定长向量必然糊，
  所以要切；BM25 是词频统计模型，文档越完整词的共现证据越多，切碎反而破坏
  TF/文档长度归一化的统计意义（一个 issue 被切成 8 个 chunk 后，还得处理"同一
  issue 的 chunk 互相竞争排名"）。各用各的最优粒度，在融合层对齐到 issue。
- **考虑过的备选方案**：两者都用 chunk 粒度，或都用 issue 粒度。
- **为什么放弃备选**：都 chunk：BM25 统计意义被破坏 + 融合前要多一层聚合；
  都 issue：向量稀释问题回来了。
- **代价/局限**：向量路聚合时"最高分 chunk 代表整条 issue"，body 字段是片段而非
  全文（这是特性也是坑：对 Rerank 是最相关证据，对人读是断章取义——docstore
  只在 body 为空时补，不覆盖这个片段，`hybrid_retriever.py:216-224` 注释）。

## 决策 11（横切）：所有 LLM 输出必须过程序级校验，宁可降级不可带幻觉返回

- **决策是什么**：解析层（剥代码块、正则截 JSON、fallback）+ 语义层（枚举、
  区间截断、related_issues 白名单、无证据降级触发重试）双层防御
  （`nodes.py:86-113,388-425`）。
- **为什么这么选**：这是对外契约问题——调用方拿到的 `related_issues` 里若有一个
  编造的 issue id，整个系统的可信度归零。校验层保证"返回的每个 id 都真实存在于
  本轮候选"这条硬性质，可以写进接口文档。
- **备选**：信任 prompt 约束（decision_system.md 里已写"只能从候选列表选"）。
- **为什么放弃**：prompt 约束是概率性的，校验是确定性的；防御纵深要求两层都有。
- **代价/局限**：降级策略偏保守（无合法 id 的 duplicate 一律转 new），可能把
  "判断对了但 id 抄错"的案例也压下去了——换取的是零幻觉 id 的硬保证。
