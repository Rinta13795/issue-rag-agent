# 07 已知缺陷与改进路线

> 第一部分诚实列出当前实现的不足（含踩过的坑的残留影响）；第二部分是 v3 路线，
> 按优先级排序，每项写清"为什么值得做"和"大概怎么做"。面试时主动讲缺陷比被问出
> 缺陷分数高得多。

## 一、当前已知缺陷

### A. 评估层

1. **端到端三分类没有可信指标**。检索层有完整评估，但 duplicate/similar/new 的
   最终判断没有人工标注测试集——现在无法回答"系统分类准确率多少"。这是最大的
   缺口（建法见 06 文档 2.1）。
2. **时间穿越（time-travel leakage）**。评测和线上检索的都是全量索引，包含比
   query 更晚创建的 issue；真实场景只能检索到更早的历史。`created_at` 没写进
   Chroma metadata（`src/indexer.py:91-99` 的 base_meta 里没有它），修复必须
   重建 1.8G 索引，v2 没做。当前指标相对真实场景**偏乐观**。
3. **两个 benchmark 缺 verified 案例**。retry 价值、双路召回价值的对照框架都写好
   了（`eval/benchmarks/`），但要求人工确认的案例数据（`status=verified` 校验，
   `eval/benchmarks/retry_quality.py:50-62`），没有编造数据，所以还没有结论。
4. **抽样评估**。当前数字基于 200 条抽样（全量 1,726 条太慢），置信区间没算。

### B. 检索层

5. **BM25 是纯 Python 全量打分**。106,656 条 issue 约 2-5s/query，是在线延迟的
   绝对大头（`src/retrievers/bm25_retriever.py:51`）；数据量再涨一个量级就不可用。
6. **向量路"最高分 chunk 代表整条 issue"**。其余命中 chunk 的信息被丢弃
   （`src/retrievers/vector_retriever.py:46-53`）；docstore 只补空不覆盖，所以
   Decision 看到的向量路候选正文是片段而非全文开头，跨段证据可能缺失。
7. **error 正则只认三种模式**（`src/indexer.py:33-49`：Python Traceback、
   XxxError:、at file:line）。Rust panic、Go panic、Java 长堆栈变体识别不到，
   落回 body chunk，损失 error_log 单独成块的加成。
8. **component 过滤没有数据基础**。当前快照 component 字段全空，LLM 猜出的
   component 会构造一个永远匹配不到的 Chroma filter（好在 BM25 路不过滤兜底）。
9. **现有 Chroma 索引是 l2 空间遗留**。`1 - distance` 只保序、数值含义不严格；
   代码已为重建后的索引声明 cosine（`src/indexer.py:180-187`），但没重建。
10. **中文分词器处理英文语料**。jieba 对英文只是按空格切+小写
    （`src/indexer.py:209-218`），没有词干化（crashes/crashed 是不同 token）、
    没有驼峰拆分（`NullPointerException` 不会拆成 3 个词）——对代码类 token 的
    召回有隐性损失。

### C. 决策层

11. **confidence 未校准**。只做区间截断（`src/agent/nodes.py:398-402`），0.8 不
    等于 80% 准确率；0.7 重试阈值没有数据支撑。
12. **重试是整轮重跑**。retry 回到 Query Analysis 后 retrieval/rerank 全部重做
    （`src/agent/graph.py:106-110` 的图结构决定），即使新旧 query 差异很小；
    最坏 3 轮 = 3 倍延迟和 LLM 费用。
13. **prompt 注入只有提示词级防护**（`nodes.py:361-368` 声明 + 输出白名单兜底），
    没有内容转义或结构化隔离。
14. **降级策略偏保守**。"duplicate 但白名单过滤后无合法 id"一律降级 new
    （`nodes.py:421-425`），可能误伤"判断对但 id 抄错"的案例。

### D. 工程层

15. **无法真实调用 LLM 的现状**：DeepSeek 账户余额为 0（2026-07-26 实测 402），
    且 v1 的 `.env.example` 曾提交真实有效 key 进 git 历史——**该 key 必须作废
    轮换**。当前所有含 LLM 的验证走离线替身。
16. **没有 Docker/lockfile/CI**。requirements 只有下界版本约束，干净环境复现
    没有保证；测试没有在 CI 里自动跑。
17. **API 无鉴权、无限流**（`api.py`）；BM25 慢查询会占死 worker（同步阻塞）。
18. **索引无增量更新**。新 issue 进不了索引，只能全量重建（数小时）。

## 二、v3 改进路线（按优先级）

### P0（先做：补上"说不出分类准确率"的洞）

1. **人工标注 200-300 条三分类测试集 + 端到端评估**
   为什么：这是系统最终价值的直接度量，也是面试最常被追问的数字；没有它，
   一切决策层改动都无法验证。
   怎么做：从 test set 分层抽样（按 project、按检索难度），双人标注 + 仲裁；
   跑通 06 文档 2.1 的混淆矩阵与 related_issues 命中率；顺手给两个 benchmark
   标 20-30 条 verified 案例，把 retry 和双路的价值量化出来。
   前置：给 DeepSeek 充值或换可用的 LLM 供应商。

2. **重建索引：created_at 进 metadata + cosine 空间 + 时间过滤评估**
   为什么：消除时间穿越，让指标可信；顺手把 l2 遗留清掉。
   怎么做：`chunk_issue` 的 base_meta 加 `created_at`；评估时按"只检索早于
   query 的 issue"过滤重跑，得到真实场景指标；线上接口同步支持按时间/项目过滤。
   成本：一次数小时的全量重建（可趁机换 embedding，见 P1-4）。

### P1（检索质量与性能的确定性收益）

3. **BM25 换引擎**（Elasticsearch / Tantivy / bm25s 库）
   为什么：2-5s → 几十 ms，消除最大延迟瓶颈，同时解锁增量更新。
   怎么做：`BM25Retriever` 接口不变换实现；分词管道加词干化与驼峰拆分（对应
   缺陷 10）；迁移后跑消融确认 recall 不回退。

4. **升级 embedding 并重建**（如 bge-base-en-v1.5 或 gte 系列）
   为什么：MiniLM 384 维是召回天花板；vector_only recall@30 仅 0.48，
   召回层每提一个点，全链路跟着涨。
   怎么做：候选模型在 eval set 上小规模对比（golden set 已可信，实验成本低），
   赢家全量重建；与 2 合并成一次重建。

5. **消融矩阵跑全**（06 文档 2.3 的五组开关）
   为什么：v2 的每项改进目前只有"结构上应该更好"的论证，缺 A/B 数字；
   面试说"docstore 让 rerank recall@5 提升 X 点"比"我做了 docstore"强一个档次。

### P2（决策质量）

6. **置信度校准 + 重试阈值数据化**（依赖 P0-1 的标注）
   可靠性图 + 温度缩放；用"重试后改善率"曲线选阈值替换拍脑袋的 0.7。

7. **重试增量化**：改写后的 query 与上轮相似度高时跳过重检索，只重跑
   rerank/decision；或图上加"检索结果无变化则直接终止"的短路边——砍掉最坏
   3 倍延迟中的浪费部分。

8. **注入防护升级**：候选正文进 prompt 前做定界符包裹与指令样式转义；
   加对抗样例回归测试。

### P3（工程化与部署形态）

9. **Docker + lockfile + CI**（pytest + 冒烟测试进 pipeline；uv/pip-tools 锁版本）。
10. **API 生产化**：鉴权、限流、检索线程池隔离、/triage 流式返回（先吐候选列表
    再吐 LLM 判断，感知延迟减半）。
11. **增量索引管道**：新 issue 实时进三份资产（Chroma upsert + BM25 引擎增量 +
    docstore append），配每日一致性校验任务。
12. **本地分类模型蒸馏**（远期）：积累数万条人工核验分诊记录后，蒸馏一个
    duplicate 判别小模型替代 API 决策，消除单次调用费用与网络依赖。

## 三、一句话优先级逻辑

**先让"最终输出"可度量（P0），再抬"检索上限"（P1），然后精修"判断质量"（P2），
最后做"部署形态"（P3）**——每一层的优化都以上一层的可信评估为前提，这是这个
项目 v1→v2 用 34% 无解评测集换来的最重要教训。
