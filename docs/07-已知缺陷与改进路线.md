# 07 已知缺陷与改进路线

## 📌 项目速览（每个文档都重复，便于单独阅读）

Issue 查重系统：新 issue 提交后，在 106,714 条历史 issue（GitBugs 数据集，8 个开源项目）里找重复，输出 duplicate / similar / new 三分类 + 置信度 + 相关 issue 编号 + 判断理由。在线流程是 LangGraph 四节点：LLM 改写 query → 双路混合检索（BM25 + 向量各 Top-30，双层 RRF 融合，docstore 补齐正文）→ Cross-Encoder 精排 Top-5 → LLM 决策 + 程序级校验；置信度 < 0.7 且未超 2 次重试时带诊断回环重写。技术栈：Python、LangGraph、DeepSeek、ChromaDB（all-MiniLM-L6-v2，384 维）、rank-bm25、bge-reranker-base、FastAPI。

> 面试时主动讲缺陷比被问出缺陷分数高得多。每条缺陷都是代码事实，不是谦虚话术。

## 一、当前已知缺陷

### A. 评估层

1. **端到端三分类没有可信指标**。检索层有完整评估，但 duplicate/similar/new 的
   最终判断没有人工标注测试集——无法回答"系统分类准确率多少"。最大缺口，建法
   见 06b。
2. **时间穿越（time-travel leakage）**。评测和线上检索的都是全量索引，包含比
   query 更晚创建的 issue；真实场景只能检索到更早的。根因：`created_at` 没写进
   chunk 的 metadata，修复必须重建 1.8G 索引。当前指标相对真实场景**偏乐观**。

   <details><summary>点开看证据（src/indexer.py 的 base_meta，没有 created_at）</summary>

   ```python
   base_meta = {
       "issue_id": issue["id"], "title": issue["title"],
       "labels": ",".join(issue["labels"]), "component": issue.get("component") or "",
       "status": issue["status"], "project": issue["project"],
       # 注意：没有 created_at —— 无法在检索时做"只查更早的 issue"过滤
   }
   ```
   </details>

3. **两个 benchmark 缺 verified 案例**。retry 价值、双路召回价值的对照框架都写好
   了，但要求人工确认的案例（`status=verified` 校验），没有编造数据，所以还没有
   结论。
4. **抽样评估**。当前数字基于 200 条抽样（全量 1,726 条太慢），置信区间没算；
   hybrid / hybrid_rerank 两个配置的评估中断待补跑。

### B. 检索层

5. **BM25 是纯 Python 全量打分**。实测 p50=2.9s、p95=49s（200 条抽样），是在线
   延迟的绝对大头；数据量再涨一个量级就不可用。

   <details><summary>点开看根因（src/retrievers/bm25_retriever.py）</summary>

   ```python
   scores = self.bm25.get_scores(query_tokens)   # rank-bm25：对全库 106,656 条逐一打分
   # 没有倒排跳表/剪枝，复杂度 O(语料数 × query 词数)，长 query 最坏近 1 分钟
   ```
   </details>

6. **向量路"最高分 chunk 代表整条 issue"**。其余命中 chunk 的信息被丢弃；docstore
   只补空不覆盖，所以 Decision 看到的向量路候选正文是片段而非全文，跨段证据可能
   缺失。
7. **error 正则只认三种模式**（Python Traceback / `XxxError:` / `at file:line`）。
   Rust panic、Go panic 等识别不到，落回 body chunk，损失 error_log 单独成块的
   加成。
8. **component 过滤没有数据基础**。当前快照 component 字段全空，LLM 猜出的
   component 会构造一个永远匹配不到的 Chroma filter（好在 BM25 路不过滤兜底）。
9. **现有 Chroma 索引是 l2 空间遗留**。`score = 1 - distance` 只保序、数值含义
   不严格；代码已为重建后的索引声明 cosine，但没重建。
10. **中文分词器处理英文语料**。jieba 对英文只是按空格切+小写：没有词干化
    （crashes/crashed 是不同 token）、没有驼峰拆分（`NullPointerException` 不会
    拆成 3 个词）——对代码类 token 的召回有隐性损失。

### C. 决策层

11. **confidence 未校准**。只做区间截断，0.8 不等于 80% 准确率；0.7 重试阈值没有
    数据支撑。
12. **重试是整轮重跑**。retry 回到 Query Analysis 后 retrieval/rerank 全部重做
    （图结构决定），即使新旧 query 差异很小；最坏 3 轮 = 3 倍延迟和 LLM 费用。
13. **prompt 注入只有提示词级防护**（候选区块前的声明 + 输出白名单兜底），没有
    内容转义或结构化隔离。
14. **降级策略偏保守**。"duplicate 但白名单过滤后无合法 id"一律降级 new，可能
    误伤"判断对了但 id 抄错"的案例——换取零幻觉 id 的硬保证。

### D. 工程层

15. **LLM 调用当前不可用**：DeepSeek 账户余额为 0（实测 402），且 v1 的
    `.env.example` 曾提交真实有效 key 进 git 历史——**该 key 必须作废轮换**。
    当前所有含 LLM 的验证走离线替身（smoke_test 默认 offline 模式）。
16. **没有 Docker/lockfile/CI**。requirements 只有下界版本约束，干净环境复现
    没有保证；测试没有在 CI 里自动跑。
17. **API 无鉴权、无限流**；BM25 慢查询会占死同步 worker。
18. **索引无增量更新**。新 issue 进不了索引，只能全量重建（数小时）。

### ✅ 自测（缺陷）

2. 四层缺陷里哪两条互相关联成"评估→决策"的因果链？（提示：1 和 11）

## 二、v3 改进路线（按优先级）

### P0（先做：补上"说不出分类准确率"的洞）

1. **人工标注 200-300 条三分类测试集 + 端到端评估**。这是系统最终价值的直接
   度量；没有它，一切决策层改动都无法验证。顺手给两个 benchmark 标 20-30 条
   verified 案例，把 retry 和双路的价值量化。前置：DeepSeek 充值或换供应商。
2. **重建索引：created_at 进 metadata + cosine 空间 + 时间过滤评估**。消除时间
   穿越让指标可信；评估改为"只检索早于 query 的 issue"；线上接口同步支持按
   时间/项目过滤。成本：一次数小时全量重建（可与 P1-4 换模型合并）。

### P1（检索质量与性能的确定性收益）

3. **BM25 换引擎**（Elasticsearch / Tantivy / bm25s）：2.9s → 几十 ms，消除最大
   延迟瓶颈，解锁增量更新；分词管道加词干化与驼峰拆分（对应缺陷 10）；迁移后跑
   消融确认 recall 不回退。
4. **升级 embedding 并重建**（bge-base-en-v1.5 / gte 系列）：MiniLM 384 维是召回
   天花板（vector_only recall@30 仅 0.48）；候选模型先在 eval set 上小规模对比，
   赢家全量重建，与 P0-2 合并成一次重建。
5. **消融矩阵跑全**（06b 的五组开关）："docstore 让 rerank recall@5 提升 X 点"
   比"我做了 docstore"在面试里强一个档次。

### P2（决策质量）

6. **置信度校准 + 重试阈值数据化**（依赖 P0-1 标注）：可靠性图 + 温度缩放；
   用"重试后改善率"曲线选阈值替换 0.7。
7. **重试增量化**：新旧 query 相似度高时跳过重检索只重跑 rerank/decision，或
   图上加"检索结果无变化则短路终止"——砍掉最坏 3 倍延迟中的浪费。
8. **注入防护升级**：候选正文定界符包裹 + 指令样式转义 + 对抗样例回归测试。

### P3（工程化与部署形态）

9. **Docker + lockfile + CI**（pytest + 冒烟进 pipeline）。
10. **API 生产化**：鉴权、限流、检索线程池隔离、/triage 流式返回（先吐候选列表
    再吐 LLM 判断，感知延迟减半）。
11. **增量索引管道**：新 issue 实时进三份资产 + 每日一致性校验。
12. **本地分类模型蒸馏**（远期）：积累数万条人工核验分诊记录后，蒸馏 duplicate
    判别小模型替代 API 决策。

### 优先级逻辑（一句话）

**先让"最终输出"可度量（P0），再抬"检索上限"（P1），然后精修"判断质量"（P2），
最后做"部署形态"（P3）**——每一层的优化都以上一层的可信评估为前提，这是 v1→v2
用 34% 无解评测集换来的最重要教训。

## 自测答案

<details>
<summary>缺陷部分答案</summary>

1. 评测/线上检索包含"比 query 更晚创建"的 issue，而真实分诊只能查历史 → 指标
   **偏乐观**。根因是 created_at 没进 chunk metadata；修复要全量重建 1.8G 索引
   （数小时 CPU）。
2. 缺陷 1（无三分类标注）→ 缺陷 11（confidence 无法校准）：校准需要"预测置信度
   vs 实际对错"的配对数据，而"实际对错"只能来自三分类标注集。先补 1 才能修 11。
3. rank-bm25 没有倒排索引跳表/WAND 剪枝，get_scores 对全库 106,656 条逐一算分，
   复杂度随语料数 × query token 数线性增长；评测 query 是完整 title+body，token
   极多，长尾就到了 49 秒。
</details>

<details>
<summary>路线部分答案</summary>

4. 因为当前的瓶颈是"无法度量"而不是"能力不足"：没有三分类标注，换任何模型都
   说不出变好还是变坏；没有时间过滤，检索指标本身失真。度量基础设施先行，
   模型升级（P1-4）才有裁判。
5. P1-3 解决**延迟/扩展性**维度（2.9s→几十 ms，解锁增量更新），P1-4 解决
   **召回质量**维度（384 维语义表征天花板）。两者正交，可分别消融验证。
6. "先让最终输出可度量，再抬检索上限，然后精修判断质量，最后做部署形态。"
   关系：故事 1 证明了"尺子不可信时所有优化都是自我感觉良好"，所以 v3 路线把
   补全度量（P0）放在一切能力升级之前——同一教训从 v2 的检索层推广到端到端。
</details>
