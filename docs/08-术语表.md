# 08 术语表

## 📌 项目速览（每个文档都重复，便于单独阅读）

Issue 查重系统：新 issue 提交后，在 106,714 条历史 issue（GitBugs 数据集，8 个开源项目）里找重复，输出 duplicate / similar / new 三分类 + 置信度 + 相关 issue 编号 + 判断理由。在线流程是 LangGraph 四节点：LLM 改写 query → 双路混合检索（BM25 + 向量各 Top-30，双层 RRF 融合，docstore 补齐正文）→ Cross-Encoder 精排 Top-5 → LLM 决策 + 程序级校验；置信度 < 0.7 且未超 2 次重试时带诊断回环重写。技术栈：Python、LangGraph、DeepSeek、ChromaDB（all-MiniLM-L6-v2，384 维）、rank-bm25、bge-reranker-base、FastAPI。

> 每个术语：通用含义一句话 + **在本项目里具体指什么**。按主题分组。

## 检索基础

| 术语 | 通用含义 | 在本项目里 |
| --- | --- | --- |
| RAG | 检索增强生成：先检索相关材料，再让 LLM 基于材料产出 | 检索历史 issue 候选，LLM 基于候选做三分类判断（生成的是结构化决策不是文章） |
| BM25 | 基于词频统计的经典检索算法（TF 饱和 × IDF × 长度归一化） | rank-bm25 库的 BM25Okapi，issue 粒度建索引，k1=1.5/b=0.75 库默认，负责错误码等精确信号 |
| TF | 词频：词在文档中出现的次数（BM25 中有饱和设计，k1 控制） | keywords 追加进 query token 就是在放大目标词的 TF 贡献 |
| IDF | 逆文档频率：全库越罕见的词权重越高 | NullPointerException 这类错误码 IDF 极高，是 BM25 擅长查重的根源 |
| 倒排索引 | 词 → 包含它的文档列表的映射结构 | rank-bm25 实际是全量打分**没有**真倒排跳表，这是 p50=2.9s 延迟瓶颈的原因 |
| 分词（tokenize） | 把文本切成词单元 | jieba 分词 + 空格细分 + 小写；建索引和查询必须用同一个函数否则词对不上 |
| Embedding | 把文本编码成定长向量，语义近则向量近 | all-MiniLM-L6-v2，384 维，本地 CPU，归一化后用余弦相似度 |
| 双塔（Bi-Encoder） | query 和文档各自独立编码成向量，线上只算距离 | 向量召回层：文档向量离线预计算进 ChromaDB，才能扛 10 万级候选 |
| Cross-Encoder | query 和文档拼接后过同一个模型逐层交互，精度高但逐对现算 | bge-reranker-base，对 RRF Top-30 逐对打分精排到 Top-5 |
| Reranker | 精排器：对召回候选重新排序的第二阶段模型 | 即上面的 Cross-Encoder；带动态截断（分差<0.05 时最多扩到 Top-10） |
| 向量数据库 | 存向量并支持近似最近邻查询的库 | ChromaDB，本地持久化 chroma_db_en/，collection 名 issues，1.8G |
| HNSW | 分层小世界图，近似最近邻的主流索引算法 | Chroma 底层使用；换 Milvus/pgvector 时也是同类算法 |
| 余弦相似度 | 两向量夹角的 cos 值，方向越一致越相似 | embedding 归一化后 cos=内积；现索引是 l2 遗留（只保序），重建后切显式 cosine |
| chunk | 长文档切出的片段，向量化的基本单位 | 三类：title chunk（必建）、error_log chunk（正则命中时）、body chunk（500 字符/重叠 80，<30 丢弃） |
| Top-K | 取排序结果前 K 条 | 向量/BM25 各 Top-30 → RRF Top-30 → 精排 Top-5（动态最多 10） |
| OOV | 词表外词：模型没见过的 token | 错误码/版本号对 embedding 模型近似 OOV，语义区分弱——BM25 补这一刀 |

## 融合与流程

| 术语 | 通用含义 | 在本项目里 |
| --- | --- | --- |
| RRF | 倒数排名融合：`Σ 1/(k+rank)`，只用排名不用分数 | k=60，用了**两层**：单 query 内融合向量+BM25；两条 query 之间再融合一次 |
| 混合检索 | 关键词检索 + 语义检索并用 | BM25（精确信号）+ 向量（语义信号），RRF 对等融合互为兜底 |
| 双路召回 | 同一请求用两个不同 query 各检索一遍再融合 | rewritten_query（改写主路）+ raw_issue（原文兜底路），防改写幻觉漏召回 |
| Query 改写 | 把口语输入转成适合检索的表达 | DeepSeek 产出 rewritten_query + keywords + component；解析失败回退原文 |
| docstore | 文档正文存储：id → 原文的 KV 库 | docstore.pkl（72M），id→{title, body 前 1200 字符}；融合后给 BM25-only 空正文候选补证据，只填空不覆盖 |
| Lost in the Middle | LLM 对长上下文中间部分注意力弱的现象 | 精排压到 Top-5 的动机之一：不给 Decision 塞 30 个候选 |
| LangGraph | 用图（节点+边+共享状态）编排 LLM 工作流的框架 | StateGraph 编排四节点 + should_retry 条件边；不是自主 Agent |
| State | LangGraph 各节点共享的数据容器 | IssueState（TypedDict，12 字段）；节点只返回增量，框架做 dict 合并 |
| 条件边 | 根据运行时状态决定下一个节点的边 | decision 后：confidence<0.7 且 retry_count≤2 → 回 query_analysis，否则 END |
| 幻觉 | LLM 编造不存在的内容 | 典型：related_issues 里编造 issue id——用候选白名单校验剔除 |
| 白名单校验 | 输出只允许取自预定义合法集合 | related_issues 必须 ⊆ 本轮 reranked 候选 id 集合；违反则过滤+降级 |
| 降级 | 出错时退到更保守的安全输出 | 无合法 id 的 duplicate → new + confidence≤0.4（故意低于 0.7 以触发重试） |
| prompt 注入 | 外部内容里藏指令试图操控 LLM | 候选 issue 正文是外部输入；防护=prompt 声明 + 输出白名单（缓解非根治） |
| 温度（temperature） | LLM 采样随机度，越低越确定 | 0.1：分类决策要一致性 |

## 评估

| 术语 | 通用含义 | 在本项目里 |
| --- | --- | --- |
| ground truth | 评估用的标准答案 | issue 的 duplicate_of 标注（它真正重复的目标 id 列表） |
| golden set | 带标准答案的评测集 | 8,599 条有效 query（13,104 条原始记录清洗后），eval 6,873 / test 1,726 |
| 可达性过滤 | 剔除"标准答案不在索引里"的无解评测题 | 清出 34% 无解 query——v1 指标被系统性低估的根源 |
| 自命中 | 评测 query 检索到它自己 | query 本身在索引里；检索 top_k+1 后剔除自身 id 再截断 |
| duplicate family | 由重复关系互相连通的一组 issue | 并查集把 query 和 ground truth 连成 3,333 个家族，划分以家族为最小单位 |
| 并查集 | 维护元素分组的经典数据结构（union/find） | 实现 family 合并：a→b、b→c 传递合并成一个家族 |
| 数据泄漏 | 测试信息以隐蔽方式进入训练/调参 | 家族跨侧=泄漏；时间穿越（检索到未来 issue）也是一种泄漏 |
| Recall@K | 前 K 条中命中的标准答案数 / 标准答案总数 | 主指标；Recall@30 = 召回层硬底线（实测 vector 0.48 / bm25 0.43） |
| Precision@K | 前 K 条中相关条数 / K | precision@5 看精排头部纯度 |
| MRR | 第一个命中排名的倒数（平均） | 实测 vector 0.27 ≈ 首个命中平均排第 4 |
| DCG / IDCG / nDCG | 按排名折扣累加的增益 / 理想值 / 两者之比 | IDCG 必须按 min(答案数, K) 算——v1 用已检索 gains 重排，命中 1 条就满分（已修） |
| P50 / P95 | 延迟中位数 / 95 分位 | vector 22ms/35ms；bm25 2.9s/49s（瓶颈实锤） |
| 消融实验 | 关掉单个组件对比，验证该组件的贡献 | 五组待跑：docstore/keywords/双路/0 分过滤/动态截断 |
| rescue / regression | 新方案救回的 case / 新方案反而搞砸的 case | dual_query benchmark 的核心对照指标（缺 verified 案例待跑） |
| 置信度校准 | 让自报置信度接近实际正确率 | 未做：confidence 只截断到 [0,1]；计划可靠性图+温度缩放 |
| 冒烟测试 | 最小化端到端跑通验证 | scripts/smoke_test.py：真索引+真模型+假 LLM，断言每步产物 |
| 时间穿越 | 评测时用到了"未来"数据 | 索引含晚于 query 的 issue；created_at 不在 metadata，修复需重建索引 |
| 增量索引 | 新数据不重建全量、直接追加进索引 | 未实现：新 issue 现在只能全量重建才能入库 |
| 词干化 | 把词还原为词干（crashes→crash） | 未做；jieba 对英文只切空格+小写，是 BM25 的隐性损失 |

### ✅ 自测

1. 用"双塔 vs Cross-Encoder"和"TF/IDF"各造一句话，说明它们在本项目的位置。
2. 可达性过滤、自命中、family 隔离——三个评估术语各对应哪类偏差？
3. rescue/regression 这对指标为什么比"平均 recall 提升"更能说明双路召回的价值？

---

## 自测答案

<details>
<summary>答案</summary>

1. 例："双塔（MiniLM）在召回层把 10 万条压到 Top-30，Cross-Encoder
   （bge-reranker）在精排层把 30 压到 5"；"错误码因为全库罕见所以 IDF 极高，
   keywords 追加相当于放大它的 TF，两个乘起来让 BM25 一命中就顶到前排"。
2. 可达性过滤→"无解题被算失败"的系统性低估；自命中→"查到自己"占位造成的排名
   失真；family 隔离→调参集与测试集互见近亲的泄漏性虚高。
3. 平均值会互相抵消：救回 10 条同时搞砸 8 条，平均只 +2 条看不出风险结构。
   rescue/regression 分开数，才能回答"双路是净收益还是高方差赌博"，以及
   regression 集中在哪类 case（是否可通过规则规避）。
</details>
