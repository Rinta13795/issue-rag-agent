## 1. 端到端三分类评估（最优先缺口）

**缺口**：系统最终输出是 duplicate/similar/new，但没有这一层的人工标注测试集，
现在说不出"分类准确率是多少"。

**建法**：
1. 从 test set 抽 150-300 条，人工标注三分类标签。duplicate_of 标注只能提供
   duplicate 正例；**similar/new 的边界必须人标**，这是最难也最有价值的部分；
2. 指标：三分类混淆矩阵 + 按类别 precision/recall；业务上最贵的两类错误单列——
   "真 duplicate 被判 new"（维护者白处理一遍）和"幻觉 duplicate"（误关 issue）；
3. related_issues 命中率：判为 duplicate/similar 时，标注目标是否出现在
   related_issues 里（retry benchmark 已有此指标实现雏形，缺数据）：

```python
# eval/benchmarks/retry_quality.py 中已实现的单条记录指标（节选）
"retrieval_hit": bool(expected_ids & set(reranked_ids)),      # 检索层命中
"related_issue_hit": bool(expected_ids & set(related_ids)),   # LLM 引用命中
"duplicate_decision_correct": (
    final.get("decision") == "duplicate"
    and bool(expected_ids & set(related_ids))                  # 判对且引用对
),
```

4. 成本指标同步记录：每条 LLM 调用次数、token 数、端到端延迟。

**前置条件（当前的现实约束）**：DeepSeek 账户余额为 0（实测 402），且旧 key 已
泄漏进 git 历史需作废轮换——充值/换 key 之前，一切含 LLM 的评估都做不了。

## 2. 置信度校准

**缺口**：confidence 是 LLM 自报值，0.8 不代表 80% 正确率；0.7 的重试阈值也是
拍的，没有数据支撑。

**建法**：有了三分类标注后——
1. 画可靠性图：按 confidence 分桶（如 0.1 一档）× 每桶实际准确率，算 ECE；
2. 系统性偏高/偏低时用温度缩放或等值回归校准；
3. 用校准后的曲线重新选重试阈值：目标是"重试触发的案例中，重试后变好的比例"
   最大化（当前 0.7 只是对齐了 prompt 里的置信度分档语义）。

## 3. 消融实验（v2 每项改进是否真有效）

方法：同一 golden set、同一 seed，开关单个组件对比。

| 消融项 | 对照 | 看什么指标 |
| --- | --- | --- |
| docstore 补齐 | hybrid_rerank 有/无 docstore | rerank 后 recall@5（BM25-only 候选能否被排上来） |
| keywords 进 BM25 | extra_terms 有/无 | bm25_only 的 recall/MRR |
| 双路召回 | search_queries vs 单 query | rescue/regression 率（benchmark 已写好） |
| 0 分过滤 | BM25_MIN_SCORE 开/关 | hybrid recall@30（确认无回退） |
| 动态截断 | 固定 Top-5 vs 动态 | rerank recall@10 与平均候选数 |

双路 benchmark 的核心对照逻辑（`eval/benchmarks/dual_query_retrieval.py` 节选）：

```python
# rescue：单路没命中、双路命中（双路救回来的）
retrieval_rescues = sum(
    not r["single_rewritten"]["retrieval_metrics"][metric]
    and r["dual_query"]["retrieval_metrics"][metric] for r in records)
# regression：单路命中、双路反而丢了（融合稀释造成的退化）
retrieval_regressions = sum(
    r["single_rewritten"]["retrieval_metrics"][metric]
    and not r["dual_query"]["retrieval_metrics"][metric] for r in records)
# 只统计人工确认过的案例：status != "verified" 的草稿不进正式结果
verified = [c for c in cases if c.get("status") == "verified"]
```

### ✅ 自测（缺口与建法）

1. 三分类评估里业务上最贵的两类错误是什么？为什么要单列？
2. "置信度校准"具体校什么？校准后能改进系统里的哪个具体参数？
3. 消融表里"docstore 是否有效"应该看哪个指标、为什么是它？

---

## 自测答案

<details>
<summary>答案</summary>

1. "真 duplicate 判成 new"（维护者重复劳动，系统价值归零）和"幻觉 duplicate"
   （可能导致误关 issue，伤害用户信任）。单列是因为总体 accuracy 会掩盖这两类
   高成本错误的占比，业务风险和平均错误率不是一回事。
2. 校"自报 confidence 与实际正确率的一致性"（画可靠性图、算 ECE，偏差大时温度
   缩放/等值回归）。直接改进 `CONFIDENCE_THRESHOLD=0.7`：用"重试后改善率"曲线
   把拍脑袋的阈值换成数据选的阈值。
3. 看 hybrid_rerank 的 rerank 后 recall@5（有/无 docstore 对照）。docstore 的
   作用机制是给 BM25-only 候选补正文、让 Cross-Encoder 能给它们打出真实分数——
   效果就应该体现在"这些候选能否进入精排 Top-5"，检索层 recall@30 不经过精排、
   体现不出补正文的价值。
</details>
