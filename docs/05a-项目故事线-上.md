## 一、两分钟项目介绍（逐字稿，直接背）

> 我做了一个 issue 查重系统，解决的是开源项目维护者的一个真实痛点：新 issue 进来，
> 很大比例是历史上报过的重复问题，但人工要在十几万条历史里找，一条要花好几分钟。
>
> 系统输入一条新 issue 的原始文本，输出三分类判断——duplicate、similar 还是 new，
> 附带置信度、相关历史 issue 的编号和判断理由。整个流程用 LangGraph 编排成四个
> 节点。第一步 Query 分析，用 DeepSeek 把口语化的 issue 改写成技术检索式，同时抽
> 关键词；第二步混合检索，这里我做了双保险——改写结果和原文各跑一路，每路里面
> BM25 负责错误码这类精确信号、向量负责语义相似，用 RRF 按排名融合，两路再融合
> 一次，取 Top-30；第三步用 Cross-Encoder 对这 30 条精排到 Top-5；第四步 LLM 基于
> 这 5 条候选做判断。判断置信度低于 0.7 时，系统会带着上一轮的诊断信息——比如
> 候选分差、缺证据数量、上轮 Top-3 候选——回到第一步重写 query，最多重试两次。
>
> 数据用的是 GitBugs 数据集，本地索引了十万零六千条 issue。工程上我比较看重两点：
> 一是输出可信——LLM 返回的相关 issue 编号会过一层候选白名单校验，保证绝不返回
> 编造的 id；二是评估可信——我自己踩过一个大坑，最初的评测集里 34% 的 query 的
> 标准答案根本不在索引里，我用可达性过滤、剔除自命中、按重复家族隔离划分把评测
> 体系重建了一遍，现在检索层的每个指标都有可复现的脚本支撑。
>
> 这个项目最大的收获是想清楚了一件事：RAG 系统的上限在检索层，而检索层的优化
> 必须先有一套可信的评估，否则所有调参都是自我感觉良好。

## 二、STAR 故事（1-2）

### 故事 1：评测集 34% 的题根本无解——重建评估体系

- **S（情境）**：检索链路搭完后我开始做量化评估，用数据集自带的 duplicate_of
  标注构建了一万三千条 query 的 golden set，跑出来的 recall 一直很难看，我一度
  以为是检索方案不行，反复调参数没有起色。
- **T（任务）**：搞清楚到底是检索差，还是"尺子"本身有问题。
- **A（行动）**：我停下调参，去人工抽查没召回的 case，发现相当一部分 query 的
  duplicate_of 指向的目标 issue 在索引里根本不存在——有的被清洗规则过滤了，有的
  数据集本身就缺。这种 query 无论检索多强都是零分。于是我给 golden set 构建器加
  了可达性校验：用 BM25 索引的 id 全集过滤每条 ground truth，剔除自引用和不可达
  目标，全部目标不可达的 query 整条丢弃；顺手修了另外两个坑——评测 query 自己就
  在索引里会自命中占位，检索时多取一条剔除自身；随机划分会把同一个重复家族拆到
  调参集和测试集两边造成泄漏，我用并查集把 query 和它的标注目标连成家族，以家族
  为单位做 80/20 划分。
- **R（结果）**：13,104 条原始 duplicate 记录里清出 4,505 条（34%）无解 query，
  之前的指标全部被系统性低估了约三分之一；清理后得到 8,599 条有效 query、3,333
  个家族，全部构建统计都随 golden set 一起落盘可复现。这件事之后我把"先验证尺子
  再优化"当成铁律。

targets = []
for target in issue["duplicate_of"]:
    target_id = str(target)
    if target_id == query_id:                 # 自引用是数据噪声
        stats["dropped_self_reference_targets"] += 1
        continue
    if target_id not in indexed_ids:          # 不可达：检索永远不可能命中
        stats["dropped_unreachable_targets"] += 1
        continue
    targets.append(target_id)
if not targets:                               # 全部不可达 -> 整条丢弃
    stats["dropped_no_reachable_target"] += 1
    continue

# family 隔离：并查集把 query 与 ground truth 连成家族，整族同侧划分
for query in golden:
    for target in query["duplicate_of"]:
        _union(parents, query["id"], target)
family_queries[_find_root(parents, query["id"])].append(query)
# 每个 project 内按家族 80/20 贪心装箱（seed=42），家族绝不跨侧

### 故事 2：白召回的候选——docstore 补证据

- **S**：v1 有个我在 README 里自己承认的已知限制：BM25 索引只存 id，只被 BM25
  召回、没被向量路命中的候选没有 title 和 body。往下游走，Reranker 对着空字符串
  打分，Decision 对着空字符串判断——这些候选等于白召回了。而错误码强匹配的候选
  恰恰最容易只被 BM25 召回，最有价值的一路信号在最后两步失效。
- **T**：让所有进入精排和决策的候选都带上正文证据，同时不能把向量路已有的
  "最相关 chunk"覆盖掉。
- **A**：评估了三个方案：正文塞进 bm25.pkl（耦合，加载变重）、在线反查 Chroma
  （30 次点查，且 Chroma 存的是 chunk 拼不回完整正文）、独立 docstore。选了第三
  个：离线用和建索引完全相同的清洗链路产出 id→{title, body 前 1200 字符} 的
  pickle，1200 是按下游需求定的——Reranker 只看 800、Decision 只看 400。在
  HybridRetriever 融合排序后统一补齐，规则是"只填空、不覆盖"，因为向量路的 body
  是命中的 chunk，是比正文开头更好的精排证据。docstore 缺失时自动退回旧行为，
  只降效果不崩服务。
- **R**：冒烟测试从"BM25-only 候选全空"变成 30/30 候选都有正文证据；配套单元测试
  锁住"补空不覆盖"的语义。

<details>
<summary>点开看核心代码（src/retrievers/hybrid_retriever.py 节选）</summary>

```python
def _hydrate(self, results: list[dict]) -> int:
    """只填空缺、不覆盖：向量路候选的 body 是与 query 最相关的 chunk。"""
    if not self.docstore:
        return 0                              # docstore 缺失 -> 退回 v1 行为
    hydrated = 0
    for doc in results:
        record = self.docstore.get(str(doc["id"]))
        if record is None:
            continue
        if not str(doc.get("title", "")).strip() and record.get("title"):
            doc["title"] = record["title"]
        if not str(doc.get("body", "")).strip() and record.get("body"):
            doc["body"] = record["body"]
            hydrated += 1
    return hydrated
```
</details>

   query 占比；0.7=触发重试的置信度阈值。
3. 检索层决定 RAG 上限，而优化检索的前提是先有可信评估（先验尺子再调参）。
