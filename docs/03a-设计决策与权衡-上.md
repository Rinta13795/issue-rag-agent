## 决策 1：混合检索（BM25 + 向量），而不是纯向量

- **决策是什么**：每个 query 同时走 BM25 关键词检索和向量语义检索，各取 Top-30，
  RRF 融合成一个候选列表。
- **为什么这么选**：issue 查重场景里两类信号缺一不可。
  ① 错误码、异常类名、函数名（如 `NullPointerException`、`MOZ_CRASH`）是**精确匹配
  信号**——BM25 对这类罕见 token 有天然的高 IDF 加权，向量模型反而会把不同错误码
  嵌到相近的位置；② "描述同一现象的不同说法"（"点登录就闪退" vs "crash on login
  button"）是**语义信号**，BM25 一个词都对不上，只有向量能召回。GitBugs 数据里两类
  duplicate 都真实存在。
- **考虑过的备选方案**：a) 纯向量；b) 纯 BM25；c) 向量召回 + BM25 只做过滤。
- **为什么放弃备选**：a) 纯向量对错误码/版本号这类 OOV 精确信号不敏感，且
  all-MiniLM 只有 384 维，区分细粒度技术术语能力有限；b) 纯 BM25 无法跨说法召回，
  同义改写直接漏；c) 过滤式组合有先后依赖，一路错全错——对等融合让两路互为兜底。
- **代价/局限**：BM25 全量打分是纯 Python（rank-bm25 库），106,656 条 issue 约
  2-5s/query，是在线延迟大头；两套索引要同步维护（同一批 clean 数据构建），
  存储翻倍（1.8G Chroma + 101M bm25.pkl）。

核心实现（`src/retrievers/hybrid_retriever.py`，单 query 的两路召回 + RRF 融合）：

```python
def search(self, query, top_k=HYBRID_TOP_K, filter_dict=None, bm25_extra_terms=None):
    # 向量检索可以使用 metadata filter，利用 component 等结构化信息缩小语义召回范围。
    vector_results = self.vector_retriever.search(
        query=query, top_k=top_k, filter_dict=filter_dict,
    )
    # BM25 不做预过滤，防止 component 判断错误时漏掉关键词强匹配的 duplicate。
    # keywords 作为补充 token 加强错误码、API 名等精确信号的权重。
    bm25_results = self.bm25_retriever.search(
        query=query, top_k=top_k, extra_terms=bm25_extra_terms,
    )

    # RRF 不做线性加权，因为 BM25 分数无上限、向量相似度约在 0-1，量纲不一致。
    rrf_scores: dict[str, float] = defaultdict(float)
    issue_docs: dict[str, dict] = {}

    # 第一遍融合向量结果：保存完整 issue 信息，并按排名累加 RRF 分。
    for rank, doc in enumerate(vector_results, start=1):
        issue_id = doc["id"]
        rrf_scores[issue_id] += 1.0 / (RRF_K + rank)          # RRF_K = 60
        issue_docs[issue_id] = {
            "id": issue_id, "title": doc.get("title", ""),
            "body": doc.get("body", ""), "metadata": doc.get("metadata", {}),
        }

    # 第二遍融合 BM25 结果：BM25 只有 id/score，先占位，融合后由 docstore 补齐正文。
    for rank, doc in enumerate(bm25_results, start=1):
        issue_id = doc["id"]
        rrf_scores[issue_id] += 1.0 / (RRF_K + rank)
        if issue_id not in issue_docs:
            issue_docs[issue_id] = {"id": issue_id, "title": "", "body": "", "metadata": {}}

    # 按 RRF 分数降序，两路都靠前的 issue 自然胜出。
    ranked_ids = sorted(rrf_scores, key=lambda i: -rrf_scores[i])[:top_k]
    results = []
    for issue_id in ranked_ids:
        result = issue_docs[issue_id].copy()
        result["score"] = rrf_scores[issue_id]
        results.append(result)

    hydrated = self._hydrate(results)   # docstore 补齐空正文候选（见决策 4）
    return results
```

## 决策 2：RRF 融合，而不是加权分数融合

- **决策是什么**：两路结果只用**排名**融合：`score(d) = Σ 1/(k + rank_d)`，k=60
  （代码即上方决策 1 代码块中的两个 `rrf_scores[issue_id] += 1.0/(RRF_K + rank)`
  循环）。多 query 场景再做一层同公式的外层 RRF（代码见 03b 决策 8）。
- **为什么这么选**：两路分数**量纲完全不可比**——BM25 分数无上界（长 query 能打到
  几十分），向量相似度在 0-1 之间。线性加权 `α·bm25 + (1-α)·cos` 必须先归一化再调 α，
  而 BM25 的 min-max 归一化对 query 长度极其敏感，α 也没有标注数据可调。RRF 只看
  排名，天然免疫量纲问题，k=60 是 Cormack 2009 在 TREC 上验证的经验值，不需要调参。
- **考虑过的备选方案**：a) 归一化后线性加权；b) 训练 LTR（learning-to-rank）模型；
  c) 两路取并集直接交给 Reranker。
- **为什么放弃备选**：a) 归一化方式本身就是新超参，且没有验证集可调（做这个项目时
  连可信 golden set 都还没有）；b) LTR 需要标注的相关性数据和特征工程，冷启动做不了；
  c) 并集不排序会让 60 个候选全进 Cross-Encoder，精排延迟直接翻倍，而 RRF 的"两路
  共识排前"本身就是有效的粗排。
- **代价/局限**：RRF 丢掉了分数的绝对信息——BM25 第 1 名是 50 分还是 0.5 分，RRF
  眼里都是 1/61；极端情况下"一路非常确定"的信号被平均化。这个损失由下游
  Cross-Encoder 重打分兜底。

## 决策 3：本地小模型 Embedding（all-MiniLM-L6-v2），而不是 API 或大模型

- **决策是什么**：用 sentence-transformers 的 all-MiniLM-L6-v2（384 维）本地 CPU
  跑 embedding，归一化后走 cosine。
- **为什么这么选**：① 建库要对 10 万+ issue 的约 30 万个 chunk 全量向量化，走 API
  百万级 token 的费用和限流都不可控，本地模型零成本可重跑；② 数据集全英文，MiniLM
  在英文 STS 任务上性价比高；③ 384 维让 1.8G 的 Chroma 存储和检索延迟都减半
  （对比 768 维模型）；④ 离线可用。
- **考虑过的备选方案**：a) OpenAI/其他 embedding API；b) bge-large 等 768/1024 维
  大模型；c) 曾经用过 bge-small-zh-v1.5（v1 早期，中文模型）。
- **为什么放弃备选**：a) 费用+限流+网络依赖，且数据出境合规存疑；b) CPU 上建库时间
  数倍增长，Mac 内存压力大，召回层的精度损失可以由 Reranker 补（两阶段设计的意义
  就在这）；c) 数据集实际全英文，中文模型是早期误选，v1 后期已换（配置注释记录了
  这次纠错）。
- **代价/局限**：MiniLM 对长文本和代码片段的表征弱；384 维天花板明显——所以召回层
  只求"进 Top-30"，精度交给 Cross-Encoder。换更强 embedding 需要全量重建索引
  （数小时 CPU）。

## 决策 4：单独建 docstore，而不是把正文塞进 BM25 索引或查 Chroma

- **决策是什么**：独立文件 `docstore.pkl`（issue_id → {title, body 前 1200 字符}），
  检索融合后只给"缺正文的候选"补齐（只填空、不覆盖）。
- **为什么这么选**：v1 的最大已知缺陷是——bm25.pkl 只存 id 和倒排结构，**只被 BM25
  召回的候选没有 title/body**，Reranker 对它打分、Decision 对它判断时拿到的是空字符
  串，等于这些候选"白召回了"。修复要点是给候选补正文，而正文的唯一权威来源是清洗后
  的 issue 数据，所以独立建一份 id→正文映射最直接。
- **考虑过的备选方案**：a) 把正文直接存进 bm25.pkl；b) 在线时按 issue_id 反查
  Chroma；c) 不补，让 Reranker 只对有正文的候选打分。
- **为什么放弃备选**：a) bm25.pkl 已 101MB，塞正文后每次加载 BM25 都被迫连正文一起
  加载，职责耦合，且换 BM25 实现（如 ES）时正文逻辑跟着重写；b) Chroma 按 metadata
  反查 30 个候选要 30 次 `get`，且 Chroma 存的是 chunk 不是完整正文，拼回 issue 还要
  聚合；c) 等于系统性歧视 BM25-only 候选——恰恰错误码强匹配的候选最可能只被 BM25
  召回。冒烟实测补齐后 30/30 候选都有正文证据。
- **代价/局限**：多一份 72MB 资产要与索引同步重建（构建脚本把它和 golden set 合并成
  一次预处理产出）；正文截 1200 字符，超长 issue 的后段信息丢失（够用：下游 Rerank
  只看 800、Decision 只看 400）；docstore 缺失时静默退回 v1 行为，是柔性降级但也
  意味着忘了建就悄悄变弱。

核心实现（`src/docstore.py` 构建 + `src/retrievers/hybrid_retriever.py` 补齐）：

```python
# src/docstore.py —— 离线构建：与建索引同一批清洗后 issue
def build_docstore(issues, path=DOCSTORE_PATH, body_max_chars=DOCSTORE_BODY_MAX_CHARS):
    store = {
        str(issue["id"]): {
            "title": str(issue.get("title", "")),
            "body": str(issue.get("body", ""))[:body_max_chars],   # 1200 字符封顶
        }
        for issue in issues
    }
    with Path(path).open("wb") as file:
        pickle.dump(store, file)
    return store

def load_docstore(path=DOCSTORE_PATH) -> dict:
    # 文件不存在时返回空字典而不是抛异常：docstore 是证据增强，不是检索的硬依赖；
    # 缺失时系统退回 v1 行为（BM25-only 候选无正文），只损失效果不损失可用性。
    if not Path(path).exists():
        return {}
    with Path(path).open("rb") as file:
        return pickle.load(file)

# src/retrievers/hybrid_retriever.py —— 在线补齐：融合排序后调用
def _hydrate(self, results: list[dict]) -> int:
    """为缺少 title/body 的候选从 docstore 补齐正文，返回补齐数量。
    只填空缺、不覆盖：向量路候选的 body 是与 query 最相关的 chunk，
    对 Reranker 是比"正文开头 N 字符"更好的证据，保留原值。"""
    if not self.docstore:
        return 0
    hydrated = 0
    for doc in results:
        record = self.docstore.get(str(doc["id"]))
        if record is None:
            continue
        changed = False
        if not str(doc.get("title", "")).strip() and record.get("title"):
            doc["title"] = record["title"]; changed = True
        if not str(doc.get("body", "")).strip() and record.get("body"):
            doc["body"] = record["body"]; changed = True
        if changed:
            hydrated += 1
    return hydrated
```

## 决策 5：加 Cross-Encoder Reranker，而不是召回分直接排序

- **决策是什么**：RRF Top-30 之后用 bge-reranker-base 对 (query, 候选) 逐对精排，
  取 Top-5（分差近时最多扩到 10）再交给 LLM。
- **为什么这么选**：两阶段是"算力分配"问题。召回层（双塔向量 + BM25）为了能在
  10 万级语料上跑，query 和 doc 各自独立编码，**互相看不见对方**，精度天花板低；
  Cross-Encoder 把 query 和 doc 拼在一起过同一个 BERT，每层 attention 都在做
  token 级交互比对，精度高但一对一对算——只可能用在小候选集上。30 → 5 正是
  "贵模型只算 30 对"的设计点。另一个动机是保护 LLM：给 Decision 塞 30 个候选，
  prompt 超长且真答案容易淹没在中间（Lost in the Middle），Top-5 让 LLM 的比对
  任务变简单。
- **考虑过的备选方案**：a) 直接按 RRF 分取 Top-5 给 LLM；b) 让 LLM 自己从 30 个
  候选里挑（跳过精排）；c) 用更大的 reranker（bge-reranker-large）。
- **为什么放弃备选**：a) RRF 分是排名共识不是相关性度量，Top-5 截断误伤率高；
  b) LLM 读 30 个候选的成本比 Cross-Encoder 贵一个量级，且长上下文比对可靠性差；
  c) large 版 CPU 上单轮多花数秒，base 版精度已够"从 30 里挑出前 5"这个难度的任务。
- **代价/局限**：CPU 上 30 对约 1-3 秒；输入截 800 字符，候选核心证据若在正文后段
  会打分失真；分数不是概率，只能比大小（所以诊断里的 top_score/score_gap 只当
  相对线索用）。

核心实现（`src/reranker.py`）：

```python
def rerank(self, query, docs, top_k=RERANK_TOP_K, dynamic_threshold=DYNAMIC_THRESHOLD_DIFF):
    if not docs:
        return []
    # 先浅拷贝每个 doc 再写入 rerank_score：v1 直接原地修改调用方传入的列表，
    # 导致 State 中 retrieved_docs 被悄悄污染。
    scored_docs = [doc.copy() for doc in docs]

    pairs = []
    for doc in scored_docs:
        # pair 格式是 (query, title + body)，让 CrossEncoder 同时看查询和候选 issue。
        text = f"{doc.get('title', '')}\n{doc.get('body', '')}"
        # 截断 800 字符：BERT 最大输入约 512 token，不截断可能被底层不一致截断。
        pairs.append((query, text[:RERANK_DOC_MAX_CHARS]))

    scores = self.model.predict(pairs)        # bge-reranker-base 一次批量打分
    for doc, score in zip(scored_docs, scores):
        doc["rerank_score"] = float(score)

    sorted_docs = sorted(scored_docs, key=lambda item: -item["rerank_score"])
    cut = min(top_k, len(sorted_docs))        # 默认 Top-5

    # 动态阈值扩展：TopK 和 TopK+1 分数很接近时，避免武断截断漏掉真正 duplicate。
    max_cut = min(len(sorted_docs), top_k + RERANK_MAX_EXTRA_DOCS)   # 最多扩到 10
    while cut < max_cut:
        score_gap = sorted_docs[cut - 1]["rerank_score"] - sorted_docs[cut]["rerank_score"]
        if score_gap < dynamic_threshold:     # 分差 < 0.05 就继续放宽
            cut += 1
        else:
            break
    return sorted_docs[:cut]
```

## 自测答案

<details>
<summary>决策 1-3 答案</summary>

1. BM25 的 IDF 项让全库罕见的 token 权重极高，错误码正是低频精确 token，一命中
   排名就上去；向量模型反而会把不同错误码嵌到相近位置（都是"错误"语义），
   区分度不足。
2. `score(d) = Σ_每路 1/(k + rank_d)`，k=60。k 调小→头部排名分差被放大，单路
   第一名容易独大；k 调大→各排名趋于平权，头部优势被抹平。
3. 成本：建库时间（CPU 数倍）、存储（1.8G→约 3.6G）、检索延迟（维度翻倍）。
   收益替代：召回层精度不足由第二阶段 Cross-Encoder 精排弥补，所以召回层只需
   "把答案带进 Top-30"。
</details>

<details>
<summary>决策 4-5 答案</summary>

4. 向量路候选的 body 是"命中的那个 chunk"——与 query 最相关的片段，是精排的
   最佳证据；覆盖成 docstore 的"正文前 1200 字符"会把最相关片段换成开头，
   Reranker 打分质量下降。
5. 双塔：query/doc 独立编码互不可见，文档向量可预计算建索引，所以能扛大规模；
   交叉编码：两者拼接后逐层 attention 交互，必须每对现算，无法预计算，只能小
   候选集精排。
6. 解决"真答案恰好排第 6 被武断切掉"的边界问题。阈值调到 1.0 后分差几乎永远
   小于它，每次都扩到上限 10 条，等于 RERANK_TOP_K=10，Decision 的 prompt
   变长、动态截断失去意义。
</details>
