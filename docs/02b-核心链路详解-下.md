## 三、精排与决策（步骤 3-4）

### 步骤 3：Rerank（Cross-Encoder 精排）

- **输入**：`rewritten_query` + Top-30 `retrieved_docs`。
- **处理**：组 (query, title+body 截 800 字符) 对 → bge-reranker-base 批量打分 →
  降序取 Top-5，分差 < 0.05 时动态扩展最多到 Top-10。
- **输出**：`reranked_docs`（5-10 条，每条带 `rerank_score`）。

```python
# src/reranker.py
def rerank(self, query, docs, top_k=RERANK_TOP_K, dynamic_threshold=DYNAMIC_THRESHOLD_DIFF):
    if not docs:
        return []
    # 先浅拷贝再打分：v1 原地写 rerank_score 会污染 State 里的 retrieved_docs。
    scored_docs = [doc.copy() for doc in docs]

    pairs = []
    for doc in scored_docs:
        text = f"{doc.get('title', '')}\n{doc.get('body', '')}"
        pairs.append((query, text[:RERANK_DOC_MAX_CHARS]))    # 800 字符，BERT 512 token 限制

    scores = self.model.predict(pairs)         # Cross-Encoder：query 和 doc 同一 BERT 内交互
    for doc, score in zip(scored_docs, scores):
        doc["rerank_score"] = float(score)

    sorted_docs = sorted(scored_docs, key=lambda item: -item["rerank_score"])
    cut = min(top_k, len(sorted_docs))          # 默认 Top-5
    max_cut = min(len(sorted_docs), top_k + RERANK_MAX_EXTRA_DOCS)   # 最多 Top-10
    while cut < max_cut:                        # 动态扩展：边界分差太小就继续放宽
        score_gap = sorted_docs[cut - 1]["rerank_score"] - sorted_docs[cut]["rerank_score"]
        if score_gap < dynamic_threshold:       # 0.05
            cut += 1
        else:
            break
    return sorted_docs[:cut]
```

### 步骤 4：Decision（LLM 判断 + 程序校验）

- **输入**：`rewritten_query`、`keywords`、`reranked_docs`。
- **处理**：候选格式化（每条展示 id、rerank_score、title、body 前 400 字符）→
  调 DeepSeek 三分类 → 解析 → **程序级校验** → 写重试历史。
- **输出**：`decision, confidence, related_issues, reasoning, retry_count, previous_decisions`。

程序级校验（v2 核心新增；解析失败先落到 `fallback = new/0.0`）：

```python
# 1. 枚举校验：不在 ("duplicate","similar","new") 里按解析失败处理。
decision = parsed.get("decision", "new")
if decision not in VALID_DECISIONS:
    decision = "new"
    parsed["confidence"] = 0.0

# 2. confidence 强转 + 截断 [0,1]。
try:
    confidence = float(parsed.get("confidence", 0.0))
except (TypeError, ValueError):
    confidence = 0.0
confidence = min(max(confidence, 0.0), 1.0)

# 3. related_issues 白名单：只保留本轮 reranked 候选中真实存在的 id。
candidate_ids = {str(doc.get("id", "")) for doc in state["reranked_docs"]}
related_issues = [str(i) for i in related_issues if str(i) in candidate_ids]

# 4. duplicate/similar 却无合法 id：结论没有可核查证据 -> 降级 new + 压低置信度，
#    0.4 < 0.7 会在重试预算内自动触发新一轮。
if decision in ("duplicate", "similar") and not related_issues:
    decision = "new"
    confidence = min(confidence, 0.4)
    reasoning = f"{reasoning}（原判断引用的 issue ID 未通过候选白名单校验，已降级）"
```

## 四、回环、输出与超参数（步骤 5 + 参数表）

### 步骤 5：should_retry 与最终输出

```python
# src/agent/graph.py
def should_retry(state: IssueState) -> str:
    if state["confidence"] < CONFIDENCE_THRESHOLD and state["retry_count"] <= MAX_RETRIES:
        return "retry"     # 回到 query_analysis 重跑一整轮
    return "end"
# 图上：graph.add_conditional_edges("decision", should_retry,
#                                   {"retry": "query_analysis", "end": END})
```

retry_count 语义：**Decision 节点累计执行轮数**（在 Decision 里先 +1 再判断），
正常首轮结束 =1，持续低置信度最多 3 整轮后强制结束。`run_agent` 最终只返回
decision / confidence / related_issues / reasoning / retry_count 五个字段。

### 关键超参数全表（全部集中在 `config.py`）

| 参数 | 当前值 | 含义 | 为什么是这个值 | 调大会怎样 | 调小会怎样 |
| --- | --- | --- | --- | --- | --- |
| `LLM_TEMPERATURE` | 0.1 | LLM 采样温度 | 分类决策要一致性不要创意 | 输出波动大、复跑不稳 | 0 也可，略失改写多样性 |
| `LLM_MAX_TOKENS` | 1024 | 单次输出上限 | JSON 输出很短，足够 | 浪费 | 太小 JSON 被截断→解析失败兜底 |
| `LLM_TIMEOUT` | 60s | 请求超时 | 网络异常不能无限阻塞 | 故障时挂更久 | 慢响应被误杀 |
| `LLM_MAX_RETRIES` | 2 | 客户端自动重试 | 兜瞬时限流/超时 | 故障时延迟放大 | 瞬时错误直接失败 |
| `EMBED_MODEL` | all-MiniLM-L6-v2 | embedding 模型 | 英文数据、CPU 可跑、384 维省一半存储 | — | — |
| `CHUNK_SIZE` | 500 | body 切分长度 | 约一个段落；平衡语义完整与向量稀释 | 单 chunk 语义混杂 | chunk 数暴涨、上下文碎片化 |
| `CHUNK_OVERLAP` | 80 | 切分重叠 | 约 16%，保住边界句子 | 索引冗余 | 边界语义被切断 |
| `VECTOR_TOP_K` | 30 | 向量路召回数 | 召回层要覆盖，K=5 会漏真 duplicate | 噪声进 RRF、精排变慢 | 召回上限下降 |
| `VECTOR_CHUNK_FETCH_MULTIPLIER` | 2 | chunk 多召倍率 | 多 chunk 聚合会吃名额，先召 60 再聚合 | 查询变慢 | 聚合后不足 30 个 issue |
| `BM25_TOP_K` | 30 | BM25 路召回数 | 与向量对等，RRF 才有共识空间 | 低分噪声 | 关键词强匹配被截断 |
| `BM25_MIN_SCORE` | 0.0（严格大于） | BM25 最低分 | 0 分=无词命中，占 RRF 配额没意义 | 弱匹配也被扔（慎） | 无效（已是下界） |
| `RRF_K` | 60 | RRF 平滑常数 | Cormack 2009 经验值 | 头部排名优势变弱 | 头名分差过大，单路独大 |
| `HYBRID_TOP_K` | 30 | 融合后保留数 | 交给 Rerank 的候选池 | Rerank 变慢 | 融合层砍掉可救回的候选 |
| `RERANK_TOP_K` | 5 | 精排保留数 | 控 prompt 长度，防 Lost in the Middle | LLM 注意力稀释 | 真答案排第 6 被砍（动态扩展兜这个） |
| `RERANK_DOC_MAX_CHARS` | 800 | 精排输入截断 | BERT 512 token 限制 | 被模型内部不一致截断 | 证据不足打分失真 |
| `DYNAMIC_THRESHOLD_DIFF` | 0.05 | 动态扩展分差阈值 | Top5/6 分数几乎一样时不武断砍 | 几乎总扩到 10 | 动态扩展形同虚设 |
| `RERANK_MAX_EXTRA_DOCS` | 5 | 最多额外扩展 | 扩展上限 Top-10，护 prompt 长度 | prompt 失控 | 同左互补 |
| `CONFIDENCE_THRESHOLD` | 0.7 | 重试触发阈值 | 对应 prompt 置信度分档（0.7+=核心症状一致） | 大量案例反复重试 | 低质量判断直接放行 |
| `MAX_RETRIES` | 2 | 最大回环次数 | 防死循环，封顶 3 轮延迟费用 | 长尾延迟不可控 | 重写机制失去意义 |
| `DECISION_BODY_PREVIEW_CHARS` | 400 | Decision 候选正文展示 | docstore 补齐后可给更多证据（v1 是 200） | prompt 成本上升 | 证据不足误判 new |
| `RETRY_TOP_CANDIDATES` | 3 | 重试展示上轮候选数 | 反思要有具体对象 | prompt 变长收益递减 | 反思缺依据 |
| `DOCSTORE_BODY_MAX_CHARS` | 1200 | docstore 正文截断 | 覆盖 Rerank 800 + Decision 400 | 文件变大（现 72MB） | Rerank 输入吃不满 |
| `INDEX_BATCH_SIZE` | 500 | Chroma 批写大小 | 全量一次写会 OOM | 内存压力 | 建库更慢 |
| `EVAL_SEED` / `EVAL_SAMPLE_SIZE` | 42 / 200 | 抽样种子/量 | 可复现；200 条趋势已稳 | 更准更慢 | 方差变大 |

### 单轮时间都花在哪（实测，Mac CPU）

| 阶段 | 耗时 | 说明 |

## 自测答案

<details>
<summary>步骤 3-4 答案</summary>

1. 因为要往候选 dict 里写 rerank_score。不拷贝会原地修改 State 里的
   retrieved_docs（v1 真实 bug）——下游看 retrieved_docs 时发现它被偷偷加了字段，
   benchmark 还得自己防御性 copy。
2. 枚举防"类别乱写"；截断防"置信度超界"；白名单防"编造 issue id"；降级规则防
   "无证据的 duplicate 结论"。第 4 条主动触发重试：降级时把 confidence 压到
   ≤0.4，低于 0.7 阈值，只要 retry_count 还在预算内就自动回到 Query Analysis。
3. score_gap 小说明候选区分度低，重试改写应补充"能区分候选"的信号；
   missing_evidence_count 高说明很多候选没正文（docstore 缺失/未命中），提示
   改写不要基于"候选内容"过度推断。
</details>

<details>
<summary>步骤 5 + 超参答案</summary>

4. retry_count = Decision 节点累计执行轮数（每轮 Decision 里先 +1）。首轮结束 =1；
   判断条件是 `retry_count <= 2`，所以 1、2 都能触发重试，第 3 轮结束时 3<=2 不
   成立强制终止——"最多重试 2 次"+"首轮"= 最多 3 整轮。
5. BM25 纯 Python 全库打分（2-5s）。并发化只能把"vector 20ms + bm25 3s"变成
   "max(20ms, 3s)"，省的是小头；把 BM25 换成倒排引擎（ES/Tantivy）才是把 3s 变
   几十 ms 的根治方案。
6. 更多案例落入"低置信度"区间→重试率上升，延迟和 LLM 费用最多 ×3 的案例变多；
   收益是放行的判断更保守可靠。反之调低则几乎不重试，低质量判断直接输出。
</details>
