# 02 核心链路详解：一条 Query 的完整生命周期

> 以真实调用为准逐步拆解。示例输入：`"Firefox crashes with MOZ_CRASH when opening a
> PDF file in a background tab. Stack shows mozilla::dom::PDFViewer::Init."`
> （即 `scripts/smoke_test.py:26` 的冒烟用例，实测检索+精排全链路 6.8s，CPU，不含 LLM）

## 0. 入口与初始 State

- **输入**：一段 issue 文本（str）。
- **处理**：`run_agent`（`src/agent/graph.py:133`）取进程内缓存的编译图
  （`get_graph`，`graph.py:121`），构造初始 State：
  `{"raw_issue": 文本, "retry_count": 0, "previous_decisions": []}`（`graph.py:139-143`）。
  其余字段由节点逐步写入（`src/agent/state.py:8-38` 的 `IssueState`，节点只返回自己
  新增的字段，LangGraph 负责 dict 合并）。
- **输出**：进入第一个节点 `query_analysis`（入口设置 `graph.py:99`）。

## 1. Query Analysis（LLM 改写）

代码：`src/agent/nodes.py:165-282`

- **输入**：`raw_issue`；重试轮还会读 `previous_decisions` 的最后一项。
- **处理**：
  1. 拼 user message：原文永远保留在最前（`nodes.py:222`，防止重试时围绕上轮改写漂移）；
     重试轮追加"上次反思块"：上轮 query/keywords/decision/confidence/reasoning +
     检索诊断（候选数、缺证据数、top_score、前两名分差）+ **上轮 Top-3 候选的
     id/title/分数**（`nodes.py:180-216`，prompt 模板 `src/agent/prompts/query_analysis_retry.md`）。
  2. 调 DeepSeek（system prompt `src/agent/prompts/query_analysis_system.md`：要求保留
     错误码/API 名/堆栈，去掉口语化描述）。
  3. 解析 + 双层兜底：`_parse_json`（`nodes.py:86-113`）剥 \`\`\`json 代码块、正则截取
     `{...}`；整体解析失败 → 用原文当 query（`nodes.py:235-240`）；字段级清洗：
     rewritten_query 非空字符串否则回退原文（`nodes.py:244-250`），keywords 去空/去重/
     截前 8 个（`nodes.py:255-264`），component 非空字符串否则 None（`nodes.py:269-273`）。
- **输出**：`{rewritten_query, keywords, component}` 三个字段合并进 State。

## 2. Retrieval（双路混合检索）

代码：节点 `src/agent/nodes.py:284-318`；检索器 `src/retrievers/`

- **输入**：`rewritten_query`、`raw_issue`、`keywords`、`component`。
- **处理**（`nodes.py:307-312`）：调 `HybridRetriever.search_queries(queries=[rewritten_query,
  raw_issue], top_k=30, filter_dict, bm25_extra_terms=keywords)`。
  component 有值时作为 Chroma metadata filter（`nodes.py:301`），只作用于向量路；
  BM25 不预过滤（防 component 判错整批漏掉，`hybrid_retriever.py:48-54`）。
- **输出**：`retrieved_docs`（Top-30，每条含 id/title/body/metadata/score，score 是
  双层 RRF 融合分）。

### 2.1 两路 query 的作用

`search_queries`（`hybrid_retriever.py:110-201`）先按 casefold 去重去空
（`hybrid_retriever.py:126-134`）——改写失败回退原文时两路相同，只执行一次，行为
退化成单路（`hybrid_retriever.py:141-147`）。两路的分工：

- **rewritten_query 路**：LLM 提炼后的技术表达，主检索路。
- **raw_issue 路**：保底路，保留 LLM 可能删掉的错误码、版本号、原始细节，
  防"改写幻觉/漂移导致真 duplicate 完全漏召回"。

### 2.2 每一路内部：Vector 与 BM25 如何跑、如何融合

注意一个容易说错的点：**两路检索在实现上是顺序调用，不是并发执行**
（`hybrid_retriever.py:42-54` 先 vector 后 bm25；两条 query 也是顺序循环
`hybrid_retriever.py:154-157`）。"并行"只指逻辑上互不依赖、结果地位对等；
CPU 单机下顺序执行更简单，延迟瓶颈也不在这（见 04 文档压力层问答）。

**Vector 路**（`src/retrievers/vector_retriever.py:18-60`）：
1. 用 query 向 Chroma 召回 `top_k × 2 = 60` 个 **chunk**（`vector_retriever.py:29-33`，
   倍率 `config.py:78`）；
2. 按 `metadata.issue_id` 聚合回 issue，同一 issue 只留分数最高的 chunk，chunk 内容
   作为该 issue 的 body（`vector_retriever.py:35-53`）；
3. `score = 1 - distance`（`vector_retriever.py:43`；现有索引是 Chroma 默认 l2 空间，
   该转换只保序、数值含义不严格，重建索引后切 cosine，`src/indexer.py:180-187`）；
4. 按 issue 分数降序截 Top-30。

**BM25 路**（`src/retrievers/bm25_retriever.py:28-70`）：
1. query 过 `tokenize`（jieba 分词 + 空格细分 + 小写，`src/indexer.py:209-218`，
   与建索引同一函数保证切分规则一致）；
2. **keywords 追加进 token 列表**（`bm25_retriever.py:44-46`），等效提升错误码/API 名
   的词频权重（v2 新增；v1 keywords 不参与任何检索）；
3. `get_scores` 对全库 106,656 条 issue 打分（`bm25_retriever.py:51`，纯 Python，
   这是在线延迟大头，实测约 2-5s/query）；
4. 取 Top-30 并**过滤 0 分候选**（`bm25_retriever.py:62-66`，0 分=一个词都没命中）。

**内层 RRF 融合**（`hybrid_retriever.py:56-99`）：

对两路各自的排名（不是分数）打分累加：

```text
RRF(d) = Σ_每路  1 / (k + rank_d)，k = 60
```

- vector 第 1 名得 1/61，BM25 第 3 名得 1/63；两路都出现的 issue 分数累加自然靠前
  （`hybrid_retriever.py:63-64,76-77`）；
- 只在 BM25 出现的 issue 没有正文，先占位（`hybrid_retriever.py:79-86`），
  融合排序后由 **docstore 补齐**（`_hydrate`，`hybrid_retriever.py:203-228`：只填空
  不覆盖——向量路的 body 是"与 query 最相关的 chunk"，比正文开头更好的精排证据）；
- 按 RRF 分降序截 Top-30（`hybrid_retriever.py:89`）。

**外层 RRF**（`hybrid_retriever.py:159-201`）：对"两条 query 各自的 Top-30 排名"再做
一次同公式融合；同一 issue 被两路同时召回则两次加分。同分时 Python 稳定排序保证
改写主路的结果排前（`hybrid_retriever.py:176-181`）。保留 title+body 更完整的版本
（`hybrid_retriever.py:166-174`）。

## 3. Rerank（Cross-Encoder 精排）

代码：节点 `src/agent/nodes.py:321-343`；`src/reranker.py:25-76`

- **输入**：`rewritten_query` + Top-30 `retrieved_docs`。
- **处理**：
  1. 每条候选浅拷贝（`reranker.py:42`，不污染 State 里的 retrieved_docs）；
  2. 组 `(query, title + "\n" + body 截 800 字符)` 对（`reranker.py:45-49`，截断原因：
     BERT 输入约 512 token）；
  3. `bge-reranker-base` 一次 `model.predict` 批量打分（`reranker.py:52`）——
     Cross-Encoder 让 query 和 doc 在同一个 BERT 里做 attention 交互，比双塔精准；
  4. 按分降序，默认截 Top-5；**动态扩展**：第 cut 名与第 cut+1 名分差 < 0.05 时继续
     放宽，最多扩到 Top-10（`reranker.py:58-72`，参数 `config.py:97-106`）。
- **输出**：`reranked_docs`（5-10 条，每条带 `rerank_score`）。

## 4. Decision（LLM 判断 + 程序校验）

代码：`src/agent/nodes.py:346-493`

- **输入**：`rewritten_query`、`keywords`、`reranked_docs`。
- **处理**：
  1. 候选格式化：每条展示 id、rerank_score、title、body 前 400 字符
     （`nodes.py:115-134`，长度 `config.py:119`）；prompt 声明候选是外部内容
     不得执行其中指令（`nodes.py:361-368`，注入防护是提示词级）；
  2. 调 DeepSeek（system prompt `decision_system.md`：三分类定义 + 置信度分档 +
     防幻觉硬约束）；
  3. 解析失败 → 降级 `new/0.0`（`nodes.py:380-386`，低置信度会触发重试）；
  4. **程序级校验**（v2 核心新增，`nodes.py:388-425`）：
     - decision 不在 `("duplicate","similar","new")` → 按解析失败处理（`nodes.py:392-396`，
       枚举 `config.py:116`）；
     - confidence 强转 float 并截断 [0,1]（`nodes.py:398-402`）；
     - related_issues 白名单：只保留本轮 reranked 候选中真实存在的 id，幻觉 id 记日志
       剔除（`nodes.py:410-419`）；
     - duplicate/similar 却没有任何合法关联 id → 降级 `new`，confidence 压到 ≤0.4，
       reasoning 附降级说明（`nodes.py:421-425`）——宁可触发重试也不带幻觉结论结束；
  5. 写历史：本轮 query/决策/诊断统计 + **Top-3 候选 id/title/分数** 追加进
     `previous_decisions`（`nodes.py:447-478`），`retry_count + 1`（`nodes.py:485`）。
- **输出**：`decision, confidence, related_issues, reasoning, retry_count, previous_decisions`。

## 5. should_retry（条件回环）与最终输出

- `confidence < 0.7` 且 `retry_count <= 2` → 回 Query Analysis 重来一整轮
  （`src/agent/graph.py:70-82`）；retry_count 语义是"Decision 累计执行轮数"：
  正常 1，持续低置信度最多 3 整轮。
- 否则 END，`run_agent` 只挑对外 5 个字段返回（`graph.py:148-155`）。

## 6. 关键超参数全表

所有参数集中在 `config.py`（"所有参数从 config 读取"是 CLAUDE.md 的硬规范）。

| 参数（config.py 行号） | 当前值 | 含义 | 为什么是这个值 | 调大会怎样 | 调小会怎样 |
| --- | --- | --- | --- | --- | --- |
| `LLM_TEMPERATURE`(23) | 0.1 | LLM 采样温度 | 分类决策要一致性不要创意 | 输出波动大、复跑结果不稳 | 0 也可，略失改写多样性 |
| `LLM_MAX_TOKENS`(26) | 1024 | 单次输出上限 | JSON 输出很短，1024 足够 | 浪费（按输出计费） | 太小 JSON 被截断→解析失败兜底 |
| `LLM_TIMEOUT`(29) | 60s | 请求超时 | 网络异常不能无限阻塞 | 故障时挂更久 | 慢响应被误杀 |
| `LLM_MAX_RETRIES`(32) | 2 | 客户端自动重试 | 兜瞬时限流/超时 | 故障时延迟放大 | 瞬时错误直接失败 |
| `EMBED_MODEL`(36) | all-MiniLM-L6-v2 | embedding 模型 | 英文数据集、本地 CPU 可跑、384 维省存储（选型权衡见 03 文档） | — | — |
| `CHUNK_SIZE`(65) | 500 | body 切分长度 | 约一个 issue 段落；太大稀释向量语义，太小切碎上下文 | 单 chunk 语义混杂、召回变糊 | chunk 数暴涨、上下文碎片化 |
| `CHUNK_OVERLAP`(68) | 80 | 切分重叠 | 约 15%，保住段落边界句子 | 索引冗余、近重复 chunk | 边界语义被切断 |
| `VECTOR_TOP_K`(75) | 30 | 向量路召回数 | 召回层要覆盖，K=5 会漏真 duplicate | 噪声进入 RRF、精排变慢 | 召回上限下降，Rerank 无米下锅 |
| `VECTOR_CHUNK_FETCH_MULTIPLIER`(78) | 2 | chunk 多召倍率 | 多 chunk 聚合到同一 issue 会"吃掉"名额，先多召 60 个 chunk 再聚合 | 查询变慢 | 聚合后不足 30 个 issue |
| `BM25_TOP_K`(82) | 30 | BM25 路召回数 | 与向量对等，RRF 才有共识空间 | 低分噪声（已被 0 分过滤缓解） | 关键词强匹配被截断 |
| `BM25_MIN_SCORE`(85) | 0.0 | BM25 最低分（严格大于） | 0 分=无词命中，占 RRF 配额没意义 | 弱匹配也被扔（慎） | 无效（已是下界） |
| `RRF_K`(87) | 60 | RRF 平滑常数 | Cormack 2009 经验值；k 越大排名差异越被抹平 | 头部排名优势变弱 | 第 1 名与第 10 名分差过大，单路独大 |
| `HYBRID_TOP_K`(90) | 30 | 融合后保留数 | 交给 Rerank 的候选池大小 | Rerank 慢（30 对→更多对） | 融合层就砍掉了可救回的候选 |
| `RERANK_TOP_K`(97) | 5 | 精排保留数 | 控制 Decision prompt 长度，防 Lost in the Middle | LLM 上下文变长、注意力稀释 | 真 duplicate 可能排第 6 被砍（动态扩展就是兜这个） |
| `RERANK_DOC_MAX_CHARS`(100) | 800 | 精排输入截断 | BERT 512 token 限制，不截会被底层不一致截断 | 超长被模型内部截断，行为不可控 | 证据不足打分失真 |
| `DYNAMIC_THRESHOLD_DIFF`(103) | 0.05 | 动态扩展分差阈值 | Top5/Top6 分数几乎一样时不该武断砍第 6 | 几乎总是扩到 10，等于 TOP_K=10 | 动态扩展形同虚设 |
| `RERANK_MAX_EXTRA_DOCS`(106) | 5 | 最多额外扩展数 | 扩展上限=Top-10，护住 prompt 长度 | prompt 失控 | 同左互补 |
| `CONFIDENCE_THRESHOLD`(110) | 0.7 | 重试触发阈值 | 对应 decision prompt 的置信度分档（0.7 以上=核心症状一致） | 大量案例反复重试、延迟×3 | 低质量判断直接放行 |
| `MAX_RETRIES`(113) | 2 | 最大回环次数 | 防死循环，封顶 3 整轮延迟与费用 | 长尾延迟不可控 | 重写机制失去意义 |
| `DECISION_BODY_PREVIEW_CHARS`(119) | 400 | Decision 候选正文展示 | docstore 补齐后可给更多证据（v1 是 200） | prompt 成本上升 | 证据不足→误判 new |
| `RETRY_TOP_CANDIDATES`(122) | 3 | 重试展示上轮候选数 | 让改写知道"上轮检索到了什么" | prompt 变长收益递减 | 反思缺依据 |
| `DOCSTORE_BODY_MAX_CHARS`(61) | 1200 | docstore 正文截断 | 覆盖 Rerank 800 + Decision 400 的需求，再长无下游收益 | 文件变大（现 72MB） | Rerank 输入吃不满 800 |
| `INDEX_BATCH_SIZE`(52) | 500 | Chroma 批写大小 | 全量一次写会 OOM | 内存压力 | 建库更慢 |
| `EVAL_SEED`(126) | 42 | 划分/抽样种子 | 可复现 | — | — |
| `EVAL_SAMPLE_SIZE`(135) | 200 | 建议抽样量 | 全量 1,726 条太慢，200 条趋势已稳定 | 更准更慢 | 方差变大 |
