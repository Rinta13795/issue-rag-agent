## 1. 评测集（Golden Set）怎么来的

数据集自带 ground truth：`resolution=duplicate` 且 `duplicate_of` 非空的 issue，
其标注目标就是标准答案。但直接用会产生系统性偏差，构建器做了四层处理：

1. **与建索引同链路预处理**：`clean([normalize(x) for x in load_data()])`，
   保证评测 query 的文本形态和索引一致（v1 漏了 normalize）；
2. **可达性过滤**：ground truth 必须存在于当前索引（用 bm25.pkl 的 id 全集校验）；
   剔除自引用目标；全部目标不可达的 query 丢弃；
3. **duplicate family 隔离划分**：并查集把 query 与标注目标连成家族，同一家族
   整体进 eval 或 test，杜绝"调参集见过 A→B、测试集又考 B→A"的泄漏；
4. **project 分层 + 固定 seed=42**：每个项目内部按家族 80/20 贪心装箱，构建统计
   随文件落盘。

核心实现（`eval/golden_set_builder.py` 节选）：

```python
def load_indexed_ids(bm25_path=BM25_INDEX_PATH) -> set[str]:
    """BM25 和 Chroma 由同一批 clean issue 构建，用 BM25 的 id 列表代表
    "检索系统可达的 issue 全集"，加载成本远低于扫描 Chroma。"""
    with Path(bm25_path).open("rb") as file:
        data = pickle.load(file)
    return {str(i) for i in data["ids"]}

# 逐条清理 ground truth：自引用剔除、不可达剔除、全不可达整条丢弃
targets = []
for target in issue["duplicate_of"]:
    target_id = str(target)
    if target_id == query_id:
        stats["dropped_self_reference_targets"] += 1; continue
    if target_id not in indexed_ids:
        stats["dropped_unreachable_targets"] += 1; continue
    targets.append(target_id)
if not targets:
    stats["dropped_no_reachable_target"] += 1; continue

# 并查集 family：query 与其全部 ground truth 连通
```

## 2. 评估怎么跑 + 指标定义

`eval/run_eval.py` 对四个配置在 **held-out test set** 上评估：vector_only /
bm25_only / hybrid / hybrid_rerank。两条公平性规则：

```python
def _exclude_self(retrieved, query_id, top_k):
    """评测 query 本身也在索引中，检索到自己不算能力：
    检索 top_k+1 条，剔除自身 id 后再截断，否则自命中挤占一个候选位置。"""
    ids = [str(d["id"]) for d in retrieved if str(d["id"]) != str(query_id)]
    return ids[:top_k]

RERANK_CUTOFFS = (5, 10)        # Rerank 输出最多 10 条：不与 30 条配置比 recall@30
RETRIEVAL_CUTOFFS = (5, 10, 30)
```

抽样规则：`--limit N` 固定 seed=42 随机抽样；样本量、抽样方式、自命中标记全部写
进结果 JSON 的 `_meta`，报表打印时先展示元信息，防止抽样结果被当成全量引用。

指标定义（`eval/metrics.py`）：

| 指标 | 定义 | 用途 |
| --- | --- | --- |
| Recall@K | 命中的 ground truth 数 / ground truth 总数 | 召回硬底线；@30 = "Rerank 有没有米下锅" |
| Precision@5 | Top-5 中相关数 / 5 | 精排头部纯度 |
| MRR | 首个命中排名的倒数 | 第一个答案排多前 |
| nDCG@10 | DCG / IDCG | 多答案时的整体排序质量 |
| P50/P95 延迟 | 单 query 检索耗时分位数 | 在线可行性 |

nDCG 的 IDCG 是 v2 修过的 bug，正确实现：

```python
def ndcg_at_k(retrieved_ids, golden_ids, k):
    golden_set = set(golden_ids)
    gains = [1.0 if rid in golden_set else 0.0 for rid in retrieved_ids[:k]]
    dcg = sum(g / np.log2(i + 2) for i, g in enumerate(gains))
    # 关键修复：IDCG 按"全部相关目标数"计算（min(len(golden), k) 个理想命中），
    # v1 用"已检索到的 gains 重排"当理想序——命中 1 条就满分，漏检不进分母，数值虚高。
    ideal_hit_count = min(len(golden_set), k)
    idcg = sum(1.0 / np.log2(i + 2) for i in range(ideal_hit_count))
    return dcg / idcg if idcg > 0 else 0.0
```

**已能得出的结论**：
- 纯向量把约一半 query 的答案带进 Top-30，MRR 0.27 ≈ 首个命中平均排第 4——
  这正是需要 Rerank 的证据；
- 向量在全部质量指标上略优于 BM25，但两者召回的是**不同的子集**（这正是混合
  检索的动机，融合收益待 hybrid 数字确认）；
- 延迟差距悬殊：向量 p50=22ms vs BM25 p50=2.9s、p95=49s——BM25 纯 Python 全量
  打分是系统的绝对延迟瓶颈（长 query 分词后 token 多，最坏近 1 分钟）。

## 自测答案

<details>
<summary>评测集答案</summary>

1. BM25 和 Chroma 由同一批 clean issue 构建，id 全集等价；bm25.pkl 一次 load 即得
   全部 id，扫 Chroma 要遍历几十万 chunk 的 metadata，慢且没必要。
2. 防"同一 duplicate family 的成员分属 eval/test 两侧"——调参时见过 A→B，测试
   又考 B→A，test 指标虚高。用并查集（union-find，带路径压缩）把 query 和
   ground truth 连成连通分量。
3. 可达性过滤影响最大：34% 的 query 被清除，方向是**提升**全部指标（v1 把无解题
   全算 0 分，系统性低估约 1/3）。
</details>

<details>
<summary>评估执行答案</summary>

4. 检索 top_k+1 条，过滤掉与 query id 相同的结果再截断到 top_k。不剔除：自己
   几乎永远排第 1，挤占一个名额且把真目标整体往后推，Recall/MRR/nDCG 全部失真。
5. v1 把"已检索到的 gains 降序排列"当理想序：若 golden 有 2 个目标只命中 1 个，
   DCG=1/log2(2)=1，v1 的 IDCG 也只有这 1 个 gain=1，nDCG=1.0 满分；正确算法
   IDCG=1/log2(2)+1/log2(3)≈1.63，nDCG≈0.61。
6. ① 召回上限：向量 Top-30 只带回 48% 的答案，召回层是第一优化点；② 排序质量：
   MRR≈0.27 说明命中时平均排第 4，需要精排；③ 延迟：BM25（p50 2.9s / p95 49s）
   是绝对瓶颈，向量检索（22ms）可忽略。
</details>
