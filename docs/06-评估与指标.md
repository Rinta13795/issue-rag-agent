# 06 评估与指标

> 本文分两部分：当前已建成并实际运行的评估体系（含实测数字）；以及尚未覆盖的
> 层面应该怎么建。所有数字来自 `eval_results/`，运行方式可复现。

## 1. 当前评估体系

### 1.1 评测集（Golden Set）怎么来的

数据集自带 ground truth：`resolution=duplicate` 且 `duplicate_of` 非空的 issue，
其标注目标就是标准答案。但直接用会产生系统性偏差，构建器
（`eval/golden_set_builder.py:56-179`）做了四层处理：

1. **与建索引同链路预处理**：`clean([normalize(x) for x in load_data()])`
   （`golden_set_builder.py:211-215`），保证评测 query 的文本形态和索引一致；
2. **可达性过滤**：ground truth 必须存在于当前索引（用 bm25.pkl 的 id 全集校验，
   `golden_set_builder.py:27-35`）；剔除自引用目标；全部目标不可达的 query 丢弃；
3. **duplicate family 隔离划分**：并查集把 query 与标注目标连成家族
   （`golden_set_builder.py:38-53,120-137`），同一家族整体进 eval 或 test，
   杜绝"调参集见过 A→B、测试集又考 B→A"的泄漏；
4. **project 分层 + 固定 seed**：每个项目内部按家族 80/20 贪心装箱
   （`golden_set_builder.py:139-170`），seed=42，构建统计随文件落盘。

**实际构建结果**（2026-07-26，`eval/data/golden_set.json` 的 `build_stats`）：

| 统计项 | 数值 |
| --- | --- |
| 输入 issue | 106,656 |
| 原始 duplicate 记录 | 13,104 |
| 无任何可达目标而丢弃的 query | 4,505（34.4%） |
| 被剔除的不可达目标 id | 6,114 |
| 被剔除的自引用目标 | 4 |
| 有效 query | 8,599 |
| duplicate family 数 | 3,333 |
| eval set / test set | 6,873 / 1,726 |

> 34% 这个数字是本项目最重要的评估教训：v1 直接把这些无解 query 计为检索失败，
> 全部指标被系统性低估约三分之一。

### 1.2 评估怎么跑

`eval/run_eval.py` 对四个配置在 **held-out test set** 上评估：

| 配置 | 内容 | 截断点 |
| --- | --- | --- |
| vector_only | 纯向量（chunk 召回聚合到 issue） | @5/@10/@30 |
| bm25_only | 纯 BM25（0 分候选过滤） | @5/@10/@30 |
| hybrid | 双索引 + RRF 融合（含 docstore 补齐） | @5/@10/@30 |
| hybrid_rerank | hybrid + Cross-Encoder 精排 Top-5（动态扩展至 10） | **仅 @5/@10** |

两条公平性规则（`run_eval.py:69-77,90-124`）：
- **自命中剔除**：评测 query 自身在索引里，检索 `top_k+1` 条后剔除自身 id 再截断；
- **公平截断**：Rerank 输出最多 10 条，不与 30 条配置比 recall@30
  （`RERANK_CUTOFFS=(5,10)`，`run_eval.py:51`）。

抽样规则：`--limit N` 用固定 seed=42 随机抽样（`run_eval.py:127-131`），样本量、
抽样方式、自命中标记全部写进结果 JSON 的 `_meta`，`eval/report.py` 打印时先展示
元信息，防止抽样结果被当成全量引用。

### 1.3 指标定义（`eval/metrics.py`）

| 指标 | 定义 | 用途 |
| --- | --- | --- |
| Recall@K | 命中的 ground truth 数 / ground truth 总数（K 截断） | 召回层硬底线；Recall@30 是"Rerank 有没有米下锅" |
| Precision@5 | Top-5 中相关数 / 5 | 精排头部纯度 |
| MRR | 首个命中排名的倒数 | "第一个答案排多前"，对应用户看到第几条 |
| nDCG@10 | DCG / IDCG，**IDCG 按 min(相关数, 10) 个理想命中计算**（`metrics.py:31-47`） | 多答案时的整体排序质量 |
| P50/P95 延迟 | 单 query 检索耗时分位数 | 在线可行性 |

> nDCG 的 IDCG 计算是 v2 修过的 bug：v1 用"已检索到的 gains 重排"当理想序，
> 命中 1 条就得满分，漏检目标不进分母，数值虚高。回归测试
> `tests/test_metrics.py` 锁住了正确行为。

## 2. 尚未覆盖的评估层面与建法

### 2.1 端到端三分类评估（最优先）

**缺口**：系统最终输出是 duplicate/similar/new，但没有这一层的人工标注测试集，
现在说不出"分类准确率是多少"。

**建法**：
1. 从 test set 抽 150-300 条，人工标注三分类标签（duplicate_of 标注只能提供
   duplicate 正例；similar/new 的边界必须人标，这是最难也最有价值的部分）；
2. 指标：三分类混淆矩阵 + 按类别的 precision/recall；业务上最贵的错误是
   "真 duplicate 被判 new"（维护者白处理一遍）和"幻觉 duplicate"（误关 issue），
   分别单列；
3. related_issues 命中率：判为 duplicate/similar 时，标注目标是否出现在
   related_issues 里（`eval/benchmarks/retry_quality.py:98-107` 已有此指标的
   实现雏形，缺数据）；
4. 成本指标同步记录：每条 LLM 调用次数、token 数、端到端延迟。

### 2.2 置信度校准

**缺口**：confidence 是 LLM 自报值，0.8 不代表 80% 正确率；0.7 的重试阈值也是
拍的，没有数据支撑。

**建法**：有了 2.1 的标注后，画可靠性图（按 confidence 分桶 × 实际准确率），算
ECE；如果系统性偏高/偏低，用温度缩放或等值回归校准；再用校准后的曲线重新选
重试阈值（目标：重试触发的案例中"重试后变好"的比例最大化）。

### 2.3 消融实验（改进是否真有效）

每项 v2 改进都应有 A/B 数字，方法：同一 golden set、同一 seed，开关单个组件：

| 消融项 | 对照 | 看什么指标 |
| --- | --- | --- |
| docstore 补齐 | hybrid_rerank 有/无 docstore | rerank 后 recall@5（BM25-only 候选能否被正确排上来） |
| keywords 进 BM25 | extra_terms 有/无 | bm25_only 的 recall/MRR |
| 双路召回 | search_queries vs 单 query | rescue/regression 率（benchmark 已写好） |
| 0 分过滤 | BM25_MIN_SCORE 0 vs 关闭 | hybrid recall@30（确认无回退） |
| 动态截断 | 固定 Top-5 vs 动态 | rerank recall@10 与平均候选数 |

### 2.4 线上持续评估（如果部署）

- 人工分诊结果回流当标注（维护者最终怎么处理了这条 issue）；
- 监控三条曲线：duplicate 判定率、平均 confidence、重试率——分布漂移是数据或
  模型退化的早期信号；
- 抽样人审：每周抽 N 条高置信 duplicate 复核，守住"误关 issue"这条红线。

## 3. 复现命令

```bash
python scripts/build_eval_assets.py        # 重建 docstore + golden set（约 3 分钟）
python -m eval.run_eval --limit 200        # 抽样评估（约 40-60 分钟，CPU）
python -m eval.run_eval                    # 全量 1,726 条（数小时，CPU）
python -m eval.report                      # 打印对比表（含元信息）
python -m pytest tests/ -q                 # 32 个单元测试
python scripts/smoke_test.py               # 端到端冒烟（不花钱）
```
