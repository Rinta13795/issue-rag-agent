# 04a 面试问答手册（上）：基础层 + 深挖层前半（Q1-Q16）

## 📌 项目速览（每个文档都重复，便于单独阅读）

Issue 查重系统：新 issue 提交后，在 106,714 条历史 issue（GitBugs 数据集，8 个开源项目）里找重复，输出 duplicate / similar / new 三分类 + 置信度 + 相关 issue 编号 + 判断理由。在线流程是 LangGraph 四节点：LLM 改写 query → 双路混合检索（BM25 + 向量各 Top-30，双层 RRF 融合，docstore 补齐正文）→ Cross-Encoder 精排 Top-5 → LLM 决策 + 程序级校验；置信度 < 0.7 且未超 2 次重试时带诊断回环重写。技术栈：Python、LangGraph、DeepSeek、ChromaDB（all-MiniLM-L6-v2，384 维）、rank-bm25、bge-reranker-base、FastAPI。

> 答案是口语化逐字稿风格，可以直接说出口。涉及数字全部来自本项目实测：golden set
> 8,599 条有效 query；vector_only 抽样 200 条实测 recall@30=0.48、MRR=0.27、
> p50=22ms。下篇（04b）是深挖层后半 + 压力层 + 一句话弹药。

## 基础层

### Q1 用一分钟介绍一下这个项目

> 这是一个 issue 查重系统。大型开源项目每天进来很多新 issue，其中相当比例其实是
> 报过的重复问题，维护者要在十几万条历史里人工找，很费时间。我的系统接收一条新
> issue 文本，先用 LLM 把它改写成适合检索的技术 query，然后 BM25 和向量检索双路
> 召回历史候选、用 RRF 融合成 Top-30，再用 Cross-Encoder 精排到 Top-5，最后 LLM
> 对这 5 个候选做判断，输出 duplicate、similar 还是 new，带置信度、相关 issue 编号
> 和理由。置信度低的时候系统会带着诊断信息回去重写 query 再来一轮，最多三轮。
> 数据用的是 GitBugs 数据集，本地建了十万零六千多条 issue 的索引。

### Q2 这个项目解决的核心问题是什么？

> 本质是把"人在十几万条历史里找重复"压缩成"人只看 5 条候选加一个判断建议"。
> 关键难点有两个：一是召回要全——真正的重复用词可能完全不一样；二是结论要可信
> ——给维护者的相关 issue 编号必须真实存在，不能是模型编的。所以架构上召回层
> 做宽（双路混合、Top-30），判断层做严（Cross-Encoder 精排加 LLM 判断，再加一层
> 程序校验，保证返回的每个 id 都在候选白名单里）。

### Q3 为什么叫 RAG？生成的部分在哪？

> 检索部分是标准 RAG 的 R：混合检索加重排。生成部分不是生成一篇文章，而是生成
> 结构化判断——decision、confidence、reasoning。也可以更准确地说这是"检索增强
> 的分类决策"：LLM 的判断完全建立在检索回来的候选证据上，prompt 里明确要求
> reasoning 必须引用具体候选的特征，比如"编号 042 的堆栈和新 issue 完全一致"。

### Q4 整体架构分几块？

> 两大块。离线索引：原始数据经过字段标准化和清洗后，切 chunk 做向量进 ChromaDB，
> 整条 issue 分词建 BM25 倒排，另外存一份 id 到正文的 docstore 用来给候选补证据；
> 同一批数据还会产出评测用的 golden set。在线查询：LangGraph 编排四个节点——
> Query 改写、混合检索、精排、决策，决策后有一条条件边，置信度低于 0.7 且没超过
> 重试上限就回到第一个节点重来。

### Q5 为什么用 LangGraph 而不是直接写函数调用？

> 说实话这个规模用普通函数链也能写。选 LangGraph 主要三个原因：一是它的共享
> State 加节点返回增量合并的模式，正好匹配"重试时部分字段覆盖、历史字段追加"的
> 需求，不用手写状态管理；二是条件边把"低置信度回环"表达得很清晰；三是我也想
> 通过主流编排框架的方式来做，方便以后加节点。但我会明确说：它不是自主 Agent，
> 是条件工作流，流程是我定死的，LLM 没有决定"下一步做什么"的权力。

### Q6 数据是什么样的？规模多大？

> GitBugs 数据集，我本地快照有 106,714 条 issue，来自 Firefox、Cassandra 等 8 个
> 项目，带 duplicate_of 标注可以当 ground truth。清洗后 106,656 条，切完 chunk
> 向量库 1.8G，BM25 索引 101M，docstore 72M。其中约 1.3 万条被标为 duplicate，
> 这部分抽出来构建评测集。

### Q7 输出是什么？调用方怎么用？

> 一个 dict：decision 三选一、confidence 零到一、related_issues 列表、reasoning、
> 还有 retry_count 表示跑了几轮。接入方式有三种：Python 直接调 run_agent，命令行
> main.py，还有 FastAPI 的 POST /triage 接口。对维护者的预期用法是：duplicate 高
> 置信就直接去看关联 issue，similar 就把候选列表当参考，new 就正常分诊。

### Q8 这个项目你做了多久？哪部分最花时间？

> （按实际情况说。）最花时间的其实不是搭链路，是让评估可信——我后来发现最初的
> 评测集里 34% 的 query 的标准答案根本不在索引里，等于三分之一的题无解，之前测
> 的指标全部要推翻重来。这个故事可以展开讲（见 05 文档故事 1）。

## 深挖层（前半）

### Q9 RRF 的原理和公式？为什么 k=60？

> 公式是对每个文档，把它在每一路结果里的排名代进 1/(k+rank) 求和，我用 k=60。
> 直觉是：只看排名不看分数，两路都排前面的文档加分两次自然靠前，只在一路出现的
> 也不会被丢掉。k 是平滑常数，控制头部排名的优势有多大——k 很小的话第 1 名和第
> 10 名分差巨大，一路独大；k 很大所有排名趋于平权。60 是 Cormack 2009 年论文在
> TREC 上验证的经验值，我没有标注数据可以调它，就直接用了公认默认值。我的实现
> 里 RRF 用了两层：每条 query 内部融合向量和 BM25，两条 query 之间再融合一次。

### Q10 为什么不把 BM25 分数和向量分数归一化之后加权融合？

> 量纲问题。BM25 分数没有上界，query 越长分越高；余弦相似度在 0 到 1。要加权就
> 得先归一化，但 min-max 归一化对每次检索的分数分布很敏感，同一个文档换个 query
> 归出来的值完全不同；而且权重 α 需要验证集去调，我做这块的时候连可信的评测集都
> 还没建好。RRF 只用排名，把这两个问题都绕开了，代价是丢掉分数的绝对置信信息，
> 这个损失我用后面的 Cross-Encoder 重打分补回来。

### Q11 BM25 的原理讲一下？

> BM25 是词频统计模型，一个词对文档的贡献等于 TF 项乘 IDF 项。TF 项有饱和设计
> ——词出现 10 次不会比 5 次贡献翻倍，由 k1 控制；还有文档长度归一化，长文档被
> 惩罚，由 b 控制，我用的库默认 k1=1.5、b=0.75。IDF 让罕见词权重高，这正是它适合
> 错误码检索的原因：NullPointerException 这种 token 在十万条里出现次数少，IDF 高，
> 一命中排名就上去。我的实现是 issue 粒度建索引，title 加 body 合并后用 jieba 分词
> 再小写化，查询时必须用同一个分词函数，不然词都对不上。

### Q12 向量检索的原理？你的向量是怎么建的？

> 把文本经过 sentence-transformer 编码成 384 维向量，归一化之后余弦相似度就是
> 内积，Chroma 里用 HNSW 图做近似最近邻。建库时我不是一条 issue 一个向量，而是
> 切成三类 chunk：标题单独一个，错误堆栈用正则切出来单独一个，剩下的正文按 500
> 字符递归切。检索时先多召一倍 chunk，再按 issue_id 聚合，同一条 issue 取最高分
> chunk 当代表。这样短标题、堆栈、描述各自有干净的向量，不会互相稀释。

### Q13 Embedding 模型和 Reranker 模型有什么本质区别？

> 结构上都是 BERT 类，用法完全不同。Embedding 是双塔：query 和文档各自独立编码
> 成向量，线上只算向量距离，文档向量可以提前算好建索引，所以能扛十万级候选——
> 代价是两边编码时互相看不见，精度有天花板。Reranker 是交叉编码：query 和文档拼
> 成一条输入过同一个 BERT，每层 attention 都在做 token 级别的交互比对，能看出
> "错误码一样但触发条件不同"这种细粒度差异——代价是没法预计算，一对候选算一次，
> 只能用在小集合上。所以架构是召回用双塔扛量，精排用交叉编码保准。

### Q14 为什么一定要两阶段？只用 Cross-Encoder 不行吗？

> 算不动。Cross-Encoder 对每个候选都要跑一次完整 BERT 前向，十万条候选就是十万
> 次前向，CPU 上一条 query 要跑几个小时。反过来只用召回层精度又不够。两阶段本质
> 是算力分配：便宜的模型把十万压到三十，贵的模型只算三十对。这也是工业界搜索
> 推荐的标准分层。

### Q15 你的 chunk 策略为什么这么设计？500 和 80 怎么定的？

> 三类 chunk 的动机是 issue 的三种信号性质不同：标题是人写的最强摘要，堆栈是
> 精确匹配信号，正文是语义描述——混在一起嵌入会互相稀释，比如一条长 issue 的
> 向量会把错误码信息平均掉。500 字符大概是一个段落的量，是"语义完整"和"向量不
> 糊"的折中；重叠 80 大概 16%，保住被切断的边界句子。小于 30 字符的碎片直接丢，
> 减少索引噪声。坦白说 500 和 80 没有做过网格搜索验证，是按经验定的，评估体系
> 建好之后这是可以拿数据调的点。

### Q16 RRF 之后为什么还要 Reranker？它俩不重复吗？

> 不重复，解决的问题不同。RRF 是"两路召回怎么公平合并"的问题，它只有排名信息，
> 完全不看内容；Reranker 是"合并后的 30 条里哪个真相关"的问题，它逐字读内容。
> 打个比方，RRF 是按两个评委的名次汇总，Reranker 是主评委把前 30 名叫过来重新
> 面试一遍。我还做了个动态截断：默认取 Top-5，但第 5 名和第 6 名分差小于 0.05
> 就继续往后放，最多到 10——避免真答案恰好卡在第 6 被武断切掉。

<summary>深挖层前半答案要点</summary>

4. `score(d) = Σ_每路 1/(k + rank_d)`，k=60。k 小→头部优势放大、单路易独大；
   k 大→排名趋于平权、共识信号变弱。
5. TF 饱和：词重复出现收益递减（k1 控制）；IDF：全库罕见词权重高。错误码是
   低频精确 token，IDF 极高，一命中就顶到前排。
6. 双塔：独立编码可预计算、扛大规模 → 用在向量召回（MiniLM + Chroma）；
   交叉编码：拼接输入逐层交互、精度高但逐对现算 → 用在 Top-30 精排
   （bge-reranker-base）。
