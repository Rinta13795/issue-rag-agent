# 04c 面试问答手册（专题）：为什么需要 AI、Harness 与 Agent 基础题

## 📌 项目速览

项目有两块。**单次分诊**：LangGraph 固定四节点（改写查询、混合检索、重排、决策），低置信度走条件边回环，流程由程序写死。**对话调查**：在此基础上扩展，模型从 6 个工具里自己选下一步（搜 Issue、读 Issue、读 PR、搜 PR、起草 Issue、向用户提问），循环是手写的，每轮最多 6 次模型调用、10 次工具调用。项目是先做固定流程、后扩展成对话调查，不是一开始就设计成两层。

> 答案是口语稿，可以直接说。数字口诀：**6 个工具，6 次模型，10 次工具**。

## Q1 为什么需要 AI，不是传统程序？为什么不直接用 Claude Code / Codex？

> 这个问题我自己也想过。我先说结论：不是所有地方都需要 AI，我是按"确定的交给程序，不确定的交给模型"来分的。
>
> 比如单次分诊，流程是固定的，我就直接用程序写死，不让模型自由发挥。
>
> 真正需要模型的有两个地方。第一个是语义匹配，因为不同用户描述同一个问题，说法可能完全不一样，光靠关键词会漏，所以我用了向量检索；但是错误码、版本号这种又要精确匹配，所以我同时保留了关键词检索，两路融合。第二个是追问的时候，用户问"这个怎么解决"，下一步做什么要看读到的内容，比如评论里提到的那个 PR，到底是真的修好了，还是只是相关，这个没法提前写成 if else，所以我让模型来决定下一步。
>
> 那你可能会问，为什么不直接用 Claude Code 或者 Codex。我的理解是，通用 Agent 加个命令行，大概能做到七八成，这个我不否认。我自己做的区别在于，我可以管模型外面那一层程序，也就是 Harness。
>
> 具体有三点。第一，我管它的范围：只给它六个工具，而且一个对话只能读当前这一个仓库。第二，我管它的预算：每一轮模型最多调用六次，工具最多调用十次，防止它一直循环。第三，我管它的校验：最后回答里引用的资料，必须是它真正读过的；而且"PR 说修复了"和"用户自己验证有效"我是严格区分的，不会把前者当成后者。
>
> 这些边界我都是用替身模型做的离线测试，每次改完代码跑一遍就能确认没被改坏。所以总的来说，通用 Agent 权限更宽，我自己做的更希望做到可控、可验证。

**追问：有对比数据吗？**
> 这个我还没有做，是我自己识别出来的一个不足。我打算拿几个真实的 Issue，分别用通用 Agent 和我的系统跑一遍，对比耗时、动作，还有有没有越界，先做定性的对比。

**追问：什么叫替身模型？**
> 就是测试的时候不真的调用大模型，而是用一个按剧本回答的假模型。比如我让它故意编造一个没读过的引用，然后看我的程序会不会把它丢掉。这样测的是我这层程序能不能挡住模型出错，而且不花钱、结果也稳定。

**不要说**："我的 Agent 更灵活 / 比通用 Agent 更好"（没有数据）；把精排当亮点（实测精排没有提升）。

## Q2 COT、ReAct、Agent 是什么关系？

> 我是这么理解的，这三个是一层套一层的。COT 是让模型先一步一步推理，再给结论，它只是"想"，不和外界交互。ReAct 在这个基础上加了"做"和"看"：模型想一步，调用一个工具，看到结果，再接着想，循环到能回答为止，它解决的是 COT 光在脑子里推、没有外部信息容易编造的问题。Agent 是更大的概念，核心循环通常就是 ReAct，再加上工具、记忆、预算限制这些，也就是我说的 Harness。
>
> 放到我的项目里：单次分诊是预先定好的流程，算工作流，不是 Agent。我的对话调查是个 ReAct 循环，模型决定调哪个工具，工具返回结果，它再决定下一步，最多六轮，到了预算就必须总结回答。

注意：循环用的是模型原生的工具调用，不是论文里输出"Thought / Action"文字的格式，被问到如实说。

## Q3 LangGraph 的 State 是干什么的？

> State 可以理解成整个流程共享的一块"黑板"。每个节点从里面读自己需要的数据，算完只返回自己更新的那部分，框架把它合并回去，这样节点之间不用互相传参，也互不依赖。
>
> 在我的项目里是 IssueState，里面有原始 Issue、改写后的查询、检索结果、决策和置信度这些字段，四个节点各写各的。低置信度重试时，中间结果会被新一轮覆盖，但上一轮的决策要保留，所以我用 previous_decisions 这个列表，每轮追加一条，下一轮的提示词会带上它。

注意：previous_decisions 是在节点里手动复制再追加的，没用 LangGraph 的 reducer，被追问如实答。

## Q4 LangChain 和 LangGraph 的区别？

> LangChain 更像一套零件：模型接口、提示词、工具、检索器、输出解析这些，可以拼成一条线性的链。
>
> LangGraph 解决的是另一个问题：流程不是一条直线的时候怎么编排。比如要根据结果走不同分支，或者要回到前面某一步重来，用链不好表达，用图就很自然：每一步是节点，节点之间用边连，边还可以带条件，所有节点共享同一个 State。它还能把状态持久化，让流程中断后继续，这个我项目里没用到。
>
> 我的项目里，LangChain 我用它的 ChatOpenAI 去连 DeepSeek；LangGraph 我只用了最核心的一部分，就是四个节点加一条条件边，实现"置信度低就回去重写查询"的循环，再加共享 State。并行、子图、持久化这些我没有用。说实话这个规模用普通函数也能写，选它是因为条件边和 State 的合并方式正好对应我的重试需求。

注意"保存状态"有两种意思：一次运行里节点共享 State（用了），和 checkpoint 持久化恢复（没用，对话那边是自己用 SQLite 存的）。别混着说。

## Q5 对话调查那部分为什么没用 LangGraph？

> 这个和项目的演进过程有关。我一开始做的是 Issue 查重，流程很固定，加一条低置信度回环的条件边，用 LangGraph 很合适。后来我在这个项目的基础上，扩展成了能对话、能自己查 Issue 和 PR 的调查 Agent，这一块是模型自己选工具，循环我是直接手写的，没有再迁移到 LangGraph。
>
> 说实话我知道用 LangGraph 也能做。但现在这套手写循环已经有了预算限制、暂停等用户回答再恢复、重启后继续，而且都有测试覆盖，所以我没有为了统一框架再去重写一遍。如果以后要加更复杂的多步编排，我会考虑迁过去。

**追问：两套风格不统一吗？**
> 确实不统一，这是演进留下来的。单次分诊是固定流程，对话调查是 Agent，本来也是两种性质的东西，我现在接受这个分工，更干净的做法是统一，但那属于重构，我没有优先做。

## 通用追问套路（答不上来时也能撑住）

任何追问都往三件事上靠：**做了什么（一个事实）、为什么这么选（一个取舍）、还有什么不足（一个缺口）。**

- 被问"为什么"：说你考虑过的另一种做法，以及为什么没选。
- 被问"有数据吗"：有就说数字和样本量；没有就承认，并说打算怎么验证。
- 被问"出错怎么办"：说兜底机制，再说怎么测的。
- 不会的问题：说"我没有深入了解过，我的理解是……"，不要装懂。
