# 会话记忆快照：读写分离（2026-10-03）

## 原实现与目的

每次普通聊天轮次都会调用 MemoryService.read_context，按当前消息选取偏好、历史经验和案例；然后把 memory 放进本轮调查上下文。目的在于让后续回答及时用上新沉淀的经验，并按当前问题选相关记忆。后台整理另有独立模型调用；这两条路径不是同一回事。

代价是选取结果、案例摘要及其时间信息会变化，模型输入的记忆部分也跟着变化。记忆存储需要更新，不等于每轮都应该重写已经发给模型的记忆视图。

## 现在的读取机制

首次普通轮次加载相关记忆，深拷贝并持久化到 session_memory_snapshot。之后同一会话不再按消息重新选记忆，即使首次结果为空也不会重读。记忆快照作为独立 system 消息，位于历史及动态调查上下文之前；动态上下文不再重复携带 memory。

新会话读取最新存储。旧会话若已有 selected_memory_context，首次升级沿用该读取视图。服务重启继续使用持久化快照。已经暂停的旧工具轮次保留原有消息协议，直到下一个普通轮次迁移；不在工具执行中途搬动旧消息。

后台 Memory 整理及其调用频率不变；数据库仍可更新。当前用户纠正通过后续聊天消息传入，系统明确要求其优先于旧快照。本改动没有添加自动记忆增量注入或新读记忆工具。

## 参考与教训

参考本地 claw-code（08106b0）：CLI 启动构建 system_prompt，ConversationRuntime 后续请求复用它。该项目读取的主要是 CLAUDE.md/AGENTS.md 等文件指令，不是我们每轮模型整理经验的完整等价实现。它有本地整份回答缓存和供应商缓存统计，不能把两者当作同一个命中率。没有从它证明 95% 命中率。

本次只借鉴“会话加载快照与长期存储分开”的生命周期，不照搬其全部架构。之前小样本测到的 Memory 整理低命中率不能直接证明读取快照也低；本改动直接针对读取前缀稳定，未优化整理请求。

## 不变与边界

- 不修改 config 中的滑动窗口、摘要触发条件、token 预算、检索或发布逻辑。
- 聊天整体仍按历史窗口重组；不是完整消息 append-only，也不保证某个缓存百分比。
- 首次选取未命中的经验、其他会话新增经验不会自动进入本会话；要立即使用可在对话明确补充，或新建会话。
- 存储的删除、编辑不会自动抹除既有聊天记录和已加载快照；当前方案不提供全会话遗忘保证。显式刷新/撤销快照应作为后续单独设计，不能为提高缓存而忽视撤销语义。
- 用户纠正在当前可见历史内优先；既有历史窗口导致的早期纠正遗失风险没有在此解决。

## 验证与调试入口

运行 `.venv/bin/python -m pytest tests/test_chat_runtime.py tests/test_chat_cost_context.py tests/test_history_window.py tests/test_memory_service.py -q`。

查看 session_memory_snapshot 是否首次设置后不变，以及 runtime_memory_snapshot 是否不再携带 memory；模型请求中“会话记忆快照”块应处于动态历史之前。回归覆盖空快照、深拷贝隔离、重启、新会话读取新记忆、旧会话迁移、提问恢复。离线替身只证明结构与状态行为，不证明模型必然理解纠正，也不证明真实缓存收益。
