# Issue 对话工作流：实施与排错记录

状态：代码实现与离线验证已完成；真实 GitHub 读取、真实模型交互、公开发布尚待手工验收。本文同时是使用时的排错索引；离线测试通过不能替代在线效果。

## 产品边界

这个 Agent 只处理仓库 Issue：把一个已存在的 GitHub Issue 拉入对话，围绕原文和后续补充排查历史问题，给出带出处的建议；若是尚未提交的新问题，则先查相似反馈，再起草新 Issue。用户确认后才允许发布。它不读本机日志、不修改代码、不自动提 PR，也不把普通聊天问题都变成故障排查。

一段对话绑定一个仓库，可以绑定一条源 Issue。后续消息补充到“当前问题”中，不修改 GitHub 原文。切换仓库或开始另一个问题时新建对话。

## 用户路径

1. 粘贴 `https://github.com/owner/repo/issues/123`，服务端从 GitHub 读取该 Issue 的标题、正文、状态与链接；检查它不是 PR，并确定所属仓库。已有快照可复用，未同步的仓库先建立索引。
2. 进入对话后显示源 Issue 卡片。用户可问“这和历史哪条像”“有人解决过吗”“我该继续补充还是新提一条”。一般咨询直接回答；需要历史证据时才检索。
3. 搜索结果区分本地快照和 GitHub 当前数据。快照最多含最近更新的 300 条，未命中不能证明仓库内没有相关 Issue。对发布新 Issue 的路径，再做实时查重。
4. 创建草稿时，只使用用户确认过的事实与源 Issue 内容；标题、正文可编辑。提交前展示目标仓库和完整内容，点击确认后才写入 GitHub；失败保留草稿，成功显示真实 URL。
5. 一次问题处理结束后，可以把“确认过的处理偏好”或“有证据的处理经验”存为独立记忆。下次对话只加载与当前仓库/问题相关的少量记忆；原始聊天记录不是长期记忆。

## 数据边界与排错定位

| 现象 | 先看哪里 | 应看到什么 |
| --- | --- | --- |
| Issue 链接导入失败 | 服务端 GitHub 请求与 URL 校验 | 明确区分链接格式、404、权限/额度、PR 误用；不创建空会话 |
| 导入成功但答非所问 | 会话 `source_issue`、本轮意图、规划器输出 | 源 Issue 进入有限上下文；一般咨询不会强制检索/问日志 |
| 查不到已存在 Issue | 本地快照时间与数量、实时搜索状态 | 不把“前 300 条快照未命中”写成“全仓库没有” |
| 回复引用错仓库 | `repository_id`、候选 ID 与 GitHub URL | 候选和写入目标均属于会话绑定仓库 |
| 点发布却没有新 Issue | 草稿状态、GitHub 权限与请求结果 | 失败保留草稿；未知超时不盲目重试，防止重复提交 |
| 新对话忘记旧经验 | 记忆是否确认、所属仓库、召回记录 | 会话过期不删除长期记忆；无关记忆不注入 |

### 接口与状态

- `POST /api/chat/issues/preview`：请求体 `{"issue_url":"https://github.com/owner/repo/issues/123"}`；只读，返回源 Issue。PR URL 或 GitHub API 拒绝访问时返回错误，不创建会话。
- `POST /api/chat/repositories/sync`：按 `owner/repo` 创建/复用本地快照；前端在导入 Issue 时自动等待这个任务完成。
- `POST /api/chat/sessions`：使用 `repository_id` 和可选 `issue_url` 创建会话；服务端再次核对该 Issue 确属绑定仓库，防止跨仓库错配。
- `POST /api/chat/sessions/{id}/issue-draft`：请求一次模型起草，**不发布**；消息里说“帮我起草 Issue”也可进入此路径。
- `PATCH /api/chat/sessions/{id}/issue-draft`：保存用户编辑的标题、正文及版本。版本不一致返回 409，刷新后再编辑。
- `POST /api/chat/sessions/{id}/issue-draft/publish`：需当前 `draft_id`、`version` 和 `confirmed=true`。`draft → publishing → published`；明确失败回到 `draft`，网络结果未知进入 `uncertain` 且禁止盲目重发。成功返回真实 URL。
- `POST /api/chat/sessions/{id}/memory-proposal`：按需提炼一条待审经验，不自动保存；消息里说“记住这个”也可触发。
- `POST /api/chat/sessions/{id}/memory`：用户编辑并确认后写入独立 SQLite 记忆库；待确认提案在服务端原子领取，重复点击不会重复写入。`GET /api/chat/memories` 查看；`DELETE /api/chat/memories/{memory_id}` 撤销。

短期会话保存在 `.local/chat_sessions.sqlite3`，按 7 天/最多 20 个会话回收；已确认记忆保存在 `.local/chat_memories.sqlite3`，不会随会话过期一起删除。它们都只适合当前本机单用户原型；公开部署前必须增加登录、用户归属、授权隔离与审计，不能直接暴露现有写接口。

## 验收用例

1. 导入一条公开 Issue 后，页面显示原文链接与所属仓库；刷新页面仍在。
2. 问“体验问题该提 Issue 还是 PR？”得到直接解释，不要求日志，不触发写工具。
3. 问“当前 Issue 和哪些历史反馈相近？”返回同仓库候选与可点开的原文，不能编造已解决状态。
4. 搜索失败或无明显命中时，助手承认覆盖边界，仍可起草，但不能说“确定没有重复”。
5. 发布前取消不会创建 Issue；确认一次至多创建一条；失败可继续编辑草稿。
6. 在一个对话中确认一条处理偏好后，新对话能在相关任务中复用；撤销后不再使用。

## 运行与验证

后端：`python -m uvicorn api:app --host 127.0.0.1 --port 8002`；前端正式页面需先在 `frontend/` 执行 `npm run build`。存活检查为 `GET /health`。后端测试为 `python -m pytest tests/ -q`；前端验证为 `npm run lint` 和 `npm run build`。

GitHub 读取公开 Issue 可无需写入权限。发布新 Issue 需要服务端凭据拥有目标仓库相应权限；不要把 Token 放到浏览器、草稿或日志。真实发布只在用户指定的测试仓库做人工验收，不能把自动化测试指向公开项目。

离线验证：后端 `114 passed`，前端构建通过，lint 退出码为 0（仍提示四处 React effect 状态同步警告，可作为后续重构点）。本地服务重启后 `GET /health` 返回 `ok`、首页返回 200，页面可见“导入已有 GitHub Issue”入口。真实 GitHub 读取、真实模型回答和发布尚未手工验收；不能用离线测试代替这一部分。
