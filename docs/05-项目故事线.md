# 05 项目故事线

> 第一部分是 2 分钟口头介绍逐字稿（约 500 字，正常语速 2 分钟）。
> 第二部分是 5 个 STAR 故事，全部来自代码演进中真实存在的事件（对应 git 历史、
> IMPROVEMENTS.md 和代码注释，不虚构）。

## 一、两分钟项目介绍（逐字稿，直接背）

> 我做了一个 issue 查重系统，解决的是开源项目维护者的一个真实痛点：新 issue 进来，
> 很大比例是历史上报过的重复问题，但人工要在十几万条历史里找，一条要花好几分钟。
>
> 系统输入一条新 issue 的原始文本，输出三分类判断——duplicate、similar 还是 new，
> 附带置信度、相关历史 issue 的编号和判断理由。整个流程用 LangGraph 编排成四个
> 节点。第一步 Query 分析，用 DeepSeek 把口语化的 issue 改写成技术检索式，同时抽
> 关键词；第二步混合检索，这里我做了双保险——改写结果和原文各跑一路，每路里面
> BM25 负责错误码这类精确信号、向量负责语义相似，用 RRF 按排名融合，两路再融合
> 一次，取 Top-30；第三步用 Cross-Encoder 对这 30 条精排到 Top-5；第四步 LLM 基于
> 这 5 条候选做判断。判断置信度低于 0.7 时，系统会带着上一轮的诊断信息——比如
> 候选分差、缺证据数量、上轮 Top-3 候选——回到第一步重写 query，最多重试两次。
>
> 数据用的是 GitBugs 数据集，本地索引了十万零六千条 issue。工程上我比较看重两点：
> 一是输出可信——LLM 返回的相关 issue 编号会过一层候选白名单校验，保证绝不返回
> 编造的 id；二是评估可信——我自己踩过一个大坑，最初的评测集里 34% 的 query 的
> 标准答案根本不在索引里，我用可达性过滤、剔除自命中、按重复家族隔离划分把评测
> 体系重建了一遍，现在检索层的每个指标都有可复现的脚本支撑。
>
> 这个项目最大的收获是想清楚了一件事：RAG 系统的上限在检索层，而检索层的优化
> 必须先有一套可信的评估，否则所有调参都是自我感觉良好。

## 二、STAR 故事

### 故事 1：评测集 34% 的题根本无解——重建评估体系

- **S（情境）**：检索链路搭完后我开始做量化评估，用数据集自带的 duplicate_of
  标注构建了一万三千条 query 的 golden set，跑出来的 recall 一直很难看，我一度
  以为是检索方案不行，反复调参数没有起色。
- **T（任务）**：搞清楚到底是检索差，还是"尺子"本身有问题。
- **A（行动）**：我停下调参，去人工抽查没召回的 case，发现相当一部分 query 的
  duplicate_of 指向的目标 issue 在索引里根本不存在——有的被清洗规则过滤了，有的
  数据集本身就缺。这种 query 无论检索多强都是零分。于是我给 golden set 构建器加
  了可达性校验：用 BM25 索引的 id 全集过滤每条 ground truth，剔除自引用和不可达
  目标，全部目标不可达的 query 整条丢弃；顺手修了另外两个坑——评测 query 自己就
  在索引里会自命中占位，检索时多取一条剔除自身；随机划分会把同一个重复家族拆到
  调参集和测试集两边造成泄漏，我用并查集把 query 和它的标注目标连成家族，以家族
  为单位做 80/20 划分。
- **R（结果）**：13,104 条原始 duplicate 记录里清出 4,505 条（34%）无解 query，
  之前的指标全部被系统性低估了约三分之一；清理后得到 8,599 条有效 query、3,333
  个家族，全部构建统计都随 golden set 一起落盘可复现。这件事之后我把"先验证尺子
  再优化"当成铁律。（代码：`eval/golden_set_builder.py:56-179`）

### 故事 2：白召回的候选——docstore 补证据

- **S**：v1 有个我在 README 里自己承认的已知限制：BM25 索引只存 id，只被 BM25
  召回、没被向量路命中的候选没有 title 和 body。往下游走，Reranker 对着空字符串
  打分，Decision 对着空字符串判断——这些候选等于白召回了。而错误码强匹配的候选
  恰恰最容易只被 BM25 召回，最有价值的一路信号在最后两步失效。
- **T**：让所有进入精排和决策的候选都带上正文证据，同时不能把向量路已有的
  "最相关 chunk"覆盖掉。
- **A**：评估了三个方案：正文塞进 bm25.pkl（耦合，加载变重）、在线反查 Chroma
  （30 次点查，且 Chroma 存的是 chunk 拼不回完整正文）、独立 docstore。选了第三
  个：离线用和建索引完全相同的清洗链路产出 id→{title, body 前 1200 字符} 的
  pickle，1200 是按下游需求定的——Reranker 只看 800、Decision 只看 400。在
  HybridRetriever 融合排序后统一补齐，规则是"只填空、不覆盖"，因为向量路的 body
  是命中的 chunk，是比正文开头更好的精排证据。docstore 缺失时自动退回旧行为，
  只降效果不崩服务。
- **R**：冒烟测试从"BM25-only 候选全空"变成 30/30 候选都有正文证据；配套单元测试
  锁住"补空不覆盖"的语义。（代码：`src/docstore.py`、
  `src/retrievers/hybrid_retriever.py:203-228`、`tests/test_docstore_hydration.py`）

### 故事 3：LLM 编造 issue 编号——白名单校验与降级重试

- **S**：Decision 节点偶发返回候选列表里不存在的 issue id。对查重系统这是致命的
  ——维护者按编号点过去发现不存在，对系统的信任直接归零。prompt 里其实早就写了
  "只能从候选列表选"，但提示词约束是概率性的，挡不住所有情况。
- **T**：把"返回的每个相关 id 都真实存在于本轮候选"变成程序保证的硬性质，而不是
  祈祷模型听话。
- **A**：在 Decision 节点加了一层程序级校验：decision 必须命中三个枚举，否则按
  解析失败降级；confidence 强转并截断到 [0,1]；related_issues 逐个对照本轮精排
  候选的 id 白名单，不在的过滤并记日志。最微妙的是决策语义：如果一个 duplicate
  判断过滤后一个合法 id 都不剩，这个结论就没有任何可核查证据——我选择把它降级为
  new 并把置信度压到 0.4 以下，这样低置信度会在重试预算内自动触发新一轮检索，
  系统"自己再试一次"，而不是带着幻觉结论结束。
- **R**：幻觉 id 从"偶发泄漏给用户"变成"结构上不可能返回"；7 个针对性单元测试
  覆盖枚举、截断、白名单、降级四条路径。（代码：`src/agent/nodes.py:388-425`、
  `tests/test_decision_validation.py`）

### 故事 4：改写是把双刃剑——双路召回兜住上游单点故障

- **S**：Query 改写让检索式更技术化，但复盘 badcase 时发现一类失败：LLM 改写时
  把原文里的关键错误码删掉了，或者术语改写发生漂移，导致真正的 duplicate 在召回
  层就彻底丢了——上游一步错，下游 Rerank 和 Decision 再强都无力回天。
- **T**：在不放弃改写收益的前提下，消除"单次 LLM 输出决定全链路生死"的结构风险。
- **A**：把检索改成双路：改写 query 和原始文本各跑一遍完整的混合检索，再用第二层
  RRF 融合两路排名。几个细节：两路按 casefold 去重，改写失败回退原文时只跑一路，
  不白花一倍时间；外层融合同分时利用稳定排序让改写主路排前；同一 issue 在两路的
  正文完整度不同时保留更完整的版本。同时我写了一个对照 benchmark，固定改写结果
  和标注，量化双路相对单路的 rescue 率和 regression 率——因为它需要人工确认的
  案例，我没有编数据，目前是"框架就绪待标注"状态，这点我如实说。
- **R**：结构上，改写幻觉从"全链路失败"降级为"损失一路信号"；行为上有单元测试
  锁住去重、融合和证据保留逻辑。待 verified 案例标注后可以给出量化结论。
  （代码：`src/retrievers/hybrid_retriever.py:110-201`、
  `eval/benchmarks/dual_query_retrieval.py`；对应 git 提交 "Add dual-query
  retrieval benchmark"）

### 故事 5：一次 401 排查——配置加载的隐蔽优先级

- **S**：v2 联调时所有 LLM 调用突然 401 认证失败。检查 .env 文件，key 是对的；
  用 curl 直接测这个 key，也是通的。
- **T**：找出"配置明明正确却认证失败"的原因。
- **A**：细看报错里的 key 尾号，和 .env 里的对不上——顺着查发现 shell 环境变量里
  残留着一个早已失效的 DEEPSEEK_API_KEY，而 python-dotenv 的 load_dotenv() 默认
  **不覆盖**已存在的环境变量，所以项目一直在用那个死 key。修复很小：
  `load_dotenv(override=True)`，让项目 .env 显式优先，并把这个坑写进代码注释和
  CLAUDE.md 的踩坑记录。排查过程中还发现一个更严重的问题：v1 的 .env.example
  里提交的是一个真实有效的 key，已经进了 git 历史——立即把示例文件改成占位符、
  真实 key 移入 gitignored 的 .env，并标记该 key 需要作废轮换。
- **R**：401 根因清除；顺带堵住一个真实的凭据泄漏。教训有两条：报错信息里的
  每个字段都值得对一遍（key 尾号直接指向了真相）；示例配置文件里永远只放占位符。
  （代码：`config.py:8-10` 注释）

## 三、讲故事的使用建议

- 被问"最大的挑战"→ 讲故事 1（评估重建），它有数字（34%）、有方法论（先验尺子）、
  有可复现产物，含金量最高。
- 被问"debug 能力"→ 讲故事 5（401），短、真实、有反转。
- 被问"工程严谨性"→ 讲故事 3（白名单），落点是"把概率性约束变成结构性保证"。
- 被问"系统设计"→ 讲故事 2（docstore）或 4（双路），落点都是"识别单点故障并兜底"。
- 每个故事结尾主动补一句局限（故事 4 的"待标注"、故事 1 的"分类层还没标注集"），
  诚实是最强的可信度信号。
