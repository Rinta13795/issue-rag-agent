# 对话检索与澄清策略

用户说出“skill 无法执行”时，虽然没有错误码，这仍是一条可检索的故障现象。助手应先用这段原话查询本地历史 Issue，再判断是否需要追问；不能把精确日志当成启动检索的门槛。

| 当前条件 | 行为 |
|---|---|
| 有故障现象，规划器也提取了事实 | 用已校验的事实检索 |
| 有故障现象，但规划器漏提事实 | 用用户原话中的故障行做一次有界检索，不记录为已确认事实 |
| 没有可检索的现象 | 问一个最有帮助的问题；用户补充线索后再查 |
| 已查过相同线索 | 不重复调用检索；说明查过的范围与当前证据限制 |
| 已有候选，用户追问是否解决 | 用已有候选回答，不重新检索，不把相似候选说成已验证的修复 |

这里的“先行动”仅指查询本地已索引的历史 Issue。助手不能读取用户本机终端，也不能实时查看任意 GitHub 仓库。查不到候选不等于外部世界无人解决；回答中必须说明范围，并在必要时追问报错原文或仓库。澄清时界面提供与当前状态相符的选项，并保留自由输入。

设计依据：Anthropic 在 [Trustworthy agents in practice](https://www.anthropic.com/research/trustworthy-agents) 中区分了可由 Agent 自行研究补齐的信息与只有用户能决定的问题，并指出过度停下来提问会削弱自主性；[Writing effective tools for AI agents](https://www.anthropic.com/engineering/writing-tools-for-agents) 强调工具应让 Agent 能以多种策略完成真实任务。本项目据此采用“低风险检索先做、证据不足再澄清”，不是复刻 Claude 的内部实现。

回归验证见 `tests/test_chat_service.py`：覆盖模糊故障先检索、拒绝模型虚构事实、查无候选后不重复检索、已获候选的解法追问，以及连续澄清的能力边界说明。
